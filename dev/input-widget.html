Design walkthrough

The Input

One instrument for everything you put into the box — typing, voice, photos, files, selections — pulled out of the chat and given a firm shape. Three nouns carry the whole design: the Emission (what you're composing), the Input (the instrument itself, a true singleton), and the Target (whatever accepts the submission).

Why anything needs to change

An inventory of the current code (~4,200 lines across 30+ files) found the mess isn't essential complexity — it's the absence of two abstractions. The receipts:

  • The message-being-composed doesn't exist as a thing. Text, images, files, selections and audio live in six separate hooks; the payload is assembled ad hoc at send time — twice, in parallel: the typed path and the voice path are separate implementations sharing one helper. Every payload rule can drift between them.
  • There is no boundary. The "composer" is a set of hooks owned by the chat page, passed down as a 40+-prop bag, entangled with the chat machine, the companion pane, and card-activity tracking.
  • "The input stays when you switch chats" is mostly false today. Typed text survives (saved per-session); attachments, file uploads and selections are destroyed by the remount.
  • Stored audio is one mutable slot. The "agent can fetch the original audio" feature keeps exactly one blob, in memory, overwritten by the next send, gone on reload.
  • Stop is conflated with send. Interrupting the agent lives in the input surface, entangling "add to the conversation" with "halt the process."

The three nouns

EMISSION

What you're composing

One value holding text + images + files + selections + audio, with an id that becomes the message id. Feeders write into it through one editor; panels just render slices of it. One assemble() function turns it into a payload — the dual typed/voice assembly paths die.

INPUT

The instrument · a true singleton

There's one of you, so there's one input. It holds the current emission, is aimed at a target, and hosts the feeders (keyboard, voice, attach, camera, frame signals). Re-aiming — switching chats, or flipping from chat to inbox-deposit — never touches the emission.

TARGET

What accepts the submission

An acceptor with observable status (ready · busy-will-queue · unavailable) shown before you submit, and a receipt after (delivered · queued · deposited · rejected). It owns its own controls — stop lives here, on the target's strip, not in the input.

System map

Read it left to right: feeders write into the emission through one editor; submit() assembles the emission and hands it to the aimed target, which answers with a receipt. Two back-channels flow the other way: the target's status (shown on the submit button before you press it) and the agent's original-audio requests served from retention.

Two stances: conversation and listening

Everything above assumes one interaction stance — conversation: mic hot, turn-taking active, speech ephemeral. There is a second, motivated by real friction (trying to learn from a long spoken answer while a hot mic keeps hearing the room as "interruptions," with no way back to a missed sentence).

Conversation

Mic hot. Barge-in active — your speech pauses the agent's (the one sanctioned crossing). Speech output is ephemeral; the exchange is the point. Everything specified above, unchanged.

Listening

Mic cold. Podcast posture: a long generation plays through a seekable Player — pause, rewind 15s, scrub the synced transcript, set the rate. Ambient sound cannot interrupt, because nothing is listening. Received speech is retained (audio + transcript), so rewind is a fetch, not a regret.

Pause is just pause. In listening posture, a pause most likely means the room interrupted you — the doorbell, not a question. So pausing never arms the mic; entering conversation is always an explicit act (from paused, or the one-gesture pause-and-talk). And when you do cross over, where-you-were rides along as a selection: the playback marker enters the emission through the same addSelection path a card selection uses — ref = the retained utterance, text = the last words before the pause, position = the timestamp. Your "wait, what did you mean there?" arrives carrying its own context.
type InteractionMode = "conversation" | "listening";

interface Player {  // the target's long-form speech, seekable
  readonly state: Observable<{
    status: "playing" | "paused" | "ended";
    position: number; duration: number | null;
  }>;
  play(); pause();
  seek(to); nudge(seconds); setRate(rate);
  readonly transcript:
    Observable<readonly TranscriptSegment[]>;
}

The Player hangs off the target — it's the target's output surface, sibling to the status strip. The input stays untouched; in listening mode the voice feeder isn't "coordinated," it's off.

One wire flips the mode. The barge-in crossing (coordinate()) was already the right seam — listening mode is that crossing suspended, not a new architecture. InteractionMode is frame state, like everything ephemeral.

Retention symmetry. Your audio is retained by emission id; the agent's long utterances get the same treatment — which is what playback markers point at, and what makes rewind possible at all.

The emission's lifecycle

Queued still clears. A queued receipt is a success: the emission is accepted and now belongs to the target's queue, rendered on the target's strip. The input immediately hosts a fresh emission — it's an instrument, not a mailbox.

The interfaces

interface Emission {
  readonly id: EmissionId;
  readonly text: string;
  readonly images: readonly ImageAttachment[];
  readonly pendingImages: number;
  readonly files: readonly FileAttachment[];
  readonly selections: readonly Selection[];
  readonly audio: RetainedAudio | null;
  readonly origin: "typed" | "voice" | "mixed";
}

// all mutation through one surface:
interface EmissionEditor {
  setText(text): void;
  insertAtCursor(text): void;   // [imageN] tokens…
  addImages(blobs): Promise<void>;
  addFiles(files): Promise<void>;
  addSelection(input): void;
  attachAudio(audio): void;
  remove(kind, id): void;
  clear(): void;
}

function assemble(e: Emission, ctx): AssembledPayload;

The id is load-bearing. It's generated at compose time, becomes the messageId the chat already uses, and is the key under which the original audio is retained — so "agent fetches the audio for message X" is one lookup, not a race against a mutable slot.

One editor. Feeders call it; the attachment panel, selection chips and dictation-recovery widget become plain renderings of emission slices. This replaces six root-owned hooks and the 40-prop bag.

One assemble(). origin picks the <typed>/<speech> wrapper; selection folding happens in exactly one place. The typed and voice send paths stop being two programs.

interface Input {
  readonly emission: Observable<Emission>;
  readonly editor: EmissionEditor;
  readonly target: Observable<Target>;
  aim(target: Target): void;
  submit(): Promise<Receipt>;
  readonly feeders: {
    keyboard; voice; attach; camera; signals;
  };
  readonly retained: RetentionStore;
}

interface VoiceFeeder {
  readonly profile: "streaming" | "recorded";
  readonly state: Observable<VoiceState>;
  start(); stop(); cancel();
  readonly intents: Observable<VoiceIntent>;
    // "submit" | "cancel" | "mic-off" | "erase"
  coordinate(speaking): Unsubscribe;
    // THE sanctioned crossing: target speech
    // pauses the mic (barge-in / turn-taking)
}

One input per person. Its state — the emission, the aim — is frame state: never a card, never in the URL. It persists whole under a singleton key, so photos and selections survive a chat switch, not just text.

Feeders never send. Saying "send it" makes the voice feeder emit an intent; the input interprets it and calls submit(). The feeder's job ends at feeding and signaling.

Two voice pipelines, one interface. Streaming transcription (chat today) and record-then-upload (capture today) are genuinely different machines — they stay separate profiles under one API. Unifying interfaces, not internals.

The keyboard shell escapes. Mobile open/locked/auto-close state is embodiment chrome — it only ever lived in "composerMachine" for lack of a home.

interface Target {
  readonly kind: "chat" | "place" | "unaddressed";
  readonly status: Observable<
    | { state: "ready" }
    | { state: "busy";
        disposition: "will-queue" | "will-interrupt" }
    | { state: "unavailable"; reason }>;
  readonly pending: Observable<PendingEmission[]>;
  readonly controls: TargetControl[];  // ← stop lives here
  readonly speaking?: Observable<SpeechState>;
  accept(payload): Promise<Receipt>;
}

type Receipt =
  | { disposition: "delivered"; emissionId; at }
  | { disposition: "queued";    emissionId; at;
      behind: "turn" }
  | { disposition: "deposited"; emissionId; at;
      cardPath: string }   // a deposit's receipt
                             // is a card address
  | { disposition: "rejected";  emissionId; reason };

Status is pre-submit truth. The send button renders the acceptor's state: "Send", "Queue", or disabled-with-reason. HTTP figured this out decades ago — 200 vs 202 Accepted — surfaced here at compose time.

Stop is a target control, rendered on the target's status strip beside the input but across the API line. Submit always means add to the conversation; interruption is only ever the explicit target-side control. A place target simply has no stop, and the input doesn't know the difference.

Two adapters to start: ChatTarget (wraps send + turn state + interrupt; merges witness context — open card, card activity — at accept, so the composer never sees frame state) and PlaceTarget (wraps today's capture finalize, which already produces an inbox card — hence the receipt with a cardPath). "Unaddressed" is the declared future triage-memo kind.

Four analogies that carry the design

An instrument, not a mailbox The input is what you speak through. What's queued belongs to the acceptor; the instrument is immediately free for the next thought.
Ctrl-C Interrupt aims at the running process, never at the readline buffer. Stop is the target's control, not a key on the keyboard.
HTTP 202 Accepted "Received, will process" is a different answer than "done" — and the UI should say which one you're about to get, before you press send.
One microphone You don't have a microphone per conversation. You have one, and you point it — at a chat, at the inbox, or (someday) at "wherever this belongs."

Decisions, and what they trade away

Singleton draft

One emission that travels with you across chats — the boxholder's stated model. Trade: departs from the messaging-app convention of per-conversation drafts. Chosen because the box's input is one person's instrument, not N conversation buffers.

Queued clears the input

The queue is the target's, visible on its strip. Trade: you can't edit a queued message from the composer (it's submitted). Chosen so the instrument is always free and "what's pending" has one honest home.

Stop moves out

Submit never interrupts; interruption is only the explicit control on the target strip. Trade: one extra visual region beside the input. Chosen to unconflate two unrelated verbs that currently share a surface.

One sanctioned crossing

Target speech pauses the mic (barge-in / turn-taking) via coordinate(). Trade: the boundary isn't perfectly airtight. Chosen because pretending otherwise would just hide the wire.

Where this goes if accepted: staged implementation, first stage pure refactor (Emission + assemble(), doctests, no UI change), then the boundary, then targets/receipts/stop, then singleton persistence (the visible behavior change), capture-as-PlaceTarget last.
