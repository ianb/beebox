A box agent regenerated a PDF at the same path, in a card's attach scope. The
app kept showing the previous version. Nothing cleared it — not opening the
card again, not a hard reload. The agent had to write a **new file under a new
name** for the boxholder to see the change, which is why the same document
exists several times with a counter in its name. The session spent real time on
"is it regenerating or not", which is the expensive part: the boxholder could
not trust what was on screen.

## Where it comes from

The server side looks correct. `/api/files/*` serves a weak ETag built from
mtime and size (`beebox/src/webapp/file-etag.ts`) with
`Cache-Control: no-cache` (`beebox/src/webapp/routes/api-files.ts:171,198`),
so a changed file should revalidate and a 304 should only happen when the
bytes really are unchanged.

The URL is the problem. `apiRawFileUrl`
(`beebox/src/frontend/src/api-core.ts:84`) returns
`${apiBase}/files/${path}` with **no version token**, and the PDF renderer
hands that straight to `PdfFrame` (`renderers/pdf.tsx:17`), which embeds it in
an `<object>` carrying the browser's built-in PDF viewer
(`components/PdfFrame.tsx`). A plugin-rendered resource inside `<object>` is
not reliably re-fetched on a page reload: the browser's PDF viewer keeps its
own copy keyed by URL. Same URL, same document, regardless of what the server
would say if asked.

That also explains why a hard reload failed: a hard reload re-fetches the
page's own resources, but the embedded viewer is not obliged to re-request
anything.

## The fix, roughly

Give the URL a version token so regenerated bytes get a new URL. The token
already exists: the same mtime+size ETag the route computes, and `ViewFile`
already carries an `etag` for conditional writes (see the comment in
`file-etag.ts` naming all three consumers). Appending it as a query parameter
is enough — `?v=<token>` — and it is a cache key the server can ignore.

Points to settle:

- **Which surfaces need it.** PDFs are the reported case, but any
  plugin-rendered or long-lived embed has the same exposure. Images go through
  a different route (`api-image.ts`) that already sets ETag and `no-cache`;
  whether they have the same problem in practice needs a check rather than an
  assumption.
- **Where the token comes from.** The renderer gets `data.path`; it needs the
  file's current version too, so this may be a small change to what a renderer
  receives rather than a one-line URL edit.
- **Live updates.** When the file changes while a card is open, the version
  the client holds is stale until something tells it. The box watcher already
  reports file changes; whether the open view re-derives its URL on that event
  is the difference between "correct after reopening" and "correct".

## Related

An agent working around this by writing a new filename each time is the
behavior to remove; it litters the box with near-duplicates and each one needs
its own card and refs.
