The launch needs a SECURITY.md-shaped "what this can touch" page (the
OpenClaw lesson from
[the competitive research](../../../research/openclaw-hermes/README.md):
install UX was never the complaint, blast radius was — what saved them was an
explicit threat-model doc). Rather than hand-writing it once and letting it
rot, the boxholder wants a **system**: the report is generated and updated by
an agent, and the prompts that generate it are committed alongside it.

The claim this makes is a *process* claim, stated honestly: a reader can't
verify the report wasn't influenced by malice, but they can see the prompt
that produced it, the diff of every regeneration, and the cadence — the
report is auditable as a process even where it isn't verifiable as an
artifact. ("Hard to verify against malice, but makes real process claims" —
boxholder, 2026-07-20.)

Content the generation pass should inventory: unauthenticated endpoints,
auth surfaces and bind defaults, what the agent can touch (filesystem/tools),
external services data flows to, residual accepted risks.
[todo-security.md](../../../callback-box/docs/todo-security.md) is the seed —
it's already an honest posture doc (auth model, setup-token window, no MFA)
and shows the right register.

Fits existing infrastructure: knowledge-audits
([docs](../../../callback-box/docs/knowledge-audits.md)) and the doc-generation
tooling are precedents for committed-prompt → generated-artifact loops.

**First run produces the launch SECURITY.md** — gate 4 in
[soft-launch posture](../../decisions/2026-07-20-soft-launch-posture.md) — so
the system and the gate are one piece of work, not two.

Open: where the prompt lives (a procedure card? `src/dev/`? a skill), what
triggers regeneration (release cadence? endpoint-diff detection?), and
whether the generated doc carries a visible "generated by <prompt>, last run
<date>" header (lean: yes, that's the whole point).

## Design notes (2026-08-07 — boxholder + main session)

The shape settled into **two artifacts**:

- **Structured version** — a breakdown / checklist, not prose: an accounting,
  section by section. Easier to update from a git diff because it's clear where
  any given change belongs. Categories:
  - **Endpoints** — an accounting of every endpoint, its auth, and its abilities.
  - **Credentials** — the same accounting for every credential/secret.
  - **Data egress** — each place data leaves the machine (e.g. to Anthropic) and
    what the dangers are there.
  - **Internal security practices** — how the code/process defends itself.
  - **Operational security** — deployments and the running server.
  - **Feature-specific sections** — special coverage for particular features
    (e.g. publishing).
- **Final report** — the human-facing synthesis derived from the structured
  version.

**Update mechanism — anchor to git rev, not time.** The structured version
records the rev it was generated at; updating means adjudicating
`git diff <last-rev>..HEAD` scoped to security-relevant surfaces, not
re-deriving from scratch. The checklist form makes this tractable — a diff maps
cleanly to the section it affects. Provenance header carries: `generated-by`
(prompt/skill path), `generated-at-rev` (the update anchor), date, model,
`reviewed-by` (human).

**The rubric IS the committed artifact.** The prompt is an ordered inventory +
evaluation process (the categories above + per-item state/severity/reachability
+ a map from each category to the code surfaces it covers, so the diff can be
scoped), not "write a security doc." Regeneration is reproducible and auditable
because the process is committed.

**Granularity: lean detailed — an agent consumes this.** The structured version
is exhaustive (per-endpoint, per-credential, per-egress point). The final report
is the readable layer over it.

**Human review before commit is load-bearing** — an agent-generated *security*
doc that auto-commits could assert false safety. Loop: agent drafts → boxholder
reviews → commit; the header records `reviewed-by`.

**Prompt home (tentative): a skill** (`/security-report`), body = the committed
rubric; versioned and human-invoked. Alternatives weighed and rejected: a
`src/dev/` script (too automated for this), a box procedure card (wrong layer —
this is the *engine's* security surface, not box content).

**todo-security.md's fate:** its actionable "future hardening" items get filed
as issues (breakdown via subagents, 2026-08-07); its residual-accepted-risk
prose seeds the structured version's accepted-risks entries. It dissolves into
(issues + the report) rather than surviving as a third backlog.

**README linkage:** the README keeps a short, personal "what leaves your machine"
section and links here; SECURITY-level detail lives in these two artifacts, not
duplicated in the README.
