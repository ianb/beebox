# Highlight Scout: Agent Zero

## 1. Identity / focus

Agent Zero bills itself as "a full Linux system for your AI agent" (`README.md:6-8`): one Docker container ships a full XFCE desktop, a native browser, LibreOffice, and a "Plugin Hub" of 100+ community plugins. It is explicitly a general personal-computer-use agent, not a coding assistant — flagship features in the README are a real desktop the agent drives (Blender, GUI apps), a browser with "Annotate mode" for lifting/critiquing web UI, live cowork on Markdown/ODF documents, and "Time Travel" workspace snapshotting (`README.md:95-186`).

Philosophy, per the README's own framing: "transparent and extensible by design" — "almost nothing is hidden. Prompts live in `prompts/`, tools live in `tools/` or plugins, and built-in behavior can be inspected, changed, replaced, or extended" (`README.md:222-226`). It positions itself against black-box agent products.

Maturity/community: real and active — Discord, Skool community, YouTube channel, GitHub Sponsors, a separate desktop "A0 Launcher" installer product, and a companion commercial-ish product "Space Agent" (`README.md:10-13, 44-53, 236-247`). Internally it's well past hobby-project stage: 106 files under `tests/`, a plugin system with 25 first-party plugins (`plugins/_*`), a documented extension API (`docs/developer/extensions.md`), and a per-file documentation convention (`*.dox.md` / `AGENTS.md` "DOX" files) that pairs almost every source file with an ownership/contract/verification note — e.g. `tools/call_subordinate.py.dox.md`. Last commit in the clone: 2026-07-02, i.e. actively maintained.

## 2. Architecture in brief

### Hierarchy model (superior/subordinate agents)

- One Python `Agent` object per level; `Agent.DATA_NAME_SUPERIOR` / `DATA_NAME_SUBORDINATE` are just keys in a per-agent `data` dict (`agent.py:357-358`).
- Spawning: the `call_subordinate` tool (`tools/call_subordinate.py:37-92`) is a normal agent-invoked tool, `Delegation.execute`. On first call it does `sub = Agent(self.agent.number + 1, config, self.agent.context)`, `sub.set_data(DATA_NAME_SUPERIOR, self.agent)`, `self.agent.set_data(DATA_NAME_SUBORDINATE, sub)`, then feeds it a user message and awaits `subordinate.monologue()` synchronously (`tools/call_subordinate.py:57-79`) — i.e. the superior's own tool-call blocks until the subordinate's full turn returns. Each agent can only ever have **one live subordinate at a time** (a single slot, not a list); calling again with `reset=false` reuses it, `reset=true` respawns.
- Depth bound: **there is none in code.** `Agent.number = self.agent.number + 1` and a subordinate can itself call `call_subordinate` to spawn a grand-subordinate — nothing stops arbitrary recursion depth (confirmed by reading the tool and `tests/test_subagent_profiles.py`, which never exercises or asserts a depth cap). The only guardrails are prompt-level social pressure, not code: "never delegate full to subordinate of same profile as you", "always describe role for new subordinate" (`prompts/agent.system.main.solving.md:19-21`), and for the scheduler specifically, "do not create recursive task prompts that schedule more tasks" (`prompts/agent.system.tool.scheduler.md`).
- Communication up/down: down is a plain user message into the subordinate's history (`hist_add_user_message`); up is the subordinate's return value, added to the superior's history as a tool result (`fw.msg_from_subordinate.md`, wired in `agent.py:296-300`). There's also a broadcast-intervention path: `AgentContext.communicate()` walks the *whole superior chain* to inject a user "intervention" message into every live ancestor agent when the user interrupts, up to a `broadcast_level` (`agent.py:260-273`) — and `_process_chain` (`agent.py:290-311`) recursively calls back up the superior chain once a subordinate's monologue ends, so a full multi-hop chain resolves before the top-level agent responds to the user.
- Profiles specialize subordinates: `call_subordinate` takes an optional `profile` arg validated against `agents/<name>/agent.yaml` directories (`agents/agent0`, `default`, `developer`, `hacker`, `researcher`, `tiny-local`); each just overrides a subset of prompt files (e.g. `agents/hacker/prompts/` only overrides `agent.system.main.environment.md` and `agent.system.main.specifics.md`).

### Prompt-as-OS

Prompt assembly is explicitly file-based and layered, per the agent's own self-knowledge doc (`knowledge/main/about/architecture.md:14`): "Main prompts come from `prompts/`, profile overrides from `agents/<profile>/prompts/`, and plugin prompts from `plugins/<plugin>/prompts/`." The top-level `prompts/` dir alone has 73 files, roughly in four families:
- `agent.system.*` — the actual system prompt, composed of includable fragments: role (`agent.system.main.role.md`), environment, communication style, solving procedure (`agent.system.main.solving.md`), tool docs (one `agent.system.tool.*.md` per tool), behavior (`agent.system.behaviour.md` + a mergeable `agent.system.behaviour_default.md`), skills, secrets, MCP tool docs, vision tools, projects.
- `fw.*` — framework-injected messages the *system* sends the agent mid-loop (errors, timeouts, nudges, tool-not-found, subordinate messages, truncation notices) — i.e. even internal plumbing messages are editable markdown, not hardcoded strings.
- `behaviour.*` — the self-modification machinery (see below).
- `memory.*` — prompts for the utility-LLM calls that do memory recall/consolidation (referenced from `plugins/_memory/prompts/`, not shown above).
Profile dirs (`agents/*/prompts/`) only need to contain the *override* files; everything else falls through to the base `prompts/` files. Nothing is compiled — it's read straight off disk per turn (`agent.read_prompt`), so editing a `.md` file changes agent behavior on the very next turn with no rebuild step.

### Memory (auto-memorization, solutions)

Vector memory has three areas — `Memory.Area`: `MAIN`, `FRAGMENTS`, `SOLUTIONS` (`plugins/_memory/helpers/memory.py:53-59`), backed by FAISS. Two always-on extensions drive it without any explicit tool call:
- **Recall** (`plugins/_memory/extensions/python/message_loop_prompts_after/_50_recall_memories.py`): every N iterations (`memory_recall_interval`), a utility-LLM call turns the recent conversation into a search query, then does a similarity search against `MAIN`/`FRAGMENTS` and, separately, `SOLUTIONS` (lines 130-146), optionally post-filtered by another LLM validation pass, and injects results into the prompt's `extras_persistent`.
- **Memorize solutions** (`plugins/_memory/extensions/python/monologue_end/_51_memorize_solutions.py`): at the end of *every* monologue, a background task runs a utility-LLM call over the just-finished conversation (system prompt `memory.solutions_sum.sys.md`) asking it to extract "problem/solution" pairs, parses the JSON, and inserts each as `# Problem\n...\n# Solution\n...` into the `SOLUTIONS` area — either raw or through an "intelligent consolidation" pass (`memory_consolidation.py`) that finds and merges/dedupes near-duplicate solutions rather than piling up redundant entries (lines 38-210). This is fully automatic background learning: the agent doesn't decide to memorize a solution, a framework extension always tries to, gated only by a settings toggle.
- Retrieval loop: `agent.system.main.solving.md:9` ("check memories solutions skills prefer skills") tells the agent to prefer a recalled skill/solution over solving from scratch — the recall extension has already put candidates in context by the time the agent reasons about step 1.

### Instruments vs tools vs skills

The historically famous Agent Zero "instruments" concept (user-authored callable scripts, distinct from built-in "tools") appears to have been folded into the newer **Skills** system in this version: `knowledge/AGENTS.md:11` still reserves `instruments/` as a knowledge root ("`fragments/`, `instruments/`, and `solutions/` are reserved knowledge roots") but there is no live `knowledge/instruments/` content, and the actual runtime docs (`docs/guides/skills.md`) describe Skills as "focused instructions Agent Zero can load when a task needs them" — loaded on demand or pinned into the prompt "Protocol" section, distinguished from Agent Profiles (broader role change) and Projects (workspace/memory/secrets scope) (`docs/guides/skills.md:60-66`). Core built-in **tools** remain a small fixed Python set (`tools/*.py`: `call_subordinate`, `scheduler`, `search_engine`, `parallel`, `wait`, `response`, `notify_user`, `a2a_chat`, `document_query`, `vision_load`, `skills_tool`, `unknown`), while code execution (shell/Python/Node, plus SSH) is itself a plugin (`plugins/_code_execution/tools/code_execution_tool.py`) — i.e. general computer-use lives in a tool, and reusable procedures live in skills/plugins, not a separate "instrument" tier anymore.

### Docker runtime and UI

Single Docker image (`docker/run/Dockerfile`, `docker/base/Dockerfile`) exposing ports 22/80/9000-9009, with `docker-compose.yml` mounting the *entire* repo (`./agent-zero:/a0`) read-write into the container — there is no read-only mount separating framework code (`prompts/`, `tools/`) from user data; only `usr/` is documented as the "survives updates" convention (`knowledge/main/about/architecture.md:12,16`). Nothing in the container prevents the agent's own shell/code-execution tool from editing `prompts/*.md` directly. The Web UI (`webui/`) hosts a chat plus a "Canvas" side panel that can show a live XFCE desktop, a browser view with DOM-annotation mode, and a cowork Markdown/ODF editor (per README screenshots/gifs), plus a Memory dashboard, Plugin Hub, Skills selector, and "Time Travel" snapshot browser.

## 3. Highlights

**Does the hierarchy actually buy anything observable?** Partially, and mostly as *context isolation*, not as parallelism or specialization depth. The one concrete, tested pattern is profile-scoped delegation: spawn a `researcher` or `developer` subordinate so its context window fills up with its own tool calls/search results instead of polluting the superior's context, then hand back only the distilled result (`tools/call_subordinate.py:79-92` even special-cases long results with a `§§include(path)` hint so the superior doesn't have to re-paste them). `tests/test_subagent_profiles.py` only exercises profile validation/switching, not multi-level chains, depth limits, or any emergent "team" behavior — so the hierarchy's real-world exercise in this repo is shallow (superior → one subordinate), and the "OpenAI Codex plan," README use-cases, and skills docs all describe single-agent workflows; multi-agent delegation is mentioned once in README ("Multi-Agent Cooperation") with no worked example beyond "every agent can create subordinate agents to break down work." This reads as a real, working mechanism rather than vaporware, but the codebase gives no evidence it's exercised beyond one hop in practice, and nothing enforces bounded depth — a mis-prompted agent chain could recurse arbitrarily (the only brake is the solving-prompt's soft rule against same-profile delegation, `prompts/agent.system.main.solving.md:19`).

**Self-modification story.** Two tiers, with very different guardrails:
1. Narrow, guarded: the `behaviour_adjustment` tool (`plugins/_memory/tools/behaviour_adjustment.py`) lets the agent (invited by the system prompt: "use for durable behavior, personality, style, response-format... rules", `prompts/agent.system.tool.behaviour.md`) rewrite a single memory-scoped `behaviour.md` file. Crucially it never lets raw text overwrite the file — every adjustment goes through a *merge* utility-LLM call (`behaviour.merge.sys.md`) that combines old + new into a deduplicated ruleset, then a `normalize_ruleset()` pass (`behaviour_adjustment.py:62-100`) strips triple-backticks, de-duplicates repeated headings/bullets case-insensitively, and normalizes line endings before writing. That's a real, thought-through guardrail against a naive "keep appending instructions until the prompt rots" failure mode.
2. Unguarded, structural: because the whole repo (including `prompts/`) is a plain read-write mount and the agent has a code-execution tool with real shell access, nothing stops the agent from editing its own `agent.system.*.md` files directly with `cat >`/a text editor, bypassing the merge/dedup guardrail entirely. The framework's only real defense here is doc convention ("do not edit promptinclude files for behavioral rules unless the user explicitly asks for a file change", `prompts/agent.system.tool.behaviour.md`) — a norm, not an enforced boundary.

**"Solutions" memory.** Genuinely clever and fully automatic: every monologue ends with a background utility-LLM pass that mines the just-finished conversation for problem/solution pairs and writes them to a dedicated vector area, with an "intelligent consolidation" step that searches for near-duplicates and merges rather than accumulates (`_51_memorize_solutions.py`, `memory_consolidation.py`). Retrieval is symmetric and automatic too — recalled every few iterations via a separate similarity search restricted to the `solutions` area (`_50_recall_memories.py:141-146`) and surfaced to the agent before it starts problem-solving. This is a real "recipe reuse" loop, not just a memory dump: it distinguishes durable facts/preferences (`MAIN`) from recipes-for-tasks (`SOLUTIONS`), and the solving prompt explicitly tells the agent to check solutions/skills before working from scratch.

**Scheduling / proactivity.** A first-class `scheduler` tool supports cron-style recurring tasks, one-off planned tasks, and ad-hoc tasks, each optionally running in a "dedicated context" (i.e. its own agent/session) (`prompts/agent.system.tool.scheduler.md`). The one explicit safety rule baked into the tool prompt — "do not create recursive task prompts that schedule more tasks" — shows the maintainers are aware of and defending against exactly the runaway-recursion risk that the subordinate-hierarchy mechanism leaves structurally open elsewhere.

## 4. bbx comparison and verdict on the hierarchy question

**Verdict: this is weak-to-neutral evidence for hierarchy, not strong evidence against the flat-agent conclusion.** Reading the actual mechanism rather than the marketing copy: the "hierarchy" is a single mutable superior/subordinate slot per agent, spawned by an ordinary blocking tool call, with communication reduced to "pass a string down, pass a string back up" — structurally this is closer to a *synchronous, single-purpose subagent call* (much like Claude Code's own Task/Agent tool, or bbx's own subagents) than to a persistent hierarchical organization with standing roles. It happens to be user-visible as "the superior agent" and "the subordinate agent" as distinct long-lived objects with their own histories, but nothing in the codebase demonstrates that this buys more than what a flat "delegate a bounded subtask, get a report back" call already gets a flat architecture — which is exactly bbx's own conclusion. The genuinely hierarchy-specific risk it exposes and only partially guards against (unbounded recursive depth, no code-level cap, only social-contract prompt language) is a cautionary data point *for* staying flat: even the one prominent framework that leans into hierarchy doesn't trust its own mechanism enough to bound it in code, and instead patches specific recursion dangers ad hoc (scheduler tasks) rather than solving the general problem. So: close reading confirms rather than softens the flat-agent skepticism — hierarchy-as-implemented here reduces to "flat agent with a blocking subagent-call tool," not a genuine multi-level organizational structure with independent standing agents.

**Same/different/steal, for the rest:**

- **Same as bbx's direction:** filesystem-as-database framing (prompts, skills, memory all live as readable/editable files, not opaque config); a documented distinction between durable memory and reusable procedure (their `solutions` vs `main`/`fragments` maps reasonably onto how bbx separates cards from... behavior-shaping context); skills as on-demand-loaded, pinnable procedures rather than always-on bloat, with an explicit warning to keep the pinned set short — same instinct as bbx's card-schema `instructions` budgeting.
- **Different, worth noting but not necessarily adopting:** (a) the entire framework directory is agent-writable with no boundary between "framework code" and "user/box data" — bbx's separation of box vs monorepo CLAUDE.md is a deliberate contrast to this; (b) prompt files are reloaded live with zero rebuild/review step, so a bad self-edit takes effect immediately, no review gate; (c) automatic background "memorize solutions after every turn" is a much more aggressive default than bbx's `memorize only when useful across future work` framing (`agent.system.main.solving.md:44`) — it's a real design bet that most builders would consider over-eager without the consolidation/dedup safety net, which is the part that makes it survivable.
- **Worth stealing:** (1) the merge-then-normalize pattern for `behaviour_adjustment` — if bbx ever lets an agent adjust its own standing instructions, doing it via an LLM merge + structural dedup pass rather than raw append/overwrite is a good concrete technique to prevent instruction-rot; (2) the per-file `.dox.md`/`AGENTS.md` convention pairing every source file with an ownership/contract/verification note is a genuinely interesting "context engineering" idea adjacent to bbx's own card-schema `instructions` and CLAUDE.md-placement questions — could be worth a closer look via `bbx-context` for whether a lighter version suits box-level code, if boxes ever hold substantial custom code rather than just cards.
