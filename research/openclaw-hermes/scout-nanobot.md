# nanobot (HKUDS) — Highlight Scout

Clone: github.com/HKUDS/nanobot, MIT, Python ≥3.11. Audience assumes deep prior study of OpenClaw, Hermes, and Letta — this doc leans on contrast rather than re-explaining shared concepts.

## 1. Identity / focus

- Self-description: "an open-source, ultra-lightweight personal AI agent you can truly own" — WebUI, chat channels, tools, memory, MCP, model routing, automation, deployment (`README.md:38`). HKUDS is the academic group behind LightRAG/RAG-Anything; nanobot is their product-shaped side project, not a paper artifact.
- **Not a minimal toy.** It ships on PyPI (`nanobot-ai`), has a bundled built React WebUI (`webui/`, built to `nanobot/web/dist/`), a Docker image, an OpenAI-compatible server (`nanobot serve`), 15 chat-channel integrations (`nanobot/channels/`: telegram, discord, slack, whatsapp, feishu, wecom, weixin, qq, dingtalk, matrix, signal, msteams, mochat, napcat, email), and near-daily dated changelog entries through the clone date (`README.md:59-71`). Maturity reads as "small core, large surrounding product," not "unfinished prototype."
- Self-measuring economy is baked into the repo: `core_agent_lines.sh` is a first-class script whose entire job is to print a line-count breakdown of "core runtime" vs "extra buckets" (`core_agent_lines.sh:1-89`). Running it: core runtime (agent/bus/config/cron/session top-level files only) = **11,485 lines**; everything else (tools, skills, api, cli, channels, utils) = **38,210 lines**. The project literally instruments its own "how big is the irreducible core" question — a rare, useful convention other harnesses don't bother with.
- Does it copy OpenClaw/Anthropic conventions? Yes in one clear spot: nanobot's `skills/*/SKILL.md` files use the same frontmatter shape as Claude/Agent-SDK skills (`name`, `description`, optional `metadata`) — e.g. `nanobot/skills/clawhub/SKILL.md:1-5` and `nanobot/skills/long-goal/SKILL.md:1-3`. Otherwise the architecture (bus + loop + runner, provider registry, channel plugins) reads as convergent design rather than direct imitation — it looks more like a generic "chatbot gateway" shape (also seen in countless smaller frameworks) than a copy of OpenClaw's specific abstractions.

## 2. Architecture in brief

- **Process model**: single Python asyncio process. `nanobot gateway` starts enabled channels + the WebSocket/WebUI channel + a workspace-scoped cron service + system jobs (Dream, heartbeat) + a health endpoint (`docs/architecture.md:88-96`). No worker pool, no separate scheduler process, no message broker — everything is in-process asyncio.
- **Bus**: `MessageBus` is two `asyncio.Queue`s, full stop — `inbound`/`outbound`, `publish_*`/`consume_*`, `qsize` properties, 44 lines total (`nanobot/bus/queue.py:1-44`). `InboundMessage`/`OutboundMessage` are plain dataclasses; session key defaults to `f"{channel}:{chat_id}"` unless overridden (`nanobot/bus/events.py:22-36`). This is the entire decoupling mechanism between channels and the agent core — no topics, no pub/sub fan-out, no persistence layer for in-flight messages.
- **Agent loop split** mirrors a common pattern: `AgentLoop` (`nanobot/agent/loop.py`, 1,935 lines) owns the channel-facing turn — session/workspace resolution, context construction, hooks, outbound publish. `AgentRunner` (`nanobot/agent/runner.py`, 1,461 lines) owns the model-facing loop — provider calls, streaming, tool execution, stop conditions (`docs/architecture.md:36-48`).
- **Channels**: 15 built-in integrations plus a plugin entry-point mechanism (`docs/channel-plugin-guide.md`), each translating to/from `InboundMessage`/`OutboundMessage` against a `BaseChannel` contract (`nanobot/channels/base.py`, `manager.py`).
- **Memory**: two-tier. Near-term = one JSONL file per session (`<workspace>/sessions/<key>.jsonl`), replayed each turn with careful boundary-preserving truncation (`retain_recent_legal_suffix` in `nanobot/session/manager.py:293-380` — keeps a "legal" suffix that doesn't start mid tool-call, extends back to the nearest user turn, computes drop counts by object identity to survive non-contiguous slices). Long-term = plain Markdown/JSONL files: `SOUL.md` (voice), `USER.md` (stable user facts), `memory/MEMORY.md` (project facts), `memory/history.jsonl` (append-only, cursor-based compression archive) (`docs/memory.md:14-20, 40-48`). A `GitStore` version-controls the durable files so Dream's edits are diffable/restorable (`docs/memory.md:130-145`).
- **Consolidation vs Dream**: `Consolidator` runs synchronously when context pressure hits, summarizing the oldest safe slice into `history.jsonl` (cursor-based, append-only, "machine consumption first") (`docs/memory.md:26-46`). `Dream` runs on a cron schedule (default `intervalH`, override via `cron` expr), reads new history + `SOUL.md`/`USER.md`/`MEMORY.md`, and makes "the smallest honest change" to the durable files in one pass — not a full rewrite (`docs/memory.md:50-60`, `nanobot/agent/memory.py`, 1,092 lines).
- **Tools**: discovered from `nanobot/agent/tools/` + plugin entry points — files, shell (sandboxed), web search/fetch (SSRF-checked), MCP, cron, image generation, runtime self-inspection, subagents (`docs/architecture.md:104-118`, `docs/concepts.md:100-112`). 8,826 lines under `tools/` per the self-measure script.
- **Scheduling**: `CronService` (`nanobot/cron/service.py`, 869 lines) is a hand-rolled asyncio poll loop over a JSON job store guarded by `filelock.FileLock`, using the `croniter` library for expression math (`nanobot/cron/service.py:3-63`) — no APScheduler, no Celery, no external scheduler dependency. Heartbeat (reads `<workspace>/HEARTBEAT.md`, only sends non-trivial results) and Dream are both just system-registered cron jobs, same mechanism as user reminders (`docs/concepts.md:139-155`).
- **Config**: single `~/.nanobot/config.json`, schema in `nanobot/config/schema.py` (638 lines), accepts camelCase or snake_case on read, always writes camelCase back (`docs/architecture.md:148-150`). Provider selection is a simple explicit → inferred → gateway-fallback cascade (`docs/architecture.md:56-65`).

## 3. Highlights

1. **The self-measurement habit itself.** `core_agent_lines.sh` treats "how big is the core" as a maintained, checked-in artifact rather than a one-off blog claim. For a project explicitly branded on minimalism, this is the one genuinely novel piece of process — worth stealing as a pattern (a `bin/loc-report` that segments CBX into "irreducible core" vs "elaboration" buckets, checked periodically), independent of whether nanobot's own bucket boundaries are the right ones.
2. **The bus is deliberately not a message queue product.** Two `asyncio.Queue`s with no persistence, no replay, no backpressure policy beyond `qsize()`. It works because nanobot is single-process and treats a dropped in-flight message on crash as acceptable (session JSONL + at-least-once channel semantics cover recovery). This is a clean demonstration that "message bus" doesn't have to mean infrastructure — for a single-process agent, a queue plus a dataclass is the whole contract.
3. **history.jsonl over HISTORY.md — a documented format regret-and-fix.** `docs/memory.md:82-88` explicitly narrates that free-text history was "pleasant... but too fragile as an operational substrate" and was replaced by cursor-based JSONL for stable incremental consumption, safer parsing, and cleaner migration. The two-tier split (structure in JSONL, meaning in Markdown) is a clean articulation of a distinction CBX also needs (raw event/log lane vs. curated knowledge lane) and gives useful vocabulary for why a single "memory file" tends to rot.
4. **No retrieval cleverness at all — notable by absence.** Despite HKUDS's LightRAG/RAG-Anything research pedigree, nanobot's own memory system has zero embeddings/vector search (confirmed by grep — the only `vector`/`embedding`/`rag` hits in the whole tree are in an unrelated image-generation doc and the `clawhub` skill, which describes a **third-party** npm CLI's vector search over a public skill registry, not anything nanobot itself runs, `nanobot/skills/clawhub/SKILL.md:11`). Long-term memory is `grep`/`jq`-able plain files, by explicit design ("You can still search it with familiar tools," `docs/memory.md:96-104`). Read as a strong, presumably deliberate signal: even a group whose research specialty is retrieval concluded that for personal-agent memory at this scale, curated Markdown + full-context replay beats RAG. Worth citing when justifying CBX's own preference for cards/legible files over embeddings.
5. **`long_task`/`complete_goal` as a near-zero-machinery goal marker.** The `long-goal` skill (`nanobot/skills/long-goal/SKILL.md:1-15`) is not a scheduler or project-management subsystem — it's two tool calls that write a `Goal (active): ...` line into session metadata, surfaced back into context as `[Runtime Context — metadata only]`. It explicitly discourages up-front planning ("do not spend a long thinking pass on project planning... before setting the marker") and requires idempotent goal wording so it survives compaction/retries. A useful minimal pattern for "sustained objective" tracking without inventing a plan-object schema.
6. **"Agent social network" needs no product code.** `docs/agent-social-network.md` "joins" nanobot to third-party agent communities (Moltbook, ClawdChat) purely by telling the user to send their bot a chat message like `Read https://moltbook.com/skill.md and follow the instructions to join` — i.e., the existing web-fetch tool plus a hosted instructions file *is* the integration. No bespoke connector, no new tool, no schema. It's the strongest example in the repo of "the general tool loop is the extension mechanism," and a good illustration of how far a narrow-waist tool set can be stretched by pointing it at an external instructions document.
7. **Skills adopt the Claude/Agent-SDK SKILL.md convention wholesale**, including a `metadata` bag for nanobot-specific bits like an emoji (`nanobot/skills/clawhub/SKILL.md:5`). Nothing deep, but confirms this frontmatter shape is becoming a de facto interchange format across unrelated harnesses — relevant if CBX ever wants its own skills to be portable/legible to other agent tooling.

## 4. CBX comparison

- **What's essential vs elaboration, per nanobot's own accounting**: agent loop + bus + config + cron + session = ~11.5k lines is "core"; tools/skills/api/cli/channels/utils = ~38k lines is "everything a real product needs on top." That ratio (roughly 1:3.3) is a useful sanity check for CBX's own core/box split — if CBX's card/schema/agent-loop core were audited the same way, a similar or smaller core-to-surface ratio would suggest the core is appropriately narrow; a much larger core-fraction would be a flag. Concretely worth stealing: **write a `core_agent_lines.sh`-equivalent for CBX** and check it periodically (or in cb-codehealth passes) rather than eyeballing "is the core still small."
- **Memory architecture is the single most CBX-relevant finding**: nanobot converged on the same shape CBX already uses — durable curated files (their `SOUL.md`/`USER.md`/`MEMORY.md` ≈ CBX's per-box `CLAUDE.md`/cards) plus an append-only raw-event lane (`history.jsonl` ≈ CBX's session/feedback logs), with a periodic reconciliation pass (`Dream`) that makes small, targeted edits rather than full rewrites. The `docs/memory.md:82-88` regret story (free-text → cursor-based JSONL) is worth reading before any CBX change to how feedback/history logs are structured, since it names the exact failure mode ("fragile as an operational substrate") CBX should watch for in its own logs.
- **The absence of RAG is the most load-bearing data point for CBX**, precisely because it comes from a group whose research specialty is retrieval (LightRAG). It's independent evidence — not from CBX's own priors — that plain legible files plus full-context/skill-driven search outperforms embeddings for this class of system at this scale. Useful ammunition next time embeddings-for-memory comes up.
- **The bus is a useful lower bound, not much more.** Two asyncio queues is a fine reminder that CBX shouldn't over-build its own inter-component messaging if it's single-process — but CBX already knows this; nanobot doesn't add new insight here beyond "yes, this minimal a bus really is sufficient in production."
- **Steal-worthy, concretely**: (1) the self-measuring LOC script as a recurring health check; (2) the `history.jsonl`-vs-Markdown naming/vocabulary ("structure" lane vs "meaning" lane) for talking about CBX's own log/card split; (3) the "no bespoke integration code, just an instructions file + existing tools" pattern (`agent-social-network.md`) as a template for how lightweight a new CBX integration *could* be before reaching for a real connector.
- **Honest weight**: architecturally this is thinner than OpenClaw/Hermes/Letta — no sub-agent orchestration depth, no compaction algorithm as elaborate as Hermes's, no sleep-time/multi-agent model like Letta. Its interest is almost entirely in the *economy* (self-measured core size, memory file split, zero-dependency cron) rather than in novel mechanisms. Most of its highlights are "confirms a simplification CBX already believes in" rather than "introduces a technique CBX lacks."
