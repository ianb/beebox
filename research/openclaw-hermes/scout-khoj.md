# Highlight-scout: Khoj

Clone: `/private/tmp/claude-501/.../scratchpad/khoj` (blob-limited — files >200KB missing). All paths below are relative to that clone's `src/khoj/` or `src/interface/`.

## 1. Identity / focus

Khoj bills itself as "Your AI second brain" (`README.md:15`) — a personal-knowledge chat assistant that layers retrieval over your notes/docs, with a hosted cloud tier (`app.khoj.dev`) and a self-hostable OSS core. It is **not** primarily an automation/agent-execution platform like CBX; its center of gravity is "chat with an LLM that also knows your files," with automations and multi-step research as secondary features bolted onto that chat loop. It's mature and commercially operated: Django `Subscription`/`PriceTier` billing, per-tier model gating, a company (Khoj AI) behind it, six client surfaces (web, Obsidian, Emacs, Desktop/Electron, Android, WhatsApp via Twilio), 800+ contributors implied by badges/CI. It reads as a well-funded, several-years-old product, not a research prototype.

## 2. Architecture in brief

**Server**: hybrid FastAPI + Django in one process. `main.py` calls `django.setup()` and runs migrations (`main.py:38-58`), then builds `app = FastAPI(...)` (`main.py:61-64`) and mounts the Django ASGI app as a sub-app at `/server` (`main.py:188`). FastAPI owns all `/api/*` routes, streaming chat, and Starlette-based auth (`requires(["authenticated"])` decorators throughout `routers/`); Django is used purely as ORM + migrations + admin. Routers: `api_chat.py` (70KB — the chat/streaming core), `api_content.py` (ingestion), `api_agents.py` (custom personas), `api_automation.py`, `research.py` (agentic loop), `api_memories.py`, `auth.py`, `notion.py`, `twilio.py` (WhatsApp OTP only, not a messaging channel — see below), `web_client.py`.

**Clients**: web app (Next.js, `src/interface/web/`), Obsidian plugin (`src/interface/obsidian/`), Emacs (`src/interface/emacs/khoj.el`, 1386 lines), Electron desktop (`src/interface/desktop/`), Android (TWA wrapper), and WhatsApp — but WhatsApp integration turns out to be thin: `routers/twilio.py` (36 lines total) only does OTP phone verification via Twilio Verify; there's no dedicated WhatsApp inbound-message router in this clone despite the README/docs claiming WhatsApp as a chat surface (`documentation/docs/clients/whatsapp.md` exists but the messaging webhook code wasn't found — possibly excluded by the blob-size limit, or handled server-side elsewhere not in this tree).

**Ingestion/indexing**: content-type parsers under `processor/content/{org_mode,markdown,plaintext,pdf,docx,images,github,notion}/`, mirrored in `Entry.EntryType` (`database/models/__init__.py:769-778`: IMAGE, PDF, PLAINTEXT, MARKDOWN, ORG, NOTION, GITHUB, CONVERSATION, DOCX). Retrieval is embeddings-based on pgvector: `Entry.embeddings = VectorField(dimensions=None)` (`database/models/__init__.py:787`). Default models: bi-encoder `thenlper/gte-small`, cross-encoder `mixedbread-ai/mxbai-rerank-xsmall-v1` (`database/models/__init__.py:544-583`), with `bi_encoder_confidence_threshold = 0.18` and an inference-endpoint indirection to swap in a remote/HF/OpenAI embedding server. Sync is **hash-based** server-side: `text_to_entries.py::hash_func` (line 36) MD5-hashes each parsed entry; `update_embeddings`/`mark_entries_for_update` (lines 142-325) diff current vs. existing hashes per file to find new/changed/deleted entries — true incremental reindex, not full-vault re-embedding each sync.

**Chat/research loop**: `research.py::research()` (line 476) runs a bounded agentic loop, `MAX_ITERATIONS = 5` by default (env-overridable, line 498). Each iteration: `apick_next_tool()` (an LLM call choosing the next tool) → `execute_tool()` dispatching to semantic doc search, online search (`processor/tools/online_search.py`), code execution (`processor/tools/run_code.py`), browser/computer control (`processor/operator/`), or **MCP client tools** (`processor/tools/mcp.py` — a full stdio/SSE MCP client, meaning a custom Khoj "Agent" persona can be wired to arbitrary external MCP servers). Mid-run cancellation/steering exists via an interrupt queue (`research.py:512-535`). LLM providers are pluggable: OpenAI, Anthropic, Google (`database/models/__init__.py:222-224`) — local/offline model support was explicitly removed (migration `0036_delete_offlinechatprocessorconversationconfig.py`), despite the README still advertising "local LLM."

## 3. Highlights (the clever/distinctive bits)

**Obsidian is genuinely two-way — not just a note-source.** This is the standout finding. When the plugin's `fileAccessMode` setting is `'write'` (`obsidian/src/settings.ts:42`), the LLM can emit `<khoj_edit>` SEARCH/REPLACE blocks that the plugin parses (`interact_with_files.ts:504`) and applies straight into the vault via `this.app.vault.modify(targetFile, processedEdit.newContent)` (`interact_with_files.ts:842`), with an in-chat confirm/cancel step and hotkeys `Ctrl+Shift+Enter` / `Ctrl+Shift+Backspace` to apply/roll back (`main.ts:115-137`, `chat_view.ts:2314,2336`). `createNote()` (`obsidian/src/utils.ts:257`) can also mint wholly new vault files. So Khoj chat can directly author/mutate notes in your vault, gated behind an explicit permission toggle.

**Sync is mtime-based on the client, hash-based on the server** — two different incrementality mechanisms stacked. The Obsidian plugin tracks `lastSync: Map<TFile, number>` (`settings.ts:35`) and only re-uploads files whose `mtime >= lastSync` (`utils.ts:124`), batching a `PATCH /api/content` multipart upload (10MB/50-item batches, `utils.ts:133-134`), with deleted-file tracking via empty-blob delete markers (`utils.ts:163-171`). The server then does its own content-hash diff on top (§2) — so a touched-but-unchanged file still gets skipped server-side even if the client re-uploads it. The Emacs client (`khoj.el:408-477`) does the identical multipart-upload dance by hand (no third-party HTTP lib), with org-mode-aware content typing and an idle-timer live-search (`khoj--incremental-search`, `khoj.el:1157`).

**Citations are real vault backlinks, not just quoted text.** `chat_view.ts:505-555` renders each reference as a clickable `span.reference-link` that calls `this.app.workspace.openLinkText(...)` (`chat_view.ts:520-533`) to jump straight to the cited note in the vault, with a collapsible excerpt. Web citations get a parallel but distinct rendering path that links external URLs instead (`chat_view.ts:424-502`).

**A genuine memory-write/learning loop**, separate from document retrieval. After each turn, `ai_update_memories()` (`routers/helpers.py:1038-1067`) calls `extract_facts_from_query()` — an LLM call against `prompts.extract_facts_from_query`, structured-output as `MemoryUpdates{create: [...], delete: [...]}` (`helpers.py:988-1035`) — which reads existing `UserMemory` rows and proposes new facts to add / stale ones to retract. Memories are embedded and stored per-user (optionally per-agent) in `UserMemory` (`database/adapters/__init__.py:2286-2374`), then pulled two ways every turn: `pull_memories()` — last 10 memories updated within a 7-day window (medium-term/recency) — and `search_memories()` — cosine-distance semantic search over all memories (long-term/relevance) (`api_chat.py:970-975`), de-duped and merged into context. This is a self-directed "what should I remember about this user" loop, distinct from and complementary to the note-corpus RAG.

**Automations are LLM-authored cron jobs that call themselves back.** `POST /api/automation` takes a natural-language description (`q`) plus a crontime; `schedule_query()` infers the actual query-to-run and a subject line (`api_automation.py:72`). The scheduled function `scheduled_chat()` (`routers/helpers.py:2525`) doesn't run chat logic in-process — it re-POSTs to the app's own `/api/chat` endpoint with a bearer token (`helpers.py:2574-2588`), reusing the exact same code path a live user turn would hit. Crash-safety: a `last_run_time` guard skips re-firing if the job ran within the last 6 hours (`helpers.py:2541-2547`), APScheduler jobs persist via `DjangoJobStore` with leader-election through `ProcessLock` so only one node executes in a multi-instance deployment (`main.py:154-182`), and `max_instances=2` lets a fresh run kill a stale-locked previous one (`helpers.py:2694`). Delivery is gated by an LLM relevance check `should_notify()` before emailing via Resend (`helpers.py:2613-2622`) — if no email provider is configured it just returns the text instead of silently dropping it.

**Prompt context budget is genuinely engineered**, not ad hoc: `generate_chatml_messages_with_context()` computes a per-model token budget (`model_to_prompt_size`, default 10000) and a `lookback_turns = max_prompt_size // 750` (`processor/conversation/utils.py:698-701`), then `truncate_messages()` drops oldest whole messages first — tool-call messages are dropped wholesale rather than partially truncated, since a truncated tool call reportedly confuses provider APIs (comment at `utils.py:893`) — and only tokenizer-truncates the last surviving message if it alone still exceeds budget (`utils.py:919-943`).

## 4. CBX comparison

**Notes-sync model — relevant but not superior to CBX's connector/card-ingest model.** Khoj's two-tier incrementality (client mtime-diff + server content-hash-diff) is a reasonable pattern for "external vault, pull periodically," but it's solving a problem CBX's git-as-database design doesn't have in the same form — cards already live in the box's own repo, so there's no separate "did the source change" question for box-native content. Where this *is* directly relevant: any future CBX connector that mirrors an external corpus (an actual Obsidian vault, a Notion workspace) would want exactly this shape — hash-diffed incremental entries keyed by source file, deletion tracking, batch upload — Khoj's `text_to_entries.py` is a decent reference implementation to steal the diffing logic from if we build such a connector.

**Obsidian write-back is the one mechanism CBX doesn't already beat.** CBX doesn't have an analogous "propose edits to an external, human-owned document store with a diff/confirm UI." If Obsidian integration is ever built for CBX (per the boxholder's flagged interest), the `<khoj_edit>` SEARCH/REPLACE-block-plus-confirm pattern (§3) is worth studying directly — it's a real solved instance of "let an agent edit a human's existing files safely," which is a different problem than "agent writes its own cards."

**Memory-write loop is worth a discount, not a steal.** Khoj's per-turn "extract facts, save/delete" loop is essentially a card system without the card mechanics — free-text blobs with an LLM garbage-collector deciding what's worth keeping, no schema, no versioning, no git history. CBX already does this better structurally: any fact worth remembering can be a typed card with real fields, and the box's git history *is* the audit/undo log for free — Khoj's implicit "delete old fact, create new fact" is what CBX gets from `git log` on a card. The one thing Khoj does that CBX doesn't natively is *automatic* extraction-and-write triggered on every chat turn without an explicit user action; CBX's card creation is usually more deliberate (agent decides to write a card as part of normal reasoning, not via a dedicated background "what did I learn" pass). Worth asking whether a periodic "what should be captured as a card" reactor pass is a gap — but the underlying storage model doesn't need to change.

**Automations: same shape, CBX's is more architecturally sound.** Khoj's cron-job-that-calls-its-own-chat-endpoint is functionally close to CBX's schedule→wakeup→reactor design, but Khoj's version is a thinner wrapper: an APScheduler job firing an HTTP POST back at itself, with ad hoc crash-guards (6-hour last-run check, `max_instances=2` lock-stealing) bolted on. CBX's schedule/wakeup/reactor loop over typed cards is a first-class primitive with the same conversation history and context a live turn would have, not a re-entrant self-call hack. Steal-worthy detail: the `should_notify()` LLM gate before delivery (skip notifying if the automation's result isn't actually noteworthy) — that's a clean, generally-applicable idea CBX's schedule delivery doesn't obviously have yet.

**Prompt-budget engineering is a legitimate steal candidate.** The "drop whole messages oldest-first, never partially truncate a tool call, only tokenizer-truncate the single surviving message that's still too big" policy (§3, last item) is a concrete, battle-tested truncation strategy. Worth comparing against whatever CBX currently does for context-window management in long-running box conversations.

**MCP-as-tool-source for custom agent personas** (`processor/tools/mcp.py`) is a small, clean idea: a user-defined "Agent" (Khoj's custom-persona construct) can point at an MCP server (stdio or SSE) and get its tools folded into the research loop's tool-picker. If CBX ever wants boxes to consume external MCP tool servers dynamically per-box (rather than only tools wired at the app level), this is a minimal reference implementation.

**Multi-user/billing is not relevant to CBX's model** (one box = one agent = one human) and isn't included as a steal candidate — noting only that Khoj's `Subscription`/`PriceTier` gating is a different product shape (multi-tenant SaaS) that CBX deliberately isn't.
