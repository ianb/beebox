# Deep dive: how Hermes Agent defines a plugin

*2026-10-09. Snapshot of [`NousResearch/hermes-agent`](https://github.com/NousResearch/hermes-agent) at commit `26610b0` (Oct 9 2026; latest release v0.21.6, Oct 8). Sources: shallow clone read with grep/sed (paths below are repo-relative), the docs tree under `website/docs/`, `plugin-catalog/`, and public GitHub issues/PRs via `gh`. Repo stats at snapshot: 252k stars, 48k open issues. Prior notes from 2026-07 are listed in §7 with what this note supersedes.*

## 0. One-paragraph answer

A Hermes plugin is a directory with a `plugin.yaml` manifest and a Python module exposing `register(ctx)`. `ctx` is a `PluginContext` facade (`hermes_cli/plugins.py:230`) with ~45 public methods; everything a plugin can do goes through it or through one of ~10 provider ABCs (memory, context engine, model provider, image/video gen, web search, browser, computer use, TTS/STT, secret source, terminal environment). Plugins run in-process with full agent privileges by default; an opt-in out-of-process host landed in Oct 2026. Distribution is git-clone-at-exact-SHA, with a human-merged YAML catalog in the main repo as the only name index (522 entries). Skills are a separate, data-only system with its own hub, trust tiers and agent-authoring loop; the two meet only where a plugin ships skills via `ctx.register_skill()`.

## 1. Packaging and manifest

- **Manifest** `plugin.yaml`, parsed by `hermes_cli/plugins_manifest.py:parse_manifest_file` into `PluginManifest` (line ~340). v1 fields: `name`, `version`, `description`, `author`, `requires_env` (simple or `{name, description, url, secret}`), `provides_tools`, `provides_hooks` (`hooks:` accepted as alias, #108371), `kind`, `requires_hermes` (SemVer floor, unmet = skipped before import), `capabilities`. v2 (additive, #64165): `manifest_version`, `api_version`, `requires_plugins` (advisory; orders load topologically), `python_dependencies`, `python_runtime: external`, `config_schema`, `license`, `homepage`, `tags`, `emits`/`listens`, `provides_locales`. Unknown fields are ignored with a warning (`website/docs/developer-guide/plugins/index.md` "Manifest v2 reference").
- **`provides_tools` does not gate anything** for user plugins; it feeds `hermes plugins validate`, catalog chips, and the dashboard auth hint (same doc, Step 2).
- **Kinds** (`_VALID_PLUGIN_KINDS`, `plugins_manifest.py:27`): `standalone` (default; opt-in via `plugins.enabled`), `backend` (pluggable backend for a core tool; bundled auto-load, user-installed gated), `exclusive` (one active provider, selected by `<category>.provider`; own discovery), `platform` (gateway adapter; bundled auto-load, user-installed gated), `model-provider` (lazy discovery in `providers/__init__.py`; `PluginManager` records but never imports it). Undeclared kind is sniffed from `__init__.py` source (`_detect_kind_from_source`). Unknown kind falls back to `standalone` with a warning.
- **Layout per kind** (`plugins/AGENTS.md` table): general at `plugins/<name>/`; category plugins one level deeper, keyed `image_gen/openai`, `platforms/telegram`; memory at `plugins/memory/<name>/__init__.py` subclassing `MemoryProvider` (`agent/memory_provider.py`) plus optional `cli.py` with `register_cli(subparser)`; model providers call `register_provider(ProviderProfile(...))` at import.
- **`register(ctx)`** is the single entry point. `PluginContext` public surface (grep of `hermes_cli/plugins.py`): `register_tool`, `register_hook`, `register_middleware`, `register_command` (slash), `register_cli_command`, `register_platform`, `register_platform_handler`, `register_telegram_handler`, `register_slack_action_handler`, `register_memory_provider`, `register_context_engine`, `register_approval_transport`, `register_auxiliary_task`, `register_dashboard_auth_provider`, `register_redaction_patterns`, `register_system_prompt_section`, `register_context_reference`, `register_source`, `register_locale`/`register_locale_dir`, `dispatch_tool`, `call_mcp`, `inject_message`/`inject_gateway_message`/`inject_tui_message`, `emit`/`subscribe` (inter-plugin event bus), `get_config`/`set_config`, `state`, `spawn_task`, `on_unload`, `has_capability`, `has_plugin`, `current_cron_execution`, `platform_actions`, `subagent_lifecycle`, `llm`, `plugin_id`, `profile_name`. Provider registrations for image/video/web-search/browser/TTS/STT/computer-use/terminal-environment are documented as `ctx.register_*_provider()` (`website/docs/user-guide/features/plugins.md` "What plugins can do").
- **pip entry points**: `[project.entry-points."hermes_agent.plugins"]`, plus a companion group `hermes_agent.plugin_capabilities` so capability declarations are readable without importing (dev guide "Declaring capabilities"). Memory providers use `hermes_agent.memory_providers`. Docs now steer managed installs to directory plugins so the package manager can admit dependencies transactionally ("Distribute via pip").
- **Portable Agent Plugins v1** (`plugin.json` + `skills/` + `mcp.json`, agent-plugins.org) load through a compatibility adapter: skills are read-only and namespaced `agent-plugin-<slug>-<hash>`, MCP servers are stdio/streamable-http only, and the format "does not define trust, permissions, provenance, or a sandbox" (dev guide "Portable Agent Plugins v1 packages").
- Reference plugins live out of tree in [`hermes-example-plugins`](https://github.com/NousResearch/hermes-example-plugins) (`plugins/AGENTS.md`).

## 2. What a plugin can add

- **Tools**: `ctx.register_tool(name, toolset, schema, handler)`; handler returns a JSON string; `override=True` needs the `tools.override` capability (`PluginToolOverrideError`, `plugins.py:78`).
- **Hooks** (observers, return ignored except two): `pre_tool_call` (may return block/approve directive), `post_tool_call`, `pre_llm_call` (may inject context), `post_llm_call`, `pre_api_request`/`post_api_request`/`api_request_error`, `pre_auxiliary_call`/`post_auxiliary_call`, `on_session_start`/`end`/`finalize`/`reset`, `gateway_platform_event`, `kanban_task_claimed`/`completed`/`blocked`, plus `transform_llm_output`, `transform_tool_result`, `transform_terminal_output`, `pre_gateway_dispatch`, `pre_approval_request`/`post_approval_response`, `subagent_start`/`stop` (hook reference in dev guide; catalog `provides_hooks` tallies). Callbacks are signature-inspected; `**kwargs` gets the full payload. Hot-path hooks have a 30 s timeout; a timed-out `pre_tool_call` fails closed (user guide, `hook_callback_timeout`).
- **Middleware** (changes what happens): `tool_request`, `llm_request`, `tool_execution`, `llm_execution` (`VALID_MIDDLEWARE`, `hermes_cli/middleware.py`); `next_call` single-use; a raising middleware is skipped.
- **Messaging platforms**: `ctx.register_platform(name, label, adapter_factory, check_fn, ...)`; 21 bundled adapters under `plugins/platforms/` (Discord, Telegram, Slack, Matrix, email, SMS, IRC, Feishu, WeCom, DingTalk, LINE, Teams, Google Chat, WhatsApp, ...). Platform plugins must not touch `os.environ`; config goes through `PlatformConfig.extra` (`plugins/AGENTS.md`).
- **Skills**: `ctx.register_skill(name, path)`, namespaced `plugin:skill`, loaded via `skill_view("plugin:skill")`; never collide with user skills (`skills.md` "Duplicate skill names").
- **CLI / slash / gateway / dashboard / desktop**: `register_cli_command` (argparse tree, no `main.py` change), `register_command` (`/name` in CLI and gateway), dashboard tabs via `plugin_api.py` ASGI, Desktop panes/pages/themes via `desktop/plugin.js` and `@hermes/plugin-sdk` (`website/docs/developer-guide/desktop-plugin-sdk.md`).
- **Providers**: model (`ProviderProfile`, 42 bundled under `plugins/model-providers/`), image gen (9 bundled), video gen (4), web search (14), browser (3), computer-use, TTS/STT (config-driven `type: command` recommended, Python optional), secret source, terminal environment, dashboard auth (`dashboard_auth/`, 5), cron provider (`cron_providers/chronos`).
- **Memory providers**: `MemoryProvider` ABC with `sync_turn`, `prefetch`, `shutdown`, optional `post_setup`; one active via `memory.provider`. In-tree set closed May 2026; honcho/mem0/supermemory/hindsight/openviking moved to the catalog and byterover/holographic/retaindb are scheduled for removal 2026-10-15 (`plugins/AGENTS.md`, `CONTRIBUTING.md`).
- **Scheduling**: no plugin cron API as such; `ctx.current_cron_execution` tells a plugin which cron run it is in, and cron providers are a separate ABC.
- **`ctx.llm`**: `complete()`, `complete_structured()`, async variants, task-routed auxiliary calls. Host owns credentials (plugin never sees keys); defaults to the user's active provider/model; any override raises `PluginLlmTrustError` until the operator grants `llm.*_override` (`website/docs/developer-guide/plugin-llm-access.md` "Trust gate").
- **MCP from plugins**: `ctx.call_mcp(server, tool, args)` is default-off with a per-plugin, per-server `mcp_allowlist`; no wildcards (user guide "Calling MCP servers from plugins").

## 3. Discovery and installation

- **Sources and precedence** (`hermes_cli/plugins_discovery.py:200-245`): bundled `<repo>/plugins/` → user `~/.hermes/plugins/` → project `./.hermes/plugins/` (only with `HERMES_ENABLE_PROJECT_PLUGINS=1`) → pip entry points → Nix (`services.hermes-agent.extraPlugins`). Later wins on key collision, but a user manifest claiming a bundled key from a differently named directory is rejected as an "impostor". Memory providers invert this (bundled-first) because selection is by name (`plugins/AGENTS.md` table). Model providers are last-writer-wins.
- **Three states**: `enabled`, `disabled` (always wins), `not enabled` (discovered, never opted in). Bundled general plugins ship `not enabled`, never auto-enable on upgrade (`built-in-plugins.md`). Bundled platforms, backends, memory/context/model providers bypass the allow-list; user-installed platforms and pip backends do not (user guide "What the allow-list does NOT gate").
- **Commands**: `hermes plugins [list|search|browse|info|install|update|remove|enable|disable|capabilities|check-updates|adopt|trust-update-url|validate|doctor|show|pack ...]`. `install` prompts `Enable? [y/N]` (default no); `--ref` must be a full 40-hex SHA; `update` refuses to move a pinned install; dependency consent is a separate step that `--enable` cannot bypass (user guide "Managing plugins").
- **Catalog** (`plugin-catalog/`, since 2026-07-22; README rules mirrored into the docs and kept identical by a test): one YAML per entry with `name`, `repo` (https only), `sha` (40-hex mandatory), `tier` (official|community), `category`, `requires_hermes`, `capabilities` block, cosmetic `version`/`image`/`screenshots`/`readme`. Human-merged PRs only, no self-serve. `removed.yaml` is a kill list refused at install, update, enable and load (one entry so far: `or-picker`, a fold-in, not a security pull). Delisting is distinct from removal: file deletion, installed copies keep working. Catalog state at snapshot: **522 entries, 10 official, 512 community**; categories tools 147, desktop 125, memory 57, models 42, automation 36, web 35, general 33, platform 29, voice 15. 368 of 522 declare no tools (desktop UI, hooks, providers). Top maintainers are individuals with 10-14 entries each; NousResearch has 10. More than 900 commits touched `plugin-catalog/` since 2026-09-01; 786 PRs carry `plugin-catalog` in the title, 595 merged, 100 closed unmerged.
- **Packs**: `hermes-pack.yaml` pins a set of plugins; "nothing new exists at runtime"; no `--yes`, no bulk consent, non-interactive sessions cannot install packs; `skills:` listed but not yet installed (user guide "Plugin packs").
- **Left-core migration** (`hermes_cli/left_core_migration.py`): when a feature leaves core for the catalog (Home Assistant, Spotify, memory providers), `hermes update` and agent start auto-install the catalog plugin once for homes that used it; a later `hermes plugins remove` sticks.
- **Skills distribution is separate**: Skills Hub (`hermes skills install|search|check|update|tap add`) with sources `official`, `skills-sh`, `well-known`, `url`, `github`, `clawhub`, `lobehub`, `browse-sh`; 58 bundled SKILL.md + 154 optional; skill bundles (`/<bundle>` loads several skills) (`skills.md`).
- **`hermes claw migrate`** imports OpenClaw settings/memories/skills/keys; OpenClaw plugins are archived to `archive/plugins-config.json` with a pointer to the hooks guide, not converted (`website/docs/guides/migrate-from-openclaw.md:174`). The migrator is itself an optional skill (`hermes_cli/claw.py:24`).

## 4. Trust and permissions

- **Stance** (`SECURITY.md` §2.5): "Plugins load into the agent process and run with full agent privileges: they can read the same credentials, call the same tools, register the same hooks, and import the same modules as anything shipped in-tree. The boundary for third-party plugins is operator review before install." A malicious plugin is not a Hermes vulnerability; bugs that hide what is being installed are.
- **"Trusted plugin"** is not a tier. Trust is (a) the enable allow-list, (b) per-plugin capability grants under `plugins.entries.<id>.granted_capabilities` with consent hash and timestamp, (c) `mcp_allowlist`, (d) catalog admission ("Cataloged ≠ audited"). Known capability ids: `tools.override`, `llm.provider_override`, `llm.model_override`, `llm.agent_id_override`, `llm.profile_override`, `llm.task_override`, `gateway.platform_actions` (`hermes_cli/plugin_capabilities.py`). Docs: "Capabilities are a consent and audit layer, not isolation ... a malicious plugin can ignore every gate here."
- **Install-time static scan** reuses the Skills Guard threat-pattern engine: safe / caution (confirm or `--force`) / dangerous (blocked, `--force` does not override); prose, tests and fixtures are down-weighted by rule (user guide "Install-time security scanning"). Catalog installs at the pinned SHA skip the caution prompt because CI already ran it (README rule 7).
- **Out-of-process host** (`plugins.isolation: host`, `hermes_cli/plugin_host*.py`, shipped v0.21.6): one child process per profile, framed JSON over a pipe, `RemotePluginContext`; `HOST_UNSUPPORTED_CTX_METHODS` lists what cannot cross (live gateway/adapter objects): platform adapters, approval transports, Telegram handlers, model providers with their own SDK client, streaming dashboard endpoints, monkeypatchers. At the time the doc was written 299 of 348 catalog entries ran in the host unchanged. The managed overlay (`/etc/hermes/config.yaml`) can pin it so profiles cannot opt out.
- **Desktop plugins** run in the renderer "with full app authority"; isolation is error isolation only; admission lint plus an import allowlist (`@hermes/plugin-sdk`, `react*`) are tripwires, not a boundary (`desktop-plugin-sdk.md` "Security model").
- **Gateway hooks** (`~/.hermes/hooks/<name>/HOOK.yaml`) are "trusted by placement" and not gated by `plugins.enabled` at all (user guide note).
- **Public CVEs touching this surface** (2026): CVE-2026-9369 dashboard plugin discovery under `HERMES_ENABLE_PROJECT_PLUGINS`; CVE-2026-10220 injection in plugin skill-serving; CVE-2026-9353 Skills Guard code injection; Sep 2026 RCE via malicious git repository in 0.18.2-0.21.0 ([tenable](https://www.tenable.com/cve/CVE-2026-9369), [vuln.today](https://vuln.today/tag/nousresearch)). No public record of a malicious catalog plugin; `removed.yaml` has no security entry.

## 5. Versioning and updates

- **Compat is a behaviour contract**, explicitly not a `PLUGIN_API_VERSION`: never remove/rename `PluginContext` methods; new params keyword-only with defaults; hook payloads additive keyword fields; unknown manifest fields ignored; new provider methods get defaults; local schema versions only for wire/persisted contracts. Deprecation needs a once-per-process warning, documented replacement, and ≥2 minor releases (dev guide "Native plugin compatibility contract"; `plugins/AGENTS.md`). Tests load frozen external plugins through real discovery and assert outcomes, never counts.
- **Internal imports are not API.** PR #102117 (Sep 2026) split internals into `<stem>_<topic>` modules; the compat layer was removed after 2026-09-14 and old paths now raise `ImportError`, shown as the plugin's load error (`plugins/AGENTS.md` "Internal import paths are not API").
- **Updates ship as SHA bumps**: catalog pin bump = new PR, re-reviewed; `hermes plugins update` re-pins; a re-pin that adds tools, hooks, deps, capabilities or a Desktop half shows the delta and asks y/N; new capabilities stay off until consented; non-TTY sessions complete the install but grant nothing. `plugins.auto_apply: true` opts tracked git plugins into unattended updates. Rule 3: a listed plugin must not self-update.
- `requires_hermes` floors in the catalog cluster on `>=0.21`..`>=0.21.5` (268 of 522 entries declare one); 18 entries carry `known_issues`, several saying "needs a Hermes build after 0.21.5" for a hook that just landed.

## 6. Skills vs plugins, and what the community builds

- **Skills are data; plugins are code.** A skill is `SKILL.md` + references, discovered from `project → ~/.hermes/skills → create_dir → external_dirs`, scanned at install by trust tier (`builtin`/`official`/`trusted`/`community`), and the only artifact the agent writes itself: `skill_manage` (`create`/`patch`/`delete`/`write_file`/`remove_file`) targets `~/.hermes/skills/`, with an advisory linter (`incident-log-shape`, `references-sprawl`, `oversized-body`) and an optional `skills.write_approval` gate (`skills.md` "Agent-Managed Skills"). Project skills need `hermes skills trust`. The curator never touches project/external/plugin skills. There is no agent-authored plugin path; `hermes-plugin-gen` and `hermes-toolsmith` exist as community catalog entries, not core.
- **The plugin/skill seam is one call**: `ctx.register_skill()`. Portable packages add read-only skills. Packs list skills but do not install them. Otherwise two hubs, two trust models, two update commands.
- **Volume**: 522 catalog plugins vs 212 in-tree skills plus an external hub of thousands. Catalog growth is the headline of every v0.21.x release ("dozens of new community plugins").
- **What the catalog is**: 125 desktop UI entries, 57 memory providers (the category CONTRIBUTING calls "the most common plugin type"), 42 model-provider shims, 29 platforms. Many entries are single-maintainer micro-plugins (`turn-bell`, `done-bell`, `live-time`, `nowstamp`, six `jev-*` routers from one author). No install or star counts anywhere (catalog JSON has none; the docs page's "Most starred" sort has no data).
- **Failure evidence**:
  - **Core overrides.** PR #130860 (2026-10-03) delisted 11 plugins that patched private tables, adapter methods and session stores (`browserpaw`, `clawchat`, `hermes-evolve`, `self-wake`, ...); rule 9 and the `no core override` admission check were added the same week. #109850 delisted the two `ctx.llm` reference plugins; #132340 delisted two whose repos were deleted; 15 delisting PRs total.
  - **Import-path break.** The Sep 2026 module split invalidated every plugin importing internals; the project chose a one-month shim then hard `ImportError`.
  - **Dependency seam.** Open bugs #132030 (plugin pip deps never reach `uv.lock`; the next launch undoes the install), #132242 (`exclude-newer` quarantine blocks a plugin's declared dep), #135508 (stale per-profile catalog cache, versions desync across profiles), #134408 (dashboard `plugin_api.py` imported without package context, every route 500s).
  - **Hook sprawl.** #64231 catalogues 14 one-off observer-hook PRs waiting on a taxonomy; #64182 ("Plugin Interface Expansion", 35 comments) is the maintainers' response: additive-only ground rules, observer-first, fail-closed gates, then manifest v2, event bus, capabilities, lifecycle ledger — most of which shipped Jul–Oct 2026.
  - **Maintainer stance.** CONTRIBUTING: no new in-tree memory providers (May 2026), no new third-party-product plugins (June 2026), "a hook with no concrete consumer is speculative infrastructure and is rejected" (`plugins/AGENTS.md`).

## 8. Dispositions for Bee Box

The question: should Bee Box have a plugin system, and is a plugin a bundle of existing pieces, a new kind of thing, or a distribution mechanism? Bee Box today: a box is a git repo + npm package importing `beebox/{cards,schema,view-widgets}`; extension pieces are box-local card schemas, box-authored `.tsx` views, tricks, procedures, connectors compiled into beebox, managed box skills, and templates with parked updates.

| # | Disposition | Hermes evidence → Bee Box specific |
|---|---|---|
| 1 | **Reject** a `register(ctx)`-style code plugin API (hooks, middleware, provider ABCs). | Hermes's plugin surface is ~45 `ctx` methods, ~25 hooks, 4 middleware kinds, 10 ABCs, and still 11 catalog plugins reached past it into private tables within three months of the catalog opening; the Sep import split broke the rest. The failure mode is the API itself: every seam a plugin wants and does not have becomes a monkeypatch. Bee Box's decision that connectors and CLI commands compile into beebox (`compare-skills-tools.md` §1.4) stands. If a box needs a new integration, that is a beebox change. |
| 2 | **Adopt** the distribution shape, not the runtime: a plugin is a pinned bundle of existing pieces, "nothing new exists at runtime". | Hermes packs (`hermes-pack.yaml`) and Portable Agent Plugins both work because they are declarative lists of things the host already knows how to load. For Bee Box, a "plugin" would be a directory of card schemas, `.tsx` views, tricks, procedures and skills with one manifest and an exact git SHA, installed by copying into the box repo. This reuses the template mechanism (templates with parked updates, `config/template-versions.json`) rather than inventing a loader. Answer to the open question: distribution mechanism over existing pieces; no new kind. |
| 3 | **Adopt** "the catalog is a directory of YAML in the main repo, human-merged, exact SHA, no second name index." | `plugin-catalog/` with 16 admission rules and a kill list scaled to 522 entries without a registry service. If Bee Box ever lists bundles, start as `bundles/<name>.yaml` in the monorepo with `repo`+`sha`, and a `removed.yaml`. Do not build a service. |
| 4 | **Adapt** capability declarations as a one-screen consent at install, scoped to what a bundle touches. | Hermes capabilities gate host API surfaces and are honest that they are "not a sandbox". A Bee Box bundle manifest should declare the card types it reads/writes, the connectors it expects, and whether it ships views (code) or only data, and the install step shows that once. This is disclosure for the boxholder, not security; the security boundary remains that box code is the boxholder's code. |
| 5 | **Adopt** the install-time static scan reuse: one threat-pattern engine for skills and bundles, prose down-weighted. | Hermes reuses Skills Guard for plugin trees. Bee Box has no scanner; if bundles from outside the boxholder's own repos ever install, scan `.tsx`/tricks/procedures with one rule set before copying. Until then, not needed: box pieces are authored by the boxholder or the box agent. |
| 6 | **Reject** per-kind precedence rules and multiple discovery sources. | Hermes has later-wins for general plugins, bundled-first for memory, last-writer-wins for model providers, an "impostor" rule, five sources, and a `HERMES_ENABLE_PROJECT_PLUGINS` flag that produced CVE-2026-9369. One source (the box repo) and one rule (the box's copy is the copy) is the Bee Box shape already. |
| 7 | **Later**: left-core migration pattern (feature moves out of core, homes that used it get the plugin auto-installed once). | Only relevant if Bee Box ever splits a connector out of beebox into a bundle. Record the pattern (`hermes_cli/left_core_migration.py`): a table of `(bundle, predicate "does this box use it")`, install once, removal sticks. |
| 8 | **Note the divergence**: Hermes agents author data (skills) and never code; Bee Box's box agent already authors code (`.tsx` views, tricks, schemas). | Hermes's self-improvement loop (`skill_manage`, curator, background review) writes only `~/.hermes/skills/`; there is no agent-authored plugin path. Bee Box crossed that line on purpose: box-authored views and tricks are the box agent's work, bounded by the public specifiers and the view-widgets rules (`beebox/docs/implemented-plans/card-view-widgets.md`). The transferable part is the boundary, not the prohibition: whatever a bundle ships must be the same kinds of artifact the box agent may author, so nothing in a bundle has powers the box's own code lacks. |
| 9 | **Reject** `ctx.llm`-style host-owned LLM facade for third-party code. | Only meaningful once third-party code runs in the box process, which disposition 1 rules out. Box views are React components rendered by beebox, not callers of the model. |

Net: Bee Box should not build a plugin system in Hermes's sense. If it builds anything under that name, it is a pinned, declarative bundle of the pieces a box already has, listed in a YAML directory in this repo, installed by copy, and disclosed at install. File as an issue when the extension-points discussion resumes.
