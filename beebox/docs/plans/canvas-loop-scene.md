# canvas-loop scene: a plan for planning the redesign

canvas-loop's `draw` paints immediately. This plan moves it to a different
model: `draw` describes a **scene**, a tree of plain data (shapes, text, groups
with effects, brushes, lights, interactive controls). Renderers turn the scene
into pixels: Skia headless (the deterministic reference the agent judges) and
WebGL2 in the browser. The change is large and touches everything, so this
document plans the planning: what to learn, which spikes produce real examples,
and the checkpoints where the boxholder checks the design before more is built.
It supersedes `beebox/docs/unimplemented-plans/canvas-loop-gpu-medium.md`, which covered one effect where the
whole approach needed to change.

**Issues addressed:** none filed. Searched `issues/` and `private-issues/` for
canvas-loop performance, WebGL, scene graph, display list: nothing open.
Related: `issues/closed/exploration/2026-07-13-canvas-tight-loop-agent-programming.md:90`
(*"No good headless WebGL2 exists — 2D only for the prototype."*), which is why
headless stays on Skia.

## Design

No design section: canvas-loop is a developer library. Box figure cards are the
one place a person meets it; existing figures (only in courseware) are
regenerated by the box's agent (Stage 5, subplan f), and nothing new is shown to a person by this plan itself.

## The principles every checkpoint judges against

From the boxholder (2026-11-14), in their words:

1. **Excellent agent DX.** "Testing, diffs, warnings, etc. Maybe things like
   the wash effect warning would still be there, in 'testing' mode (headless
   rendering)."
2. **Art that doesn't look like lazy digital art.**
3. **Programmatic composability and reusability.**
4. **Speed so animation is reasonable and works.** In the browser. Headless
   speed matters little: the boxholder, "it's probably trivial compared to agent
   speed."
5. **Familiar APIs that feel natural for an agent**, "API rhyming with well
   known APIs", tested the way the path form was (agents drawing with each
   candidate, `canvas-brushes.md` Track D).

Each checkpoint below names the evidence it needs under each principle.

## Decisions already made (2026-11-14)

- **Scene first.** `draw` produces a scene; rendering is the renderer's job.
  The boxholder: "this is right for doing a big change, it's a big shift but
  it's the right one".
- **No escape hatch is the goal.** The raw context `v.ctx` is used by 10
  source files in the gallery and examples, for four things: plain paths and
  text written before the API had them (`pelican-bicycle`, `fjord-tides`,
  `pell-anim`), skew transforms (`intra-lounge/screens-tea.ts`,
  `intra-lounge-drawn/light-tea.ts`), and per-pixel fields with
  `putImageData` (`intra-atrium`, `intra-lounge` ×3, `game-world-tiles`),
  which were mostly hand-built lighting. The scene needs a matrix transform, an
  image node built from pixel data, and lighting; then `v.ctx` can go.
- **Inputs keep working as they do now** (`v.control`, DOM inputs placed over
  the canvas; painted stand-ins headless).
- **Text stays drawn into the picture for now.** A selectable, accessible
  text layer is possible later and is NOT in scope.
- **Accessibility is not squeezed out of the scene.** The meaning of a figure
  ("learning to balance a chemical equation") is not in its shapes. An agent
  that understands the subject writes a different accessible form; the scene
  does not try to carry semantics.
- **The GPU is for flexibility and effects as well as speed.** The boxholder:
  "Performance is one … goal, but flexibility and effects and such are also a
  goal." WebGPU is in scope as a backend candidate beside WebGL2.
- **Visual reviews use Astra** (`codex gpt-6-astra`): the boxholder rates it
  good at visual judgement. Checkpoint exhibits get an Astra read before the
  boxholder's.
- **Headless fonts:** watch for wrapping differences between Skia and the
  browser; no design work until a spike shows a problem.

## Smallest fix and budget

The smallest fix for speed alone is already shipped (commit `2e0720f1a`: one
soft-dab image, hatching batched; browser 4 → 8.75 fps on the 16-walker sheet)
plus the Canvas2D texture-tile idea. It does not give lighting, scoped effects,
automatic caching, or memory release offscreen, which the boxholder wants.

The budget of this plan is planning work: research notes, an API draft, agent
probes, two spikes, and the subplans. Estimated:

| Stage | Output | Size |
|---|---|---|
| 0. Evidence and targets | profile, targets, inventory, coverage matrix draft, host boundaries, baselines, prior art | docs, baseline renders |
| 1. Vocabulary on paper | API draft, ~10 examples, compositing semantics, completed matrix | docs, example sketches |
| 2. Paper probe | 3–4 agents write sketches against a type stub | accounts, sketches |
| 3. Mechanism probes | 5 small runnable probes, parity criteria, backend choice | ~1,000 lines, throwaway |
| 4. Spike-through | vertical slice, host paths, sleep contract, dev-loop checklist, drawing round | ~2,500 lines, throwaway allowed |
| 5. Subplans | implementation plans, each reviewed | docs |

The implementation the subplans describe will be several **BIG CHANGE**s;
each subplan asks for its own approval.

## Stated preferences this plan trades against

- **canvas-loop's premise.** `canvas-loop/README.md:8`: *"A deterministic,
  browser-less, frame-stepped Canvas2D sandbox for agent programming."*
  Headless stays browser-less and byte-identical; "Canvas2D" in that sentence
  will change.
- **Browser and headless already differ.** `canvas-loop/BRUSHES.md:360-361`:
  *"The headless renderer (Skia) and a browser can differ"*. The boxholder:
  "Deterministic is more like it." Each runtime is deterministic; across
  runtimes they agree within a stated tolerance.
- **One way to do each thing** (`beebox/docs/engineering-principles.md` §8).
  Two renderers of one scene is the cost; one scene with one vocabulary is the
  gain (today an effect on one stroke, a cache and a sprite are three
  mechanisms).
- **Serializable-in-principle**, already a stated goal:
  `canvas-loop/src/core/paint.ts:2-4` and `beebox/docs/plans/canvas-brushes.md:63-65`
  (*"the primitives are declarative data, `ctx` calls are not"*). The styles
  plan deferred *"Pictures as values, or a recorded display list"*
  (`beebox/docs/implemented-plans/canvas-loop-styles.md:356`). This plan picks
  that up.
- **Backward compatibility.** Not preserved. The boxholder: existing box figure
  sketches "can be regenerated based on this, by the agents in the box. They
  only really exist in courseware." Migration is regeneration by the box's
  agent after the new API and its guidance ship (Stage 5, subplan f).

## What already exists

- **The painter** (`canvas-loop/src/core/painter/core.ts`, `engine.ts`): every
  feature the scene must express, as immediate calls: shapes, brush marks
  (`src/core/brush/render/`), groups with opacity, blend and CSS-filter effects,
  masks, clips (single and union), caches, sprites, paper grain, text, controls.
  It becomes the Skia renderer, reading a scene instead of being called.
- **Style as data** (`canvas-loop/TEA.md`, styles plan): styles, brushes,
  gestures and group options are already plain values. The scene reuses them.
- **The dev loop:** transcript, `--zoom`, `--timing`, `--outline`, `cli diff`,
  checkpoints, faint-mark warnings (`src/core/painter/faint.ts`), text
  warnings, `gallery:check` byte-identical runs (`src/headless/gallery.ts:142`).
  Principle 1 says all of these survive.
- **The gallery:** 39 exercises in `canvas-loop/src/gallery/` (drawings,
  animations, interactive toys, chemistry figures, the Intra rooms, the
  walkers). It is the test corpus for every stage.
- **The drawer experiment** (`beebox/docs/plans/canvas-brushes.md`, Track D):
  briefs, cycle recording, accounts. Stage 2 reuses it for API probes.
- **Browser runtime and mounting** (`src/browser/`): fixed-step
  `requestAnimationFrame` loop, `attachSketch` owning a 2D canvas
  (`src/browser/mount.ts:76`), visibility suspension. Offscreen sleep extends
  it.
- **beebox figures** use canvas-loop in the browser
  (`beebox/src/frontend/src/components/FigureView/FigureMount.tsx:80-81`) and
  headless (`beebox/src/cli/commands/figure/run-one.ts:8`); starters in
  `beebox/src/templates/builtins/starters.ts`.

## Prior art (external)

Surveyed in Stage 0; a decision depends on each, so each gets a written note.
Candidates, all **evaluated only** so far:
- **Elm `view : Model -> Html Msg`**, React elements, SwiftUI views: a view
  as a returned value, identity by key.
- **Skia `SkPicture`** (record, then replay), Flutter's layer tree and
  `RepaintBoundary` (automatic raster caching of subtrees).
- **PixiJS / Konva** scene graphs: what a familiar 2D scene API looks like,
  filters on containers.
- **CanvasKit** (Skia compiled to WebAssembly with a WebGL backend): the same
  engine headless and in the browser. Needs WebAssembly allowed by the box's
  content security policy (`beebox/src/lib/csp.ts:61`, `script-src 'self'`).
  **Human decision required** if Stage 0 favours it.
- **2D deferred lighting** (normal maps from shape outlines, 2D shadow
  casting), as in many 2D games; Bousseau et al. 2006 for watercolour; Praun
  et al. 2001 for hatching by tone.

## Ontology (draft; Stage 1 settles it)

- **Scene:** what one `draw` produces: an ordered tree of nodes, plain data.
- **Node kinds:** shape (path, fill, stroke, brush), text, image (from pixel
  data or a sprite), group (transform including matrix, opacity, blend, clip,
  mask, effects, lighting), light, control (as `v.control` today).
- **Key:** a node's identity across frames. Keyed subtrees replace `cache` and
  `sprite`; the renderer decides what to keep.
- **Effect:** a property of a group, applied to whatever the group contains:
  blur, glow, shadow, colour adjustment, wash, hatching. One stroke can be its
  own group.
- **Material and light:** material on shapes (how the surface catches light),
  lights in groups or the scene.
- **Renderer:** Skia (headless, reference) and WebGL2 (browser). Each is
  deterministic in its runtime.
- **Testing mode:** headless rendering with warnings on (faint marks, wash
  effect warnings, text overflow), as now.
- **Builder:** the `v.*` calls, kept or reshaped, adding nodes instead of
  painting. Stage 1 and 2 decide whether `draw` returns the scene or builds it
  through `v`.

## Tracks / scope

The tracks are planning stages. Each ends at a checkpoint where the boxholder
decides. Nothing after a checkpoint starts before its decision. All notes,
matrices and probe results go in `beebox/docs/plans/canvas-loop-scene/`.

### Stage 0: evidence and targets

- **Browser profile.** Chrome performance profiles of the walker sheet, an
  Intra room and a chemistry figure at pixel ratio 2: time in drawing calls,
  layer creation, compositing, filters, gradient dabs, read-backs.
- **Targets, written before any spike.** Frame budgets that count as "animation
  works" (principle 4): for example the walker sheet and a panning room at
  60 fps at pixel ratio 2 on the test machine, and a box page with six figures
  without dropped input. The boxholder confirms them.
- **API inventory.** Every View call and option, with use counts across the 39
  gallery exercises and the beebox starters; the 10 `v.ctx` files mapped to
  their replacements.
- **Coverage matrix, first draft.** One row per brush kind (ink, stamp
  presets, bristle, smear, wet), effect (blur, glow, shadow, colour
  adjustments), compositing operation (opacity, every blend, erase, mask,
  single and union clip, `at` versus `group` isolation), paper grain, text,
  image, cache, sprite, control, and the new items (light, material, wash,
  hatching). Columns: scene representation, Skia strategy, WebGL strategy,
  dependencies (for example smear reads the evolving backdrop,
  `canvas-loop/src/core/brush/render/smear.ts:114`), unresolved evidence.
- **Host boundaries.** How beebox mounts figures in the browser (runtime
  injection and activity wrapping,
  `beebox/src/frontend/src/components/FigureView/FigureMount.tsx:79`) and runs
  them headless (named exports, `beebox/src/cli/commands/figure/run-one.ts:62`);
  the production content security policy (`beebox/src/lib/csp.ts:53-61`:
  development allows `unsafe-eval`, production does not).
- **Baselines.** Renders of the gallery corpus with today's renderer, kept as
  the "before" for every later comparison, with texture crops and short
  animation sequences.
- **Prior art.** One paragraph per item in Prior art: what it does, what we'd
  borrow, what an agent would recognise.
- **Checkpoint 0:** the boxholder confirms the targets and reads the notes.
  Backend candidates are only shortlisted here.

### Stage 1: the scene vocabulary on paper

- **What:** an API draft written as the docs an agent would read, plus about
  ten example sketches against it covering the gallery's range (an inked
  character with a glow on one stroke, a lit panning room, a citizen
  component used three times, an interactive chemistry figure with controls, a
  particle animation, a wash on one layer).
- **It must specify:**
  - **Compositing semantics:** what isolates and what does not, the order of
    transform, clip, mask, opacity, effects and blend within a node, coordinate
    spaces, effect bounds, and which nodes depend on the backdrop. Today `at`
    transforms the parent surface while `group` isolates it, and union clips
    copy the backdrop so erase and blends keep their meaning
    (`canvas-loop/src/core/painter/core.ts:129,164`). Differences from today
    are allowed but written down; automatic caching must never change them.
  - **Identity, invalidation and sharing,** as three things: a key says which
    node this is across frames; invalidation says when its pixels are stale;
    sharing says when two instances use one picture (a citizen drawn three
    times).
  - **The measurement boundary:** `v.text` returns bounds, and `u.textWidth`
    and `u.textBounds` work in `init` and `update` (`canvas-loop/TEA.md:190`).
    A recorder must still answer these immediately.
  - **Warnings and errors in testing mode,** pointing at a node; unsupported
    combinations fail with a message, never silently.
  - **Non-drawing calls:** `v.cursor`, `v.log`, `v.snapshot` and the like
    (`canvas-loop/TEA.md:279`) are classified as scene data or as once-per-draw
    outputs, so cache hits and waking neither lose nor duplicate them.
- **The coverage matrix is completed:** every row has a representation and
  both strategies, or a named omission. **Human decision required** for each
  omission or replacement.
- **Checkpoint 1:** the boxholder reads the draft, examples and matrix;
  cross-model review. Judged on principles 1, 3 and 5.

### Stage 2: paper probe (provisional)

- **What:** three or four fresh agents (Opus and one Sol) get the draft docs
  and matched briefs and write sketches against a type-checked stub. Each
  writes an account. Without rendering, this tests discoverability and type
  use only; its findings are provisional until Stage 4's drawing round.
- **Checkpoint 2:** the draft changes where agents stumbled.

### Stage 3: mechanism probes

- **What:** small runnable probes of the mechanisms the matrix marks as
  hardest, each answering one question in both renderers:
  - antialiased path filling on the GPU (own tessellation) against CanvasKit,
    with CanvasKit loaded under the production policy;
  - a backdrop-dependent brush (smear) on the GPU;
  - union clip and gradient mask with erase inside;
  - brush dabs instanced on the GPU against Skia stamps, texture crops side
    by side;
  - scene construction, allocation and comparison cost per frame, measured
    apart from uploads and rendering (each timed on its own), on a mostly
    static animation, reordered children, and changing content under stable
    keys;
  - a lit scene (two lights, materials on shapes, 2D shadows) and the wash
    effect on one layer, in each backend candidate, since these bear most on
    principle 2.
- **Parity criteria, defined before the probes run:** same-runtime
  repeatability (byte-identical), cross-renderer appearance (a tolerance on
  identical scenes, judged on texture crops as well as numbers), and stability
  over time and across small edits. Brush seeds depend on device-space geometry
  today (`canvas-loop/src/core/brush/render/mark.ts:94`), so a change of pixel
  ratio or transform changes texture; the criteria say what is acceptable.
  **Human decision required** on acceptable artistic differences; GPU-exact
  pixels are not a requirement.
- **Checkpoint 3:** the backend is chosen (own GL or CanvasKit), provisionally:
  Checkpoint 4 confirms it after the spike and the host paths. A CSP change,
  if needed, is presented with its exact scope: **human decision required.**

### Stage 4: spike-through

- **What:** a thin vertical slice that produces working pictures end to end:
  the recorder and both renderers for one representative of each mechanism
  class in the matrix (plain shape, stamp brush, bristle, backdrop brush,
  group effect, mask and union clip, text with a label-sized hit target, image,
  light, wash); three ported examples (the walker sheet, a lit panning Intra
  room, a chemistry figure with controls).
- **Through beebox's real host paths:** one synthetic figure runs in the
  browser figure card and in the headless figure command, checking controls,
  activity reporting, scaling, teardown and errors.
- **Sleep contract:** what survives sleeping offscreen (model, params, frame,
  randomness, the scene) and what is released (GPU textures, cached rasters);
  how a static or paused figure redraws on waking (today `resume()` only
  restarts the loop, and unchanged models skip drawing,
  `canvas-loop/src/browser/runtime/engine.ts:138,266`). Tested with repeated
  sleep and wake on static, paused and animated figures; CPU memory, GPU
  memory and wake latency measured; lost context reported visibly.
- **Dev-loop checklist:** deliberately bad scenes, each with the expected
  output: faint marks, text overflow, a cache-hit case, outlines, timing,
  checkpoints, `cli diff` against the Stage 0 baselines. A tool that stops
  reporting shows up as a missing expected line.
- **Agent drawing round:** the drawer experiment against the running spike,
  with render cycles, matched briefs, accounts.
- **Checkpoint 4:** an exhibit with the three examples in both renderers next
  to the baselines, the numbers against the Stage 0 targets, the checklist
  results and the drawers' accounts. Judged on all five principles; principle
  2 by the boxholder's eye.

### Stage 5: subplans

- **What:** implementation plans, each through `bbx-plan` with cross-model
  review: (a) scene core and Skia renderer, gallery migrated; (b) WebGL2
  renderer; (c) brushes and effects on the GPU; (d) lighting; (e) caching and
  offscreen sleep; (f) box figures: the figure guidance and starters for box
  agents, the deployment order, and what an old figure sketch shows until the
  courseware agent regenerates it (a clear error on the card, not a blank).
- **Checkpoint 5:** the boxholder approves the order and each BIG CHANGE.

## Could this be simpler?

The simplest path is to stay immediate-mode: ship texture tiles, add
`cache(…, { every })`, and stop. It keeps one renderer and costs a few hundred
lines. It does not give the things the boxholder asked for in this
conversation: lighting that runs at animation speed (the hand-built lit rooms
used `putImageData` and ran at a few frames per second), effects on any part of
a picture through one mechanism, automatic caching with memory released
offscreen, and a GPU path for brushes. Each of those needs the renderer to know
what is in the frame, which immediate painting cannot tell it.

The planning process could also be simpler: skip the paper draft and the probe
and go straight to the spike. That risks building the spike on an API agents
find unnatural (principle 5); the path-form experiment showed that agents'
reactions change the design.

## Failure modes

These are failures of the planning process; the subplans list code failure
modes.

| What can fail | Caught by | Handling | Clear-or-silent? |
|---|---|---|---|
| A brush or effect has no plan in the new model | coverage matrix, complete at Checkpoint 1 | named omissions need a human decision | clear |
| The API reads well on paper and fails in real drawing | Stage 4 drawing round (Stage 2 is provisional) | draft revised before Stage 5 | clear |
| Scene building or comparison costs more than it saves | Stage 3 cost probe, against Stage 0 targets | design changes at Checkpoint 3 | clear |
| Caching changes compositing (isolation appears) | Stage 1 semantics; Stage 3 fixtures in both renderers | semantics written down | clear |
| Renderers drift apart; the agent judges a look the browser does not show | parity criteria set before Stage 3 | agreed tolerance | clear |
| Art gets cheaper-looking (principle 2) | Stage 0 baselines, Checkpoint 4 exhibit | boxholder decides | clear |
| A dev-loop tool silently stops reporting | Stage 4 checklist with expected output per bad scene | unsupported nodes fail explicitly | clear |
| A figure is blank after waking | Stage 4 sleep tests (static, paused, animated) | sleep contract | clear |
| A backend works in development and fails under the production CSP | Stage 3 probe under the production policy | CSP decision at Checkpoint 3 | clear |
| Old courseware figures stop rendering after the change | Stage 4 host-path figure; subplan (f) | clear error on the card until the box agent regenerates the figure | clear |
| Fonts wrap differently headless and in the browser | Stage 4 chemistry figure | noted; design only if it shows | clear |

## Agent-flow / user-flow edge cases

- **Agent reaches for raw context.** ADDRESSED: the draft has no escape;
  Stage 2 shows what agents reach for.
- **Agent misplaces an effect** (on the wrong group, or on everything).
  DEFERRED to Stage 1's warning design.
- **Agent measures text in `update`** (`u.textWidth`). ADDRESSED: Stage 1
  keeps measurement immediate.
- **Two ways to make texture** (brush vs wash effect). DEFERRED to Stage 1.
- **Existing sketches mid-migration.** DEFERRED to subplan (f).

## NOT in scope

- **Selectable, accessible text layer** over drawn text: possible later (the
  invisible-text-layer pattern), deferred by the boxholder.
- **Semantic accessibility in the scene:** the boxholder prefers agents
  writing a separate accessible form from the subject's meaning.
- **New input kinds:** inputs stay as they are.
- **Implementation beyond the Stage 4 spike:** Stage 5's subplans own it.

## Open design questions

Stage 1 answers these; leans recorded here.
- **Returned value or builder?** Lean: keep the `v.*` builder for familiarity
  (principle 5) and make it record; also allow `draw` to return composed
  subtrees from helper functions, for reuse (principle 3).
- **Keys:** explicit only, or automatic by position with explicit overrides
  (React's rule)? Lean: React's rule.
- **GPU path filling:** our own tessellation, or CanvasKit? Shortlisted at
  Checkpoint 0, decided at Checkpoint 3 from runnable probes under the
  production policy.

## What will hold this after it ships

For the planning: the notes, the draft, the probe accounts and the spike
exhibit are kept in `beebox/docs/plans/canvas-loop-scene/` and linked from the

## Implementation order

1. Stage 0: evidence, targets, inventory, coverage matrix draft, host
   boundaries, baselines, prior art. Checkpoint 0.
2. Stage 1: draft, examples, semantics, completed matrix; cross-model review.
   Checkpoint 1.
3. Stage 2: paper probe. Checkpoint 2.
4. Stage 3: mechanism probes with parity criteria set first. Checkpoint 3
   (backend, any CSP change).
5. Stage 4: spike-through, host paths, sleep contract, dev-loop checklist,
   drawing round. Checkpoint 4.
6. Stage 5: subplans, reviewed. Checkpoint 5, then implementation.

## Rollout shape

This plan ships nothing to `main` by itself: notes, docs and spike code stay on
the workstream branch until a subplan's work is approved and done. It is done
when Checkpoint 5 approves the subplans.
