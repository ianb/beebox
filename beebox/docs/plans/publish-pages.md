# Publish Pages — External Static Publishing via Cloudflare Workers

This plan adds publishing to beebox: a boxholder (or the box's agent, with the boxholder's explicit go-ahead) can take content the box already holds — markdown docs, agent-built views and visualizations — and put it at a public(ish) URL that other people can open. Publications are **static snapshots hosted externally on Cloudflare Workers**, a hard boundary: the box itself gains zero inbound public surface (boxes may sit behind Tailscale), and a published page can never call back into the box. The plan covers the bundle format, the snapshot renderers, the Cloudflare Worker that serves publications, per-publication access tiers (public / secret-URL / Google-account-gated), a "drop box" for inbound submissions that the box pulls on `bbx wakeup`, and the human-gated publish flow with a leak scan.

Several decisions were made with the boxholder before this plan and are treated as locked: snapshot-never-live semantics; one Cloudflare account per box/machine with `*.workers.dev` as the default hostname; Worker code versioned in this monorepo; the four access tiers with fail-closed semantics; the strict no-egress header set; pull-based submissions; and human-only flip-to-live. Where research contradicted a locked premise, the deviation is flagged inline (see the two **⚑ flagged deviations** in Prior art and Track A) rather than silently redesigned. Track D's auth mechanism also changed as a result of the security review (Worker-side Google OAuth → Cloudflare Access), so Track D reads as revised from the original premise.

## Stated preferences this plan trades against

- `beebox/docs/engineering-principles.md` — the principles this plan leans on:
  - **#1 Types are structure** — the access tier is a literal union (`"public" | "secret" | "accounts" | "any-account"`), the pub-id is a branded type, and the manifest is a discriminated shape where tier-specific fields (slug, allowlist, submit block) are representable only on the tiers that allow them. A manifest that can express "public tier with a submit block" is a bug the compiler should catch before the Worker ever has to.
  - **#2 Exhaustiveness** — the Worker's tier dispatch and the CLI's publish-state dispatch are closed-set switches with `assertNever`.
  - **#3 Validate at boundaries** — the manifest is parsed with `safeParse` in three places (CLI at draft time, Worker at serve time, box at submission-pull time); viewer submissions are the newest untrusted boundary and get schema + size validation twice (Worker and box).
  - **#4 Resilient AND never silent** — revocation, expiry, and upload failures must be loud; a publication that silently stays up after revocation is the worst failure this feature can have.
  - **#5 Failure paths in signatures** — publish/upload/revoke return discriminated Results because the CLI branches on *why* (network vs auth vs validation).
  - **#6 Right-sized defensiveness** — but note the Worker inverts the usual interior-trust rule: the Worker treats *its own store* (manifests in R2) as a boundary, because the anti-pattern this plan defends against (Val Town, Prior art) is exactly "the endpoint trusted a manifest that said something impossible."
  - **#8 One way to do each thing** — submissions land through the existing connector→inbox→intake pipeline, not a new ingestion path; account-tier sign-in is delegated to Cloudflare Access rather than hand-rolling a second OAuth/session scheme in the Worker (Track D).
  - **#10 Testability is architectural** — the Worker is a pure `fetch(request, env)` function tested under `@cloudflare/vitest-pool-workers`; the leak scan is a pure function over file contents; clock-dependent paths (expiry) take an injected now.
- `beebox/CLAUDE.md` — the tRPC-vs-raw-Fastify boundary (the preview route and pull endpoint follow it), "keep source generic, never hardcode personal names," and the validation contract.
- `beebox/code-style.md` — mechanical rules for all box-side TS and the Worker package.
- **Precedents (denser than docs):** the Telegram webhook (`src/webapp/routes/telegram.ts`) as the "external service with a shared secret" shape — including its known weakness (plain `!==` comparison, noted in What already exists) which this plan does *not* copy; the connectors `sync()` pattern as the pull shape; `bin/path-leak-check.ts` as the leak-scan spirit; the iOS companion plan (`docs/plans/ios-companion-app.md`) as the token/pairing and plan-structure precedent.
- **Boxholder priors:** bias toward strict / fail-closed in all things; consolidate over blast-radius fear; plan more, not less.

## Prior art (external)

Two groups: platform research (Cloudflare, searched during planning) and product-incident lessons (researched earlier; folded in with the design rule each one produced).

### Cloudflare platform research

- **⚑ FLAGGED DEVIATION FROM A PLANNING PREMISE — the design now uses Cloudflare Access for the account tiers (reverses the earlier "Worker OAuth over Access" call).** Confirmed fact: Access *can* protect `*.workers.dev` — no custom domain required (Cloudflare's own docs: enable Access on the workers.dev host and *"Validate the Access JWT in your Worker script using the audience (`aud`) tag"*). https://developers.cloudflare.com/workers/configuration/routing/workers-dev/ . Per the boxholder decision ("set up auth separately") and this plan's security review, the account tiers now run on **Cloudflare Access**, not hand-rolled Worker OAuth: Access owns the dangerous OAuth surface (IdP flow, CSRF `state`, ID-token verification, session) while the Worker keeps only the per-publication allowlist check. The one scoping constraint: Access protects a whole *hostname*, so account-gated pubs live on a dedicated Access-protected host/route while `public`/`secret` stay on the open host (Track D).
- **Versioned/preview deployment URLs are a leak surface.** Historical Worker versions can remain reachable at `<version>-<worker>.<subdomain>.workers.dev`; preview URLs *"default to matching your `workers_dev` setting unless explicitly configured."* Design consequence: publication **content never ships inside the Worker deployment** — it lives in R2 keyed by pub-id, so an old Worker version leaks only old *code*. Setup also explicitly disables preview URLs. https://developers.cloudflare.com/workers/configuration/routing/workers-dev/
- **Workers Static Assets are deploy-coupled — wrong tool for per-publication bundles.** Assets upload as part of a Worker *version*; every asset change is a deploy. Publications are data, the Worker is code (locked decision 3), so bundles go in **R2**, not Static Assets. https://developers.cloudflare.com/workers/static-assets/ , https://developers.cloudflare.com/changelog/post/2025-09-02-increased-static-asset-limits/
- **KV is eventually consistent (writes visible globally in up to ~60s); R2 is strongly consistent per object.** KV also caps values at 25 MiB and its free tier allows only 1,000 writes/day. R2: no practical object-size ceiling for this use, strong consistency, zero egress fees, 10 GB-month free. https://developers.cloudflare.com/kv/platform/limits/ , https://developers.cloudflare.com/workers/platform/storage-options/ , https://developers.cloudflare.com/r2/buckets/public-buckets/ — This drives the second flagged deviation (Track A): **manifests in R2, not KV**, because a KV-stored tombstone can keep serving a revoked publication for up to a minute.
- **Cloudflare edge caching defaults are dangerous for secret URLs and tombstones.** With no `Cache-Control`, Cloudflare caches `200` responses for up to 120 minutes and `404/410` for 3 minutes — a revoked secret URL could keep serving from cache. Design consequence: the Worker sets `Cache-Control: no-store` on **every** response (Track C). https://developers.cloudflare.com/cache/how-to/configure-cache-status-code/ , https://developers.cloudflare.com/workers/reference/how-the-cache-works/
- **workers.dev hostnames are enumerable, not secret.** The pattern `<worker-name>.<account-subdomain>.workers.dev` is predictable and public-by-default when enabled; Cloudflare recommends custom domains for production. Design consequence: secrecy lives **only** in the ≥128-bit pub-id path segment, never in the hostname. https://developers.cloudflare.com/workers/configuration/routing/workers-dev/
- **Provisioning is fully scriptable except minting the first API token.** Worker create/deploy, KV/D1/R2 creation, and secrets all work non-interactively with `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`; there is no `wrangler tokens create` (open request: https://github.com/cloudflare/workers-sdk/issues/13042 ), so `bbx pub setup` documents one dashboard step: create a scoped token (Workers Scripts: Edit, Workers R2 Storage: Edit). https://developers.cloudflare.com/workers/wrangler/migration/v1-to-v2/wrangler-legacy/authentication/ , https://developers.cloudflare.com/workers/ci-cd/builds/configuration/
- **Worker-side Google OAuth is an established pattern (retained only as the deferred alternative to Access).** Worked examples of the full code flow in a Worker: https://ryan-schachte.com/blog/oauth_cloudflare_workers/ , https://github.com/jazcarate/cloudflare-worker-google-oauth , https://community.cloudflare.com/t/use-cloudflare-worker-for-google-sign-in/324993 . The design does **not** use this (Track D runs on Cloudflare Access); it stays here as reference for the Open-questions Worker-hosted-OAuth alternative, which — if ever pursued — must use a separate Google OAuth client from the box's, with each Worker hostname's callback registered on it (Google allows no wildcard redirect URIs).
- **Rate limiting / anti-abuse.** WAF rate-limiting rules beyond simple IP rules need Business+; the in-Worker **rate limiting binding** is the programmatic option, and the free plan's 100,000 req/day ceiling is itself a backstop. Turnstile is Cloudflare's free CAPTCHA-alternative and works on Worker-served forms. https://developers.cloudflare.com/waf/rate-limiting-rules/ , https://developers.cloudflare.com/use-cases/solutions/protect-sensitive-forms-fraud-abuse/ , https://community.cloudflare.com/t/protect-worker-from-abuse-using-turnstile-captcha/877341
- **Limits sanity for the whole design.** Free plan: 100k requests/day, 3 MB gzipped script, 10 ms CPU/request; R2 free: 10 GB-month, 1M writes-class ops/mo, zero egress. A multi-MB image-bearing bundle fits R2 trivially and never touches the script-size cap because content is not bundled. https://developers.cloudflare.com/workers/platform/limits/ , https://developers.cloudflare.com/workers/platform/pricing/
- **Not found:** no prior art surfaced for "per-publication access tiers on one Worker with manifest-driven auth" as a packaged library — the closest shapes are the OAuth examples above plus hand-rolled manifest checks. This is built, not adopted.

### Product-incident lessons (each produces a design rule in this plan)

- **Claude artifacts** — separate origin + strict no-egress CSP + snapshot semantics is the gold standard; the residual hole is that any "trusted" egress endpoint becomes an exfiltration channel. → Rules: publications live on a foreign origin (workers.dev), CSP allows no external egress, and the **submit endpoint is recognized as the one deliberate egress channel** and constrained accordingly (schema-validated, rate-limited, absent entirely on `public` tier — Failure modes).
- **ChatGPT "discoverable chats," Aug 2025** — ~4,500 private chats indexed by Google; feature killed. → Rule: `X-Robots-Tag: noindex` on everything, always; discoverability is not a tier, and v1 has no opt-in to indexing at all.
- **Notion** — unpublish and share-settings were decoupled (pages stayed live after "unsharing"), and an ancillary API leaked contributor emails. → Rules: **revocation is one action** (tombstone the manifest; pages and submit die together), and the pub surface has **no side-channel APIs** — the Worker serves bundle bytes and the submit endpoint, nothing else (no listing, no metadata endpoint, no provenance exposure; the edge manifest is a minimal subset of the box manifest, Track A).
- **Val Town** — page visibility tier ≠ endpoint access control. → Rule: the submit endpoint re-checks the manifest independently of how the page was reached; a `public` manifest refuses submit even if publish-time validation was somehow bypassed (enforced twice, Track F).
- **Google Docs Referer leaks** — secret URLs leak via the `Referer` header of outbound links. → Rule: `Referrer-Policy: no-referrer` on every response.
- **Custom GPTs** — knowledge files are ~100% extractable. → Rule: nothing secret ever ships in a bundle; the leak scan (Track E) treats the bundle as fully public regardless of tier, because `secret` and `accounts` tiers only gate *who*, not *what happens after a viewer saves the page*.
- **OpenClaw mass-exposure + CVE-2026-25253** — exposing the control plane is catastrophic. → Rule: the publish surface is narrow, read-only (plus one write endpoint), separately authenticated, and **the box has no inbound surface at all** — the Worker cannot reach the box; the box pulls.

## Tracks / scope

Six tracks, ordered by implementation dependency. A (vocabulary) unblocks everything; B and C depend only on A and are independent of each other; D extends C; E wires A–D into the CLI and the human flow; F rides on C + E.

### Track A — Publication format: `box/publish/`, the manifest, and the pub-id

- **What.** The on-disk shape of a publication in the box, the manifest schema (box-side full form and edge-side subset), the pub-id and URL vocabulary, and the R2 key layout.
- **Why this needs to change.** Nothing exists; every other track consumes these shapes. Locking the vocabulary first is what lets B–F proceed without churn (principle #1: the types *are* the design here).
- **Direction.**
  - **Box layout:** `box/publish/<pub-id>/` containing `manifest.json` (full form) and `bundle/` (the rendered static tree, `index.html` at its root). Git-committed in the box repo → history, rollback, audit for free (locked decision 1). Drafts are the same layout with `status: "draft"` in the manifest; flipping live is a manifest edit + upload, so the diff *is* the audit trail.
  - **Pub-id:** branded `PubId`, 26 chars of lowercase base32 from 16 random bytes (`crypto.randomBytes`), ≥128-bit. For `secret` tier the pub-id **is** the capability token (locked decision 4). Public tier may additionally carry a human slug.
  - **URL shapes** (tier visible in the path, locked decision 4): `/p/<slug>/…` (public), `/s/<pub-id>/…` (secret), `/a/<pub-id>/…` (account-gated — both `accounts` and `any-account`; the manifest distinguishes allowlist vs any). The Worker fail-closes on prefix/tier mismatch: a request whose path prefix doesn't match the manifest's tier is a 404, so a mis-uploaded manifest can't accidentally widen access.
  - **Manifest (box-side full form),** zod-validated (principle #3), sketch:
    ```jsonc
    {
      "pubId": "…", "status": "draft" | "live" | "revoked",
      "tier": "public" | "secret" | "accounts" | "any-account",
      "slug": "build-journal",            // public tier only (schema-enforced)
      "allowedEmails": ["…"],             // accounts tier only; absent/empty = nobody
      "expiresAt": "2026-09-01T00:00:00Z" | null,   // orthogonal to tier
      "submit": { /* Track F block */ } | null,     // never on public (schema-enforced)
      "provenance": { "boxSlug": "…", "renderedAt": "…", "sourceRefs": ["…"], "renderer": "docs" | "view", "softwareVersion": "…" },
      "files": { "index.html": { "bytes": 1234, "sha256": "…" }, … }
    }
    ```
    Tier-specific fields are expressed as a zod discriminated union on `tier`, so "public + submit" and "secret + slug" are unrepresentable, not just rejected (principle #1).
  - **⚑ FLAGGED DEVIATION FROM LOCKED DECISION 2 — edge manifests live in R2, not a KV namespace.** The locked provisioning list named "KV namespace for manifests." Research (Prior art) found KV is eventually consistent with up to ~60s global propagation — meaning a revocation tombstone written to KV can keep a revoked publication (and its submit endpoint) alive for up to a minute, and there is no way to tighten that. R2 is strongly consistent per object, so a tombstone takes effect on the next read. Given "revocation is ONE action that kills pages and submit together" (locked decision 4) and the strict/fail-closed prior, the plan puts **everything in one R2 bucket**: `pubs/<pub-id>/manifest.json` (edge subset), `pubs/<pub-id>/bundle/<path>`, `submissions/<pub-id>/<ulid>.json`. One store, one consistency model, one binding (principle #8). KV is dropped from provisioning entirely; D1 too (submissions are R2 objects — rationale in Track F). If the boxholder prefers to honor the KV wording literally, the cost is stated here: ≤60s of post-revocation exposure.
  - **Edge manifest = minimal subset** (Notion lesson): tier, slug, allowedEmails (needed for gating), expiresAt, revokedAt, submit block, file map. **No provenance, no sourceRefs, no box identifiers** — nothing edge-side names cards or the box beyond what serving requires.
- **Vocabulary lock-ins:** `PubId` (branded), `box/publish/<pub-id>/`, `manifest.json` field names above, the `/p/ /s/ /a/` prefixes, the R2 key layout, command family name `bbx pub`.
- **First implementation chunk:** `src/publish/manifest.ts` — the zod schemas (full + edge subset + the `toEdgeManifest` projection), `PubId` generation, and a doctest exercising the discriminated-union rejections (public+submit, secret+slug, accounts with empty allowlist ⇒ nobody). No open questions inside it.

### Track B — Snapshot renderers (docs and views)

- **What.** `renderPublication(source, opts) → bundle/` for the two v1 source kinds: a markdown doc (Markdoc → standalone HTML) and a box view (compiled view module + inlined card data + static host page). Data is baked at render time; republish = explicit re-render (locked decision 1).
- **Why this needs to change.** There is no longer any page-snapshot path at all: `bbx render` was removed 2026-08-01 (see What already exists), and it was unusable as a publication anyway — stdout-only, expecting a live backend. Views are served live from `/api/views/:slug/module.js` + `/api/views/:slug/cards` (`src/webapp/routes/views.ts:41-42,71-72`); a snapshot must sever both wires.
- **Direction.**
  - **Docs renderer:** Markdoc render of a `.md` source into a single HTML file with inline CSS; images referenced by the doc are copied into `bundle/assets/` and rewritten to relative paths (data-URIs only for small images — the CSP allows both `'self'` and `data:` for images). No JS at all in doc bundles. This is the small, land-first renderer.
  - **View renderer:** reuse `compileView` (`src/webapp/views/compiler.ts:282`) targeting the browser, then emit a static host page that (a) inlines the card data the view depends on (the same payload `/api/views/:slug/cards` computes, via `getViewMeta().dependencies` + `loadViewCards`) as a `<script type="application/json">` block, (b) ships the compiled module and the runtime (React etc.) as files in `bundle/`, all same-origin, and (c) provides a publish-mode view host whose data hook reads the inlined JSON instead of fetching. The exact host shape, runtime bundling, and figure/p5 handling are the subplan (below).
  - Both renderers are pure box-side functions `(source, boxRoot, clock) → { files: Map<path, bytes> }` — no CF coupling, fully doctestable (principle #10).
- **Vocabulary lock-ins:** `renderer: "docs" | "view"` in provenance; `bundle/index.html` as the entry invariant.
- **First implementation chunk:** the docs renderer + doctest (render a fixture doc with an image; assert self-containment by scanning the output for any `http(s)://` reference — the same scan the leak-check reuses).

### Track C — `pub-worker/`: the serving core

- **What.** A new workspace package `beebox/pub-worker/` — the Cloudflare Worker: route parsing, manifest fetch + validation, tier dispatch for the unauthenticated tiers (public, secret), expiry/tombstone handling, and the header set on every response. Unit-tested under `@cloudflare/vitest-pool-workers` (the maintained successor to bare miniflare) with an R2 test binding.
- **Why this needs to change.** This is the external host — the whole feature (locked decision 1). Worker code lives in the monorepo, versioned and tested like everything else (locked decision 3).
- **Direction.**
  - `fetch(request, env)`: parse `/{p|s|a}/<key>/<asset-path>` → fetch `pubs/<id>/manifest.json` from R2 (slug resolution for `/p/` via a `slugs/<slug>` pointer object) → `safeParse` the edge manifest (an invalid manifest is a 404 + a Worker log line, never a serve — principle #3, and the Worker treats its own store as a boundary per the Stated-preferences note) → check status/expiry/tier-prefix → serve the asset from `pubs/<id>/bundle/<path>` with correct content-type. The Worker validates `<asset-path>` **before** building the R2 key — rejecting (404) any path that, after percent-decoding, contains a `..` segment, a leading `/`, or a reserved `__`-prefixed segment — and it never runs path normalization that could collapse `..` out of the `pubs/<id>/bundle/` prefix; R2 keys are flat, so the only way to escape the prefix is the Worker doing the normalization itself, which it must not.
  - **Fail-closed order:** tombstoned or expired → `410 Gone` (a deliberate, distinct signal per locked decision 4); unknown id, tier/prefix mismatch, bad manifest → `404`. Expiry uses the manifest's `expiresAt` against the Worker's clock; clock skew tolerance is zero (strict prior) — publish-time validation warns if `expiresAt` is within 24h.
  - **Headers on every response, no exceptions** (locked decision 5 + Prior art cache finding): `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Opener-Policy: same-origin`, and CSP `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'; connect-src 'none'` — no external egress of any kind (the anti-exfiltration boundary). Submissions are plain HTML form POSTs (`form-action 'self'`), so `connect-src` stays `'none'` even on submit-enabled pubs. `no-store` forgoes edge caching entirely; at personal scale (free tier: 100k req/day) that's the right trade — correctness of revocation over cache hits (strict prior; the Prior-art finding that Cloudflare would otherwise cache a secret URL's 200 for up to 2 hours).
  - The tier dispatch is an exhaustive switch over the manifest tier union with `assertNever` (principle #2); the account tiers' branch is "handled by Track D (Access-gated route)" — served on the dedicated Access-protected host — and Track C lands with those two arms returning 404 behind a build flag that gates the `/a/` handling until D lands; the flag's removal is D's first chunk.
- **Vocabulary lock-ins:** the package name `pub-worker`, the R2 binding name (`PUB_STORE`), the Worker's reserved path prefix `/__submit/` (Track F) — reserved now so no bundle path can collide (bundle paths are validated against `__`-prefixes at publish time). (Track D no longer reserves a Worker auth prefix — Cloudflare Access owns the sign-in flow.)
- **First implementation chunk:** the package skeleton + `fetch` for the secret tier only (manifest fetch, validation, 404/410, full header set) + vitest-pool-workers tests asserting every header on every response class (200, 404, 410), the tombstone taking effect on the next request after the manifest object is overwritten, and serve-time asset-path traversal (every form: `..`, `%2e%2e`, unicode, leading `/`). No open questions inside it.

### Track D — Account tiers via Cloudflare Access

- **What.** Google sign-in for `/a/` publications handled by **Cloudflare Access** (Zero Trust), not hand-rolled OAuth. Access terminates the Google IdP flow, issues and manages its own session, and forwards a signed identity assertion to the Worker; the Worker validates that assertion and enforces the *per-publication* allowlist.
- **Why this shape (boxholder decision: "set up auth separately", + the plan's own security review).** Hand-rolling OAuth in the Worker reintroduces the whole dangerous surface in a second, more-exposed runtime — `returnTo` open-redirect, CSRF `state`, ID-token `iss`/`aud`/`exp`/`email_verified` verification, and a shared session-signing secret. Worse, reusing the box's existing Google OAuth client would put its client-secret in two places and mint edge tokens carrying the box's own audience. Cloudflare Access does the IdP flow, session, and token verification as a maintained edge product; the Worker keeps only the trivial, non-cryptographic check (email ∈ this pub's allowlist). The pub surface's auth then shares nothing with the box's OAuth client.
- **Direction.**
  - **Access application.** `bbx pub setup` provisions one Cloudflare Access self-hosted application via the CF API, with an Access **policy of "any authenticated Google account"** and Google configured as the IdP (a one-time IdP setup in the CF Zero Trust dashboard — the single manual step, replacing the old Google-redirect-URI registration). Access mints and manages the visitor session cookie entirely; the Worker sets *no* auth cookie of its own.
  - **Host/route scoping — account tiers live behind Access, public/secret do not.** Access protects a *hostname*, and enabling it on a bare `*.workers.dev` host protects the whole host — which would wrongly force login on `public`/`secret` pubs. So account-gated pubs are served on a **dedicated Access-protected route**: a second `workers.dev` route (e.g. `<worker>-a.<sub>.workers.dev`) or — the recommended production form — a `/a/*` path on a **custom domain**, where Access path-scoping is fully supported. `public`/`secret` stay on the open host. The manifest tier dictates the URL, so `bbx pub go` places each pub on the correct host; a request for an `accounts`/`any-account` pub arriving on the open host 404s (fail-closed, mirroring the tier/prefix rule in Track A).
  - **Worker validation.** On every `/a/` request the Worker validates the Access JWT (the `Cf-Access-Jwt-Assertion` header) against the application `aud` and Cloudflare's Access JWKS (`https://<team>.cloudflareaccess.com/cdn-cgi/access/certs`), extracting the verified `email`. A missing or invalid assertion is a `401` — Access should have supplied it, so its absence means misconfiguration or a bypass attempt; never serve (fail-closed, principle #4). This is JWT *verification* against a published JWKS, not an OAuth flow — the only crypto the Worker does.
  - **Per-request authorization** (Val Town lesson — identity ≠ access): Access proves *who*; the Worker still checks the **current** manifest each request — `accounts` → email ∈ `allowedEmails` (absent/empty = nobody, mirroring `box-access.ts:28-30` fail-closed), `any-account` → any Access-verified email, logged. Changing a manifest's allowlist takes effect on the next request with no session machinery; revoking a *person* CF-side is an independent lever.
  - **Identity logging** for `any-account`: the Worker appends `{ ts, pubId, email }` to a bounded R2 log object per pub (`access-log/<pub-id>.jsonl`, rolled at a size cap); the box pulls it alongside submissions (Track F) so "who looked" lives in the box long-term.
  - **Provisioning.** `bbx pub setup` scripts the Access application + policy via the CF API and stores the Access team domain + application `aud` as Worker vars. No Google client secret ever touches the Worker or Cloudflare. (If a future boxholder wants Worker-hosted OAuth instead of Access — to avoid Zero Trust entirely — it MUST use a **separate** Google OAuth client from the box's, never the shared one; Open design questions, not v1.)
- **Vocabulary lock-ins:** the Access application `aud`, the account-tier host/route convention, the `access-log/<pub-id>.jsonl` layout. (No Worker-set auth cookie — Access owns the session.)
- **First implementation chunk:** the Worker's Access-JWT validation for `/a/` + the per-pub allowlist check, with vitest-pool-workers tests using a stubbed JWKS (injected keys — principle #10): valid assertion + allowlisted email passes; valid assertion + non-allowlisted 403s; empty allowlist 403s everyone; missing/expired/wrong-`aud` assertion 401s; `any-account` logs the email. The Access application provisioning lands in Track E's `bbx pub setup`.

### Track E — Provisioning, the `bbx pub` CLI, leak scan, and the human flip

- **What.** `bbx pub setup` (one-time CF provisioning + Worker deploy), `bbx pub draft <source>` (render + leak scan + manifest), a boxholder preview surface, `bbx pub go <pub-id>` (the human flip: upload + live), `bbx pub revoke`, `bbx pub ls`, `bbx pub status`, and Worker-version drift handling.
- **Why this needs to change.** Locked decisions 2 and 7: setup is one-time and as scripted as possible; after it, publications are data-only; the agent drafts, only the human flips.
- **Direction.**
  - **`bbx pub setup`:** interactive; walks the two irreducible manual steps (CF account exists; scoped API token created in the dashboard — Prior art: token minting isn't scriptable), then scripts the rest: create R2 bucket, deploy `pub-worker` with bindings + secrets, disable preview URLs, print the workers.dev hostname and the Google-redirect-URI instruction (Track D). Credentials (`CLOUDFLARE_API_TOKEN`, account id) are stored **machine-level outside the box repo**, same posture as Google OAuth creds (locked decision 2) — deliberately not in the box, so a bundle/leak-scan miss can never ship them and the box agent doesn't hold the publish keys as box content.
  - **`bbx pub draft <source> --tier <tier> [--expires …] [--emails …] [--slug …]`:** renders (Track B), writes `box/publish/<pub-id>/` with `status: "draft"`, runs the **leak scan**, prints the file-by-file preview listing (path, bytes, sha256) plus scan findings. Anyone — agent or human — may draft; drafting has no external effect.
  - **Leak scan (`src/publish/leak-scan.ts`):** pure function over bundle files; findings, not booleans. Patterns: the home-dir path regex from `bin/path-leak-check.ts:47` (documented copy, per the `bin/box-entry.ts` cross-package model); email addresses *other than* the pub's own allowlist and the owner; credential shapes (`AIza[0-9A-Za-z_-]{35}`, `sk-…`, `ghp_…`, `xox[bp]-…`, JWT triplets, 40+ char base64/hex runs); absolute `http(s)://` references (self-containment check — doubles as the CSP-will-block-this warning). Any finding blocks `bbx pub go` (fail-closed); an explicit per-finding `--accept-leak <id>` override exists because the scan *will* false-positive on legitimate content (e.g. a doc that quotes an email address), and the override is recorded in the manifest provenance. Draft commits to the box repo happen **after** the scan passes or findings are explicitly accepted, so a caught secret never enters box git history. The scan has real blind spots: it does not meaningfully cover (a) the **view renderer's inlined card JSON** — a large blob that is exactly what a human preview skims past — where PII/secrets won't match credential-prefix regexes, nor (b) **binary/image assets** (a screenshot of a key ships clean). For those two the **human file-by-file preview is the only real gate**; the scan is a backstop, not a guarantee (consistent with the Custom-GPTs "assume extractable" lesson).
  - **Preview:** a raw Fastify route inside the box auth wall (`server-box-scope.ts:59` preHandler applies) serving `box/publish/<pub-id>/bundle/` read-only at `/publish-preview/<pub-id>/…` — the boxholder eyeballs exactly the bytes that will ship, rendered in a browser, before flipping. (Raw Fastify not tRPC: static file serving, per the CLAUDE.md boundary.)
  - **`bbx pub go <pub-id>` — the human flip.** Requires an interactive TTY and re-displays the scan summary + tier/expiry/allowlist before a typed confirmation; then uploads in the safe order — bundle objects first, manifest last (a publication is unreachable-then-atomic, never half-served) — flips `status: "live"`, commits. **Honesty about the enforcement boundary:** this gate is procedural, not cryptographic. An agent with box shell access could in principle script around a TTY check; the real controls are (a) the CF token living outside the box at machine level, (b) the TTY-interactive confirm as the convention the agent is instructed to respect, and (c) the audit trail (git + `bbx pub ls`). This residual risk is accepted and documented (Failure modes) rather than papered over with a fake guarantee.
  - **`bbx pub revoke <pub-id>`:** ONE action — overwrite the edge manifest with a tombstone (`status: "revoked"`), which kills pages *and* submit together on the next request (R2 strong consistency, Track A ⚑); bundle objects are then deleted best-effort (the tombstone alone already fail-closes). Local manifest updated + committed. `bbx pub go` on a revoked pub mints a fresh pub-id (revoked secret URLs stay dead forever; ids are never reused).
  - **Worker-version drift:** `pub-worker` carries a build-stamped version; the deployed Worker reports it on `/__version` (unauthenticated, static string, no box info). `bbx pub status` and every `bbx pub go` compare against the packaged version and auto-redeploy the Worker when stale (Worker code is ours and data-compatible within a plan; a breaking manifest-schema change bumps a manifest `schemaVersion` and is called out in Rollout). This satisfies "updated on deploy of the box software" (locked decision 3) without giving the deploy host CF credentials.
- **Vocabulary lock-ins:** the `bbx pub` subcommand names above; `/publish-preview/` route; `--accept-leak`.
- **First implementation chunk:** `bbx pub draft` for docs sources + the leak scan + doctests (scan fixtures for each pattern class; the accepts-override path; draft-then-scan ordering). CF-independent, so it lands before setup.

### Track F — Submissions ("drop box") and the pull connector

- **What.** An optional `submit` block in the manifest (constrained form schema); the Worker's `/__submit/<pub-id>` endpoint (validate, rate-limit, store edge-side); a box connector that pulls submissions during `bbx wakeup`, lands them in `box/inbox/` as untrusted content, and deletes edge-side after landing.
- **Why this needs to change.** Locked decision 6. The box has no inbound surface, so the edge buffers and the box pulls — the existing connector pattern (`src/connectors/index.ts:33`).
- **Direction.**
  - **Submit block** (manifest, `secret`/`accounts`/`any-account` tiers only — the zod discriminated union makes it unrepresentable on `public`, and the Worker *additionally* refuses submit when the fetched manifest says `public`, the twice-enforced rule from locked decision 6 / Val Town): `{ fields: [{ name, kind: "text" | "textarea" | "email" | "choice", required, maxLength, choices? }], maxSubmissionBytes, maxPerDay }`. v1 is text-only — no file uploads (NOT in scope) — which keeps the size story trivial.
  - **Worker endpoint:** `POST /__submit/<pub-id>` accepting form-encoded bodies only; checks manifest status/expiry/tier (tombstone kills submit in the same read that kills pages); validates every field against the schema; enforces `maxSubmissionBytes` and the per-pub daily cap (count via bounded R2 list — cheap at personal scale, but **best-effort**: R2 LIST is eventually consistent, so a burst can momentarily slip past `maxPerDay`; acceptable at personal scale, with a per-pub counter object as the tightening option if abuse is seen); per-IP rate limit via the Workers rate-limiting binding, with the free plan's 100k req/day as the outer backstop (Prior art). Accepted submissions are written as `submissions/<pub-id>/<ulid>.json` = `{ ts, pubId, fields, viewer: email | null, ip: /* coarse: country only */ }` — viewer email attached only on account tiers (submission attribution, the one per-viewer datum v1 keeps). Response is a static thank-you page with the same full header set. Turnstile is deliberately deferred (Open questions) — the tiers already gate who can reach a form, and `public` never has one.
  - **Box connector** (`src/connectors/publish-submissions.ts`, implementing `Connector` per `src/connectors/index.ts:10`): on `bbx wakeup`, lists `submissions/`, downloads each, `safeParse`s (the edge is *also* untrusted from the box's perspective — principle #3), writes each as a card in `box/inbox/` (the directory intake owns — `intake.ts:128`) marked as untrusted external content for the intake pipeline (`runIntake`, `intake.ts:222`), then deletes the R2 object. **Land-then-delete order** makes the pipeline at-least-once; the ULID in the card filename makes re-pulls idempotent (dedupe by id) rather than duplicating. The connector authenticates to R2 with the machine-level CF credentials — R2 API directly, no Worker involvement, so no shared-secret channel to get wrong (and no repeat of the Telegram plain-`!==` weakness because there is no secret-comparison endpoint at all).
  - Also pulled: the `any-account` access logs (Track D), landed as a periodic digest card, same mechanics.
- **Vocabulary lock-ins:** the `submit` block field names; `submissions/<pub-id>/<ulid>.json`; the inbox card type for a submission (`*.pub-submission.card`, exact schema per `bbx-guide-schemas` conventions at implementation time — an additive net-new schema, no migration per the bbx-migration boundary).
- **First implementation chunk:** the Worker endpoint + tests (public-manifest refusal, tombstoned refusal, oversize refusal, schema violation refusal, daily-cap refusal — every refusal a distinct typed reason). The connector is the second chunk.

## Failure modes

> **Critical gap (accepted, documented):** the human-flip gate is procedural, not cryptographic — an agent with box shell access could script around the TTY confirm if it also obtained the machine-level CF token. Handling: the token lives outside the box; the flip re-verifies interactively; git + `bbx pub ls` audit everything. Not fixable without hardware/second-party signing, which is out of proportion for v1 (NOT in scope); the boxholder accepts this residual risk explicitly or the plan doesn't ship.

> **Accepted risk — submission→agent prompt injection (deferred, boxholder-acknowledged).** A `submit`-enabled pub is a low-friction channel for outside text to land in `box/inbox/`, where the box's LLM agent later reads and triages it with real tools. The plan *labels* the content untrusted (Track F) but does not yet *constrain what the agent may do with it*. This is a known, accepted limitation for v1; before the drop box is used for anything sensitive it needs separate handling (a human-released quarantine, or a tool-restricted processing path). Tracked in Open design questions.

> **Accepted risk — shared-origin content injection (deferred, boxholder-acknowledged).** All publications share one `workers.dev` origin, so a malicious or attacker-supplied bundle is same-origin with account-gated pubs. The strict CSP (`connect-src 'none'`) blocks the primary exfil path, but full isolation needs a per-publication origin, which only a custom domain (per-pub subdomains) provides. Known and accepted for v1; custom-domain-per-pub is the eventual fix. Tracked in Open design questions.

## Agent-flow / user-flow edge cases

- **Wrong tag / wrong field** — the agent drafts a pub with the wrong *tier* (e.g. `public` where `secret` was meant). **ADDRESSED**: drafting is inert; the flip re-displays tier + allowlist + expiry to the human, and tier is visible in the URL shape itself (`/p/` vs `/s/` vs `/a/`, Track A) so the mistake is legible at every later glance.
- **Stale ref** — the source card is edited or archived after render. **ADDRESSED by semantics**: snapshots never go stale *silently wrong* — they are declared point-in-time captures with `renderedAt` in provenance; republish is an explicit re-render (locked decision 1). The agent-facing convention "a publication does not follow its sources" gets a knowledge audit (below).
- **Two agents touching the same publication** — two sessions draft/flip the same pub-id concurrently. **ADDRESSED (cheaply)**: pub-ids are generated per draft (collisions cryptographically impossible), so concurrent *drafts* never collide; concurrent `go`/`revoke` on the same pub is last-writer-wins on one manifest object, and since both operations converge on a full-manifest overwrite the result is always one coherent state, with git history showing both actions. No lock needed (right-sized, principle #6).
- **Hand-edit drift** — boxholder hand-edits `box/publish/<id>/manifest.json` (bad tier string, malformed email). **ADDRESSED**: every consumer `safeParse`s (CLI at `go`, Worker at serve); the CLI refuses to upload an invalid manifest with a field-level error (principle #3 — config is untrusted content).
- **Fabricated free-form value** — the agent invents provenance (`sourceRefs` that don't exist) or writes a misleading slug. **PARTIALLY ADDRESSED**: `sourceRefs` are validated to exist at draft time (cheap check, Track E); slug wording is judgment and lands in front of the human at flip time. Honesty is made easy: provenance fields are machine-filled by the renderer, not agent-typed.
- **Validation error UX** — the agent hits a refusal (public+submit, missing OAuth config, leak finding). **ADDRESSED**: each refusal is a typed Result whose message names the field and the fix (`"tier 'public' cannot carry a submit block — use 'secret' or an account tier"`), designed to read well in an agent transcript (principle #4/#5).
- **Partial migration / transition state** — none exists: the feature is net-new and optional; boxes without `bbx pub setup` have zero behavior change. The only transition-shaped risk is Worker/manifest schema skew across upgrades, **ADDRESSED** via `schemaVersion` + drift auto-redeploy (Track E) — the Worker always upgrades before or with the first publish that needs the new schema.
- **(Eighth, feature-specific) A viewer treats a secret URL as shareable** — they forward it; that's what a capability URL *is*. **ADDRESSED as far as possible**: `Referrer-Policy: no-referrer` stops passive leakage (Google-Docs lesson), `noindex` stops crawlers, and the remaining exposure is inherent to the tier — the manifest's tier docs say so explicitly, and moving to `accounts` is the remedy the docs point at.

## NOT in scope

- **Live / server-rendered publications** (re-render per request from allowlisted cards) — locked out (decision 8); snapshots keep the box unreachable and the trust story analyzable. Revisit only as its own plan.
- **Search-engine discoverability** — `noindex` always, no opt-in tier in v1 (ChatGPT-incident lesson). A deliberate future act if ever.
- **Per-viewer persistence beyond submission attribution** — no comments, no per-viewer state, no analytics beyond the `any-account` access log (locked decision 8).
- **Multi-tenant hosted publishing service** — one CF account per box/machine; nothing shared (locked decision 8).
- **Custom-domain automation** — supported by hand (CF dashboard: attach a domain to the Worker) but not scripted in v1; workers.dev is the default (locked decision 2). Note that account tiers now run behind Cloudflare Access (Track D), and a **custom domain is the security-recommended configuration** for them (path-scoped Access + per-pub origin isolation) — so the workers.dev default is explicitly the lower-assurance option for account tiers.
- **File-upload submissions** — v1 submit is text-only; uploads reintroduce the whole malware/size/content-type surface for marginal v1 value.
- **Turnstile** — deferred until abuse is observed; the tier gates + rate limits + no-public-submit rule cover the v1 exposure (Open questions).
- **Cryptographic enforcement of the human flip** (hardware key, second-party approval) — out of proportion for v1; the residual risk is documented in Failure modes and accepted explicitly.
- **Web-UI publish button / review surface** — v1 ships the authed preview route + CLI flip; a frontend publish flow is a natural follow-up once the mechanics are proven (avoids coupling this plan to `bbx-frontend` work).
- **Agent auto-publish carve-out** (secret + short expiry without a human flip) — explicitly an open question (below), not v1 (locked decision 7).
- **Non-Google identity providers** — the box's auth is Google-only (`auth.ts:51`); the pub surface matches it.

## Open design questions

- **Agent auto-publish carve-out.** Should the agent ever flip `secret` + `expiresAt ≤ 72h` pubs live without a human, for "look at this draft" workflows? Lean: **no for v1**; revisit after real usage shows the friction — the carve-out is one policy check away if wanted, and adding it later is strictly easier than retracting it (fail-closed prior).
- **Usage/limit alerting.** The free tier's 100k req/day exhaustion is currently silent-to-the-box (Failure modes). Lean: fold a request-count probe into the pulled access-log digest (CF GraphQL analytics API) as a fast-follow, not v1.
- **Turnstile trigger.** What observed abuse level flips the deferred Turnstile decision? Lean: any daily-cap trip on two distinct days; wiring is contained to the submit form + endpoint.
- **Shared runtime asset for view bundles.** Per-publication React copies are simple but fat (~50KB gz each); a shared `runtime/<hash>/` R2 prefix would dedupe. Lean: per-publication in v1 (self-containment beats bytes at personal scale); the subplan holds the decision since it owns bundling.
- **Access-log retention edge-side.** How long do `any-account` logs live in R2 after being pulled? Lean: delete-after-pull, same as submissions — the box is the system of record (one pattern, principle #8).
- **Submission→agent injection containment.** How to constrain what the box agent may do with untrusted submission content once the drop box graduates past low-stakes use? Lean: a human-released quarantine or a tool-restricted processing path when that happens; accepted risk (Failure modes) until then.
- **Per-publication origin isolation.** Should each pub get its own origin (custom-domain per-pub subdomains) to isolate a malicious bundle from account-gated pubs? Lean: accept the shared `workers.dev` origin for v1 given `connect-src 'none'`; revisit with the custom-domain tier.
- **Worker-hosted OAuth as an Access alternative.** Should a future boxholder be able to avoid Zero Trust by hosting the OAuth flow in the Worker? Lean: only if avoiding Access is genuinely wanted, and it MUST use a **separate** Google OAuth client from the box's, never the shared one; deferred, not v1.

## Rollout shape

- **Test posture (tests as the design tool, per `docs/testing.md`):**
  - *Manifest doctest* — the discriminated-union rejections (public+submit unrepresentable, secret+slug, empty-allowlist-means-nobody) — Track A's done-when.
  - *Renderer doctests* — fixture doc → bundle; self-containment scan (no `http(s)://` refs) — Track B's done-when.
  - *Leak-scan doctests* — one fixture per pattern class + the accept-override path — Track E chunk 3's done-when.
  - *`pub-worker` vitest-pool-workers suite* — the Failure-modes table's Worker rows verbatim: full header set on every response class; tombstone-next-request; tier/prefix mismatch; invalid manifest; cookie tamper/expiry/allowlist-change; every submit refusal reason. This suite is the feature's contract and the Worker's done-when.
  - *CLI doctests with a stubbed CF API* — upload ordering, idempotent resume, credential-failure Results, drift redeploy.
  - *Connector doctest* — pull → inbox card → delete; crash-between idempotence.
  - One **manual end-to-end verification** against a real Cloudflare account at step 5 (and again at 6/7 for OAuth and submit) — recorded in the plan's completion notes; the platform's behavior (caching, consistency) is exactly what unit tests can't pin.
- **Knowledge audits:** the four entries above land with Track E and are executed before completion (see Knowledge audits).
- **Migration:** none — entirely net-new, optional surface. No existing data changes shape; boxes that never run `bbx pub setup` are untouched. The submission card schema is additive (new card type, no migration per the bbx-migration boundary). Future Worker/manifest schema changes ride the `schemaVersion` + drift-redeploy mechanism (Track E), designed in from v1 so the *first* breaking change isn't the one that invents the upgrade path.
- **Deploy wiring:** `pub-worker/` joins the workspace (lint/typecheck/test in the normal pre-commit dispatch); it is *not* added to `deploy.sh`'s rsync set (the box server doesn't run it) — Worker deployment happens only via `bbx pub setup`/drift-redeploy with per-box credentials.
