# iOS ↔ web overlap

`ios-app/` is a native SwiftUI companion app (Xcode project, deployment
target iOS 17, no third-party deps). It is NOT a separate product with its own backend — it's a
thin shell around the same web chat: `RootView` embeds a `WKWebView` loaded
against a paired box's normal chat URL, and native code adds pairing,
composer, speech, and capture on top. That means iOS calls the *same* HTTP
API and shares a bridge contract with the frontend, in Swift, duplicating
shapes that live in TypeScript on the web side. A web/backend change to one
of these surfaces can break iOS with no iOS-side commit at all.

**The canonical reference is `beebox/docs/mobile-contract.md`**
(§7 Contract Surface Index, §8 mirrored constants, §9 known open risks) — this
skill is the trigger to go read it, not a replacement. Its sync rule: any
commit touching a contract surface must update that doc in the same commit.
It lags reality in places (its index has no capture rows and still marks
bulk-upload's native side deferred, though both ship in Swift below) — when a
surface is missing there, the route/Swift files themselves are the contract;
update the doc while you're in it. `beebox/docs/mobile-parity.md`
tracks iOS-vs-Android feature parity.

## Concrete contact surfaces (web/backend ↔ iOS)

- **Chat upload/transcribe** — `beebox/src/webapp/routes/chat-uploads.ts`
  (`POST /api/chat/upload-file`), `chat-audio-routes.ts`
  (`POST /api/chat/transcribe-audio`), and `chat.ts`
  (`GET .../chat/default`) ↔ `ios-app/BeeBox/Services/ChatAPI.swift`.
- **Capture sessions** — `beebox/src/webapp/routes/capture.ts`
  (`/api/capture/sessions/...`) ↔ `ios-app/BeeBox/Services/CaptureAPI.swift`.
- **Bulk photo upload** — `beebox/src/webapp/routes/bulk-upload.ts`
  (`/api/bulk/sessions/...`) ↔ `ios-app/BeeBox/Services/BulkUploadAPI.swift`
  (explicitly documented in that file's header as reusing the same server
  contract as the web overlay, `src/frontend/src/lib/bulk-upload-api.ts`).
- **Pairing** — `beebox/src/webapp/routes/pairing.ts`:
  `POST /api/pairing/redeem` is called from Swift
  (`ios-app/BeeBox/Storage/PairedBoxStore.swift` +
  `Services/PairingURLInbox.swift`); `POST /api/pairing/session` is called by
  the *web layer inside the webview* (`src/frontend/src/lib/mobile-auth.ts`
  `refreshMobileSession()`), so it's still iOS-affecting — the webview breaks
  if it changes. Deep link shape (`beebox://pair?...`) is generated by
  `src/frontend/src/components/settings/CompanionPairingSection.tsx`.
- **Native bridge** — two directions, two files:
  `beebox/src/frontend/src/components/chat/native-post.ts` (web→native:
  the `NativeShellChannel` union and posting) and `native-emission.ts`
  (native→web: parsing what the shell injects) ↔
  `ios-app/BeeBox/Views/ChatWebView.swift` (native transport/coordinator).
  Shared JSON golden fixtures live in `beebox/test/mobile-contract/fixtures/`.
- **Auth-token carriage** — Bearer token on native HTTP calls vs. the web
  session's own auth; NOT unified (contract §2.3) — don't assume one covers
  the other.

## Rule of thumb

If your web/backend change touches an endpoint path, request/response JSON
shape, a `WKScriptMessageHandler` channel name, a URL-scheme/query param, or
token handling in any file above — check `mobile-contract.md`'s Contract
Surface Index for the matching row, update the Swift side (or file an issue if
you can't), and update the doc in the same commit. Purely internal
frontend-UI or backend-logic changes with no wire-shape impact don't need this.

## Known-fragile spots

Six open issues in `issues/bugs/` (`ios-*` slugs) track live gaps: pairing
double-redeem, plaintext token storage, HQ WAV format assumptions, missing
native-error observability, capture recorder silent stop, and a
new-tab/navigation dead end. Skim `issues/bugs/` for `ios-` before assuming a
surface is solid.

Working in `ios-app/` itself: read `ios-app/CLAUDE.md` first (build/test
commands, project-file editing rules, bridge discipline).
