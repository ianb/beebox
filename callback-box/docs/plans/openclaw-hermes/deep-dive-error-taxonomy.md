## 1. Hermes — `agent/error_classifier.py` (1,535 lines)

Hermes owns the model-call loop directly (it *is* the agent runtime talking to provider HTTP APIs), so its classifier sits right at the HTTP/exception boundary. It defines a `FailoverReason` enum with **22 members** (`agent/error_classifier.py:24-67`) and a priority-ordered pipeline, `classify_api_error()` (`agent/error_classifier.py:478-798`), producing a `ClassifiedError` dataclass (`:72-92`) with four independent recovery flags: `retryable`, `should_compress`, `should_rotate_credential`, `should_fallback`. Classification and recovery are consumed almost entirely in the retry loop in `agent/conversation_loop.py`.

**Pipeline priority order** (`agent/error_classifier.py:489-497,573-798`): (1) provider-specific pattern checks that must run before status-code logic (content-policy, thinking-signature, long-context-tier, oauth-beta, llama-grammar, xAI-entitlement) → (2) HTTP status + message-aware refinement (with 402/400 getting their own sub-dispatch) → (3) structured error-code from body → (4) message-pattern fallback when no status → (5) SSL/TLS transient-alert → `timeout` → (6) server-disconnect + large-session heuristic → `context_overflow` (or `timeout` if reasoning model) → (7) transport exception type/heuristic → `timeout` → (8) `unknown`.

Status/body/code extraction that underlies every category: `_extract_status_code` walks `.status_code`/`.status` up to 5 `__cause__`/`__context__` levels (`:1384-1400`); `_extract_error_body` walks `.body`/`.response.json()` (`:1403-1423`); `_extract_error_code` handles nested/OpenRouter-rewrapped JSON codes (`:1426-1473`,`525-549`).

### 1.2 Where classification results are surfaced

1. **Structured debug log** on every classification: `"Error classified: reason=%s status=%s retryable=%s compress=%s rotate=%s fallback=%s"` (`agent/conversation_loop.py:2476-2481`).
2. **Plugin/telemetry hook** — `agent._invoke_api_request_error_hook(error_type, error_message, status_code, retry_count, max_retries, retryable, reason=classified.reason.value)` (`:2482-2496`) — the external/telemetry surface.
3. **User-facing chat/TUI status lines**, e.g. "⚠️ API call failed (attempt N/M): {error_type} [HTTP {status}]" (`:2866-2897`), "⏱️ Rate limited. Waiting Xs..." (`:3971-3978`), "❌ Non-retryable client error…" (`:3639`), content-policy-specific guidance (`:3690-3706`), billing/entitlement guidance (`:3644-3651`).
4. **Turn-result dict**: `"failure_reason": classified.reason.value` surfaced on terminal max-retries-exhausted results (`:3931-3937`) — explicitly documented so a cron/kanban-worker caller can distinguish "quota wall" from "real task error" and pick a different exit code.
5. **`_summarize_api_error`** (`run_agent.py:2096-2164`) — human-readable one-liner for logs/cron-delivery; collapses Cloudflare/HTML challenge pages to `<title>`+Ray-ID to avoid leaking ~60KB of HTML (test: `tests/run_agent/test_nonretryable_error_html_summary.py`), redacts sensitive text.
6. **`logger.warning`/`logger.error`** operational logs throughout (`conversation_loop.py:2853-2860,2953-2958,3707`).
7. **Session-persistence gating** — classification decides whether to skip persisting a failed oversized session (`:3708-3720`).

### 1.3 Related-but-distinct Hermes classification systems

- **`agent/tool_result_classification.py`** (26 lines) — not an API-error taxonomy at all. `file_mutation_result_landed()` (`:12-26`) distinguishes a genuinely-failed file write/patch (top-level `"error"` key) from nested lint/LSP diagnostic noise inside an otherwise-successful result. Orthogonal to `FailoverReason`.
- **`gateway/platforms/base.py` `classify_send_error`** — a separate 7-value **outbound delivery** taxonomy for chat-platform sends: `too_long`, `bad_format`, `forbidden`, `not_found` (further split chat-level vs sub-chat-level, `:1917-1931`, feeding `gateway.dead_targets` blast-radius decisions), `rate_limited`, `transient`, `unknown` (conservative default, confirmed never masquerades as benign per `tests/gateway/test_send_error_classification.py:72-75`). Populated onto `SendResult.error_kind` (`:1882-1885`). Entirely independent of `FailoverReason` — classifies delivery-to-user failures, not inbound provider-API failures.
- **`cron/scripts/classify_items.py`** (226 lines) — **unrelated despite the name**: an LLM-based urgency/importance scorer for a "proactive monitor" cron pattern (scores inbox/feed items against user criteria so a cron job stays silent unless something is urgent, `:1-30`). No connection to error handling.

## 2. OpenClaw — FailoverReason, cron ladder, channel errors

OpenClaw does not necessarily own the raw model-call loop (it's positioned as an agent orchestrator with pluggable providers and, per its own docs, an SDK-adjacent design) — its taxonomy governs *auth-profile rotation* and *model/provider fallback* as two distinct stages, plus a wholly separate cron-retry ladder and per-channel (Telegram/WhatsApp/Slack/MS Teams) handling.

### 2.1 `FailoverReason` taxonomy

**Cross-cutting notes:**
- Overall order in `classifyFailoverSignal`: HTML/Cloudflare 5xx → message/detail classification (internally: image-size exclusions → session_expired → model_not_found → context_overflow → 402-text → billing → periodic-usage → rate_limit → overloaded → structured-server-error → transient-HTTP-code → auth/auth_permanent (OAuth-refresh short-circuit) → timeout-message → provider-specific patterns) → provider-plugin hook override → errorType fallback → error-code classification (`auth_permanent` short-circuits here too) → HTTP-status classification (can defer back to message classification for ambiguous statuses) → plain error-code → message/detail final fallback.
- **Non-provider local-coordination errors** (session write-lock contention, embedded-attempt takeover) are explicitly carved out — map to **no** `FailoverReason` (`null`), so the fallback loop **aborts** instead of rotating (`failover-error.ts:398-419`).
- **`LiveSessionModelSwitchError`** is a control-flow error, not a taxonomy member — handled separately so a stale persisted model doesn't create an outer retry loop; jumps directly to the already-selected later candidate.
- **`ProviderRuntimeFailureKind`** (`errors.ts:381-403`) — a **richer, partially-overlapping but genuinely distinct 20-value sibling enum** (`auth_scope, auth_refresh, refresh_timeout, refresh_contention, callback_timeout, callback_validation, auth_html, auth_invalid_token, upstream_html, proxy, rate_limit, dns, timeout, model_not_found, schema, sandbox_blocked, replay_invalid, empty_response, no_error_details, unclassified, unknown`) used purely to pick **user-facing chat copy** (`classifyProviderRuntimeFailureKind`, `errors.ts:1242-1343`, consumed by `formatAssistantErrorText`) — not for failover decisions. Several of its values (e.g. `auth_scope` vs `auth_refresh` vs `auth_html`) collapse to the single `FailoverReason.auth`.

### 2.2 Cron transient-error classification and retry ladder

**Ladder, exact values**: `DEFAULT_ERROR_BACKOFF_SCHEDULE_MS = [30_000, 60_000, 5*60_000, 15*60_000, 60*60_000]` — **30s → 60s → 5m → 15m → 60m**, defined once at `src/cron/service/jobs.ts:47-53`. Confirms the docs (`docs/cli/cron.md:142`, `docs/automation/cron-jobs.md:522-526`).

Two ladders are actually in play:
- **Recurring jobs' backoff floor** uses the full 5-step ladder (`jobs.ts:201,629-631,741`, `timer.ts:934`) via `errorBackoffMs(consecutiveErrors, scheduleMs)` (`jobs.ts:70-76`), which plateaus at 60m once `consecutiveErrors` exceeds the array length (not unbounded exponential growth).
- **The "should we retry at all" decision** (`resolveTransientCronRetryDecision`/one-shot jobs) defaults `backoffMs` to only the **first 3 entries** — `[30_000,60_000,300_000]` — paired with `DEFAULT_MAX_TRANSIENT_RETRIES = 3` (`timer.ts:423-424,467-478`), matching the type doc comment at `src/config/types.cron.ts:8-11`. Both are overridable via `cronConfig.retry.{maxAttempts,backoffMs,retryOn}`.

**Give-up behavior — three independent mechanisms:**
1. **One-shot jobs**: `consecutiveErrors > maxAttempts` (default 3) → `retryable:false`; `timer.ts:834-874` sets `job.enabled=false; nextRunAtMs=undefined` — kept in the store "to preserve the error state for inspection", **no direct user notification** from this path.
2. **Recurring jobs**: never auto-disabled for exhausting transient retries — they keep running on schedule, delayed by backoff, forever; only `consecutiveErrors` climbs (reset to 0 on next success, `timer.ts:788`).
3. **Schedule-computation errors** (a cron expression that throws, bad timezone) — separate counter, `MAX_SCHEDULE_ERRORS=3` (`jobs.ts:488`); at threshold, `job.enabled=false` **and** explicitly notifies the user via `enqueueSystemEvent` + wakes the agent via `requestHeartbeat` (`jobs.ts:504-524`, fix for issue #28861, "notify the user so the auto-disable is not silent").
4. **Failure alerts** (orthogonal to retry/disable) — `src/cron/service/failure-alerts.ts`: default `after:2` consecutive errors, `cooldownMs: 1h` (lines 8-9); fires via `sendCronFailureAlert` or `enqueueSystemEvent`, and — notably — recomputes `resolveFailoverReasonFromError()` (the same Part-A function) just to embed a human "Cause: <reason>" line, independent of whether that reason drove the retry decision.

**Transient vs. permanent classification** — `src/cron/retry-hint.ts`, two layers:
1. If a structured `FailoverReason` (persisted as `job.state.lastErrorReason`, set at `timer.ts:724-727`) is present and is one of the 5 allowed `CronRetryOn` keys, it wins outright ("structured provider classifications win over brittle message regexes").
2. Regex fallback, `TRANSIENT_PATTERNS` (`retry-hint.ts:21-30`), exactly 5 keys: `rate_limit` (rate limit/429/cloudflare/tokens per day), `overloaded` (529/overloaded/high demand/capacity exceeded), `network` (network/socket/econnreset/econnrefused/eai_again — **cron-only category, no FailoverReason counterpart**, since cron runs include non-LLM isolated-agent process/transport failures), `timeout` (timeout/timed out/"stalled before execution start" — the literal watchdog-timeout string from `execution-errors.ts:33-39`), `server_error` (deliberately hedged pattern requiring HTTP/status context, to avoid false-positives from stray numbers like "context limit 512 exceeded").

Everything else → **permanent** (`retry-hint.ts:52`). Consequence: `FailoverReason` values with no `CronRetryOn` equivalent — **`auth`, `auth_permanent`, `billing`, `context_overflow`, `model_not_found`, `format`, `session_expired`, `empty_response`, `no_error_details`, `unclassified`, `unknown`** — never satisfy the intersection check and also don't match cron's own regex set, so they are **always permanent for cron purposes** — e.g. a billing failure inside a cron job's agent turn disables a one-shot job immediately even though Part-A's own taxonomy has a richer, arguably-retryable-on-a-delay category for it.

**Two-tier relationship to the FailoverReason taxonomy**: Tier 1 (within one run attempt) uses `FailoverReason` to drive model/provider fallback *inside* the run (`src/cron/isolated-agent/run-fallback-policy.ts`). Tier 2 (across run attempts) is cron's own, narrower, more conservative `CronRetryOn` taxonomy that *prefers* the Tier-1 reason when compatible but otherwise falls back to independent regex — and is strictly more conservative (fewer retryable buckets) than Tier 1.

### 2.3 Channel-level error handling

OpenClaw's messaging-channel extensions each have their **own, independently-implemented** taxonomies — none of them reuse `FailoverReason` values directly (billing detection is the one confirmed exception, sharing the exact same pattern function).

- **Telegram `error-policy.ts`**: not a failure classifier — a **display-suppression policy** (`"always"|"once"|"silent"`, per account/group/topic, 4h default cooldown, `error-policy.ts:14,23`) deciding whether to show an already-classified error to the chat user, dedup'd per exact message text.
- **Telegram `send-error-predicates.ts`**: narrow Telegram-formatting predicates (rich-entity-invalid, HTML-parse-error) driving a plain-text-resend fallback, unrelated to transport/retry.
- **Telegram `network-errors.ts`** (richest channel taxonomy): its own transport/API classification — `RECOVERABLE_ERROR_CODES` (ECONNRESET, ETIMEDOUT, etc., `:13-31`) vs. the safety-critical subset `PRE_CONNECT_ERROR_CODES` (`:43-50`) that's the *only* set safe to retry for non-idempotent sends (guaranteed to fire before the request reached Telegram, so retry can't double-post) — a distinction Hermes/OpenClaw's other taxonomies don't make. Plus HTTP-status predicates (`error_code>=500`→server error, `429`→rate limit honoring `retry_after`), and message-edit-specific permanent-failure predicates ("message not modified", "no text", "edit target missing") that are non-retryable by definition. `allowMessageMatch` is deliberately **disabled for sends** (to avoid duplicate-message risk) but enabled for polling.
- **WhatsApp `session-errors.ts`** and **Slack `errors.ts`**: pure diagnostic-string formatters (Boom-wrapped codes for WhatsApp/Baileys; Slack API `data.error/needed/provided`/`response_metadata`), no retry/permanent buckets at all.
- **MS Teams `errors.ts`** (second genuinely distinct taxonomy): `MSTeamsSendErrorKind = "auth"|"throttled"|"transient"|"permanent"|"network"|"unknown"` — explicit HTTP-status-driven (`401`→auth, `403`→permanent unless `ContentStreamNotAllowed`, `429`→throttled w/ retryAfterMs, `408`/`>=500`→transient w/ retryAfterMs, other `>=400`→permanent, no-status transport codes→network, else unknown). Deliberately conservative: only marks retryable when there's an explicit accept/reject status, to avoid duplicate posts on ambiguous transport failures — structurally similar to `FailoverReason` in spirit (auth/throttled≈rate_limit/transient≈server_error/permanent/network/unknown) but independently implemented with its own thresholds.
- **`src/infra/errors.ts` `ErrorKind`**: `"refusal"|"timeout"|"rate_limit"|"context_length"|"unknown"` — a **coarser sibling of FailoverReason** used only to label chat-UI error events (`detectErrorKind`, fallback when no `errorKind` already attached). Has a `"refusal"` category FailoverReason lacks, and renames `context_overflow`→`context_length`.
- **`src/infra/diagnostic-error-metadata.ts`**: a **third distinct taxonomy**, deliberately narrow and PII-safe for telemetry only — `DiagnosticErrorFailureKind = "aborted"|"connection_closed"|"connection_reset"|"terminated"|"timeout"`, plus JS-builtin-class buckets (`TypeError`/`RangeError`/etc.), plus a SHA-256-hashed request-id (never the raw id). Explicitly avoids walking `.cause`/nested properties to prevent triggering userland getters during diagnostic extraction.
- **`src/agents/tool-result-error.ts`**: a large explicit **tool-execution-outcome** status-string enumeration (error/failed/timeout/blocked/denied/forbidden/unavailable/disabled/aborted/cancelled/killed/invalid) — a different domain (tool results, not provider/channel failures) from everything else here.
- **`src/agents/embedded-agent-error-observation.ts`**: reuses the *same source module* as `FailoverReason` but carries the finer `ProviderRuntimeFailureKind` sibling enum, used to decide whether raw provider error text (which might contain an auth-HTML challenge page with leakable session content) is safe to log verbatim.
- **`src/shared/assistant-error-format.ts`**: pure user-facing text formatter — detects Cloudflare/HTML challenge pages and "generic provider internal error" text, but assigns no retry/permanent bucket; one of *three* independent implementations across the codebase (this file, Hermes-analog `_summarize_api_error`, and Telegram's `network-errors.ts`) that each separately detect Cloudflare/HTML challenge pages.
- **Billing detection provenance** — confirmed via `embedded-agent-helpers.isbillingerrormessage.test.ts`: `isBillingErrorMessage` is the *exact same* function that feeds `FailoverReason.billing`; there is no duplicate/separate billing pattern set anywhere in cron or channel code.

## 3. Cross-system synthesis

### 3.1 Meta-taxonomy: failure class → detection → response, both systems

| Failure class | Hermes: detection | Hermes: action | OpenClaw: detection | OpenClaw: action |
|---|---|---|---|---|
| Auth expired/invalid (refreshable) | 401 always; 403 default; message patterns | Rotate credential + fallback, non-retryable; per-provider one-shot refresh attempts first | 401/403 w/ message patterns | Rotate auth-profile first; only escalate to model fallback once profiles exhausted |
| Auth permanently revoked | **No distinct code path** — `auth_permanent` enum unused; entitlement-403 guard is a bolt-on function, not part of the classifier | Same as auth, diverted programmatically | High-confidence revoked/deactivated patterns + `DEACTIVATED_WORKSPACE` code | **Skips the whole provider immediately** — genuinely distinct, higher-priority path |
| Billing/credits exhausted | 402/403/404/400 + patterns; structured codes | Immediate rotate + eager fallback; **excluded** from "still retryable" once both exhausted (real-incident-driven, #31273) | 402 + patterns; reclassifies "periodic/quota-window" 402s to rate_limit | **Long disable** (5h→24h doubling backoff) instead of quick rotation — opposite instinct from Hermes' "rotate fast" |

| Upstream-aggregator wrapped rate limit (key itself fine) | Distinct category `upstream_rate_limit` — explicitly skips credential rotation, bypasses "wait for pool recovery" gate | | **No distinct category** — folds into generic `rate_limit`/`overloaded` | This is a **Hermes-only refinement** (OpenRouter-specific insight not present in OpenClaw's taxonomy) |
| Provider overloaded (5xx/529, not credential-specific) | Distinct `overloaded`; explicitly no rotate/fallback flags (avoid pool exhaustion); fallback only after retry_count>=2 | | Distinct `overloaded`; same aggressive same-provider-then-fallback as rate_limit, **default 0ms backoff** | Disagreement: Hermes treats overload as "wait and retry, don't burn the pool"; OpenClaw treats it identically to rate_limit (fast rotate, no backoff) |
| Generic server error (500/502) | Distinct `server_error`, retryable only, no eager fallback | | Mostly **degrades to `timeout`** unless message explicitly says server_error; absent from cooldown-policy helpers entirely | Disagreement: Hermes keeps server_error as a first-class bucket; OpenClaw treats it as barely-classified, folded into the timeout catch-all |
| Timeout/connection/transport failure | Distinct `timeout`; wide exception-type + message-pattern net; SSL-alert transient patterns explicitly routed here not to context_overflow; reasoning-model-aware disconnect handling | Eager fallback after retry_count>=2; primary-client rebuild once before fallback | Broadest catch-all — nearly everything 5xx-adjacent, DNS/socket errors, HTML/Cloudflare challenge pages funnel here | Continues fallback (transient bucket) |
| Context/token overflow | Distinct `context_overflow`; huge multi-provider pattern list; two different token/message-count heuristics depending on detection path (400 vs. disconnect) | Compress (fixed 2s pause, max 3 attempts), then abort with `compression_exhausted` | Distinct `context_overflow`, modeled as its own classification "kind" (not just an enum value) | **Does not advance model fallback at all** — stays inside compaction/retry logic exclusively; absent from every cooldown-policy helper |

### 3.2 Categories that exist only because a system owns the model-call loop

These are largely **irrelevant to a system built on the Agent SDK** (which handles the raw HTTP/session/token/retry mechanics internally) because they concern request-shape/wire-protocol details a caller of the SDK never touches directly:

- Hermes: `thinking_signature`, `llama_cpp_grammar_pattern`, `oauth_long_context_beta_forbidden`, `invalid_encrypted_content`, `multimodal_tool_content_unsupported`, `image_too_large`, `payload_too_large` (SDK request-compression/serialization is not something a CBX caller does by hand), the entire priority-1 provider-pattern-matching stage, per-provider one-shot 401-refresh flows (Codex/Vertex/Nous/Copilot/Anthropic), Z.AI/Nous provider-specific backoff ladders, `upstream_rate_limit` (OpenRouter-aggregator-specific wire quirk).
- OpenClaw: most of `ProviderHttpError`'s status/code/errorType normalization, the `format` bodyless-400-is-noise heuristic, `context_overflow`'s "does not advance fallback, stays in compaction logic" design (an Agent-SDK-based system likely delegates context management to the SDK entirely), the whole `LiveSessionModelSwitchError` control-flow carve-out, `session_expired`, `no_error_details`/`empty_response` (SDK-internal signal shapes).

### 3.3 Categories that apply to ANY agent system regardless of who owns the model loop

These generalize directly to a CBX taxonomy:

- **Auth/credential expiry** (distinguishing refreshable vs. permanently-revoked) — both systems independently arrived at this exact two-way split (Hermes: `auth`/`auth_permanent`; OpenClaw: `auth`/`auth_permanent`), a strong signal it's a load-bearing distinction for any system with rotatable credentials.
- **Quota/billing exhaustion** vs. **rate limiting** — both systems treat these as separate categories with materially different backoff philosophy (billing = long/permanent-ish backoff or abort; rate limit = short retry-then-rotate). Both flagged real production incidents driving the billing-side caution (Hermes: ~$40/48h; conceptually the same instinct in OpenClaw's 5h→24h billing-disable ladder).
- **Timeout/transport failure** (network-level, not provider-semantic) — universal; every layer of both codebases (agent core, cron, each messaging channel) reimplements its own version of "is this ECONNRESET/ETIMEDOUT-shaped."
- **Malformed/invalid output or request** (a tool-schema violation, a request the provider rejects as malformed) — both systems have a `format_error`/`format` bucket, and both express real ambivalence about whether it should ever be retried (Hermes tries fallback; OpenClaw treats it as near-terminal but carves out a bodyless-400 exception).
- **Content/safety policy refusal** — a distinct, deterministic (non-transient) failure mode that both systems recognize exists, though they disagree on whether it belongs in the failover machinery at all (see 3.1 disagreement above).
- **Model/resource not found** — universal "the thing you asked for doesn't exist," both jump straight past retry/rotation logic that would never fix it.
- **Empty or missing error detail from a provider** — a defensive catch-all both systems needed once they had enough real-world traffic; worth a category in any system, if only to distinguish "provider gave us literally nothing" from "provider timed out."
- **The "unknown/unclassified" catch-all itself** — both systems deliberately keep it retryable-by-default rather than treating unclassified as fatal, and both treat it as low-priority in the fallback-eagerness ordering (retry within-provider before advancing).
- **A separate, coarser "what to tell the end user" taxonomy from "what recovery action to take"** — both systems independently split these: Hermes's `_summarize_api_error`/user-status-line formatting vs. `ClassifiedError`; OpenClaw's `ErrorKind`/`ProviderRuntimeFailureKind` (display) vs. `FailoverReason` (recovery decision). This split-by-purpose pattern (recovery-classification vs. display-classification vs. telemetry-classification) recurs so consistently it looks like a general design law, not incidental duplication.

## 4. CBX applicability sketch (skeleton only, no implementation)

CBX's actual failure surfaces, per the task brief: **SDK/agent-run errors**, **connector sync failures** (Gmail/Telegram/Calendar — auth+quota+transport), **scheduler/wakeup failures**, **card-validation failures**. A proposed taxonomy skeleton per surface, with rationale drawn from the synthesis above.

### 4.1 SDK/agent-run errors
Since CBX sits on the Agent SDK, it inherits the "Agent SDK owns the model loop" layer — CBX should NOT reimplement Hermes's/OpenClaw's provider-quirk categories (§3.2). What remains relevant and worth a CBX-level bucket:
- **Auth/credential expiry** (refreshable vs. permanent) — if CBX manages its own provider credentials/API keys outside the SDK's own auth, this split is still load-bearing.
- **Quota/billing exhaustion** — distinct from rate limiting; needs its own (probably long) backoff/notify path, mirroring both systems' independent convergence here.
- **Rate limiting** — short retry-then-back-off; should surface `Retry-After` if the SDK exposes it.
- **Timeout/transport** — SDK-level network failures should still classify separately from application-level failures, since the recovery action (retry the SDK call) differs from e.g. a card-validation failure (fix the data).
- **Malformed/invalid tool output** — a CBX card-schema validation failure surfacing *through* an agent run is a distinct case from a provider-format error; worth a dedicated bucket rather than folding into a generic "agent run failed."
- **Content/safety refusal** — worth tracking distinctly even if CBX's policy is "don't fail over for this," per OpenClaw's stance; the point is visibility, not necessarily an automated response.
- **Unknown/unclassified catch-all** — keep retryable-by-default, per both systems' convergent choice, rather than treating "we don't recognize this" as automatically fatal.

### 4.2 Connector sync failures (Gmail/Telegram/Calendar)
This surface maps closely to OpenClaw's channel-extension layer (§2.3), which is instructive precisely because each channel there built its *own* taxonomy rather than sharing one — suggesting CBX connectors will want a **shared base vocabulary** (auth/quota/transport/format) but connector-specific detection:
- **Auth expired** (OAuth token refresh failure, revoked grant) — split refreshable vs. permanent, same as §4.1; this is probably the single highest-value shared category across all three connectors given how much both source systems invest in it.
- **Quota/rate-limit** (Gmail API quota, Telegram flood control, Calendar API rate limits) — each provider has different units/reset semantics (daily quota vs. per-second flood), so detection is necessarily connector-specific even if the bucket name is shared.
- **Transport/timeout** — connector-agnostic network failure bucket.
- **Send/delivery-specific outcomes** (Telegram: message too long, bad markup, target chat gone, blocked-by-user) — OpenClaw's Telegram taxonomy shows this deserves its own sub-taxonomy distinct from generic transport, especially the **idempotency-aware retry-safety split** (pre-connect-safe-to-retry vs. post-connect-ambiguous) — genuinely worth adopting for any connector that sends outbound messages, since duplicate sends are a real user-visible bug class.
- **Permission/scope revoked** (calendar/gmail access removed by the user) — distinct from a transient auth failure; should disable the connector and notify, not silently retry forever (echoes OpenClaw's `auth_permanent` "skip immediately" + cron's "schedule-error auto-disable, notify the user" pattern from #28861).
- **Malformed remote data** (a calendar event or email CBX can't parse) — a format-shaped failure that's about *their* data being unusual, not CBX's request being wrong; worth distinguishing from a request-format error.

### 4.3 Scheduler/wakeup failures
Maps most directly to OpenClaw's cron taxonomy (§2.2), which is the most mature analog available:
- **Transient vs. permanent split with a bounded retry ladder** — directly reusable pattern: a small number of named transient categories (network, timeout, rate_limit, overloaded, server_error) checked first via any structured reason available from the underlying agent-run classification (§4.1), falling back to message-regex; everything else permanent.
- **A capped ladder, not unbounded exponential** — OpenClaw's 30s/60s/5m/15m/60m plateau (not indefinite doubling) is a concrete, reusable number set; CBX should pick its own but the "cap and plateau, don't grow forever" shape is worth keeping.
- **Separate counters for different failure origins** — OpenClaw distinguishes execution errors, schedule-computation errors (a bad cron expression), and skipped-runs (heartbeat disabled) as three independent counters rather than one blended "failure count." CBX's scheduler/wakeup should likely separate "the wakeup logic itself errored" from "the resulting agent run failed" from "the wakeup was skipped/suppressed."
- **Auto-disable + mandatory user notification** once a bounded threshold is hit — OpenClaw's #28861 fix (silent auto-disable was a real bug) is a directly-applicable lesson: any CBX scheduler auto-disable must notify, not just log.
- **A distinct, lower-threshold "alert" mechanism independent of the retry/disable decision** — OpenClaw's failure-alerts (after 2 consecutive errors, 1h cooldown) fire regardless of whether the job keeps retrying; worth separating "tell the user something's wrong" from "stop trying."

### 4.4 Card-validation failures
No close analog exists in either source system (both are chat/agent-first, not structured-data-first), but the closest parallels are Hermes's `tool_result_classification.py` (distinguishing a genuinely-failed mutation from noisy-but-successful diagnostic output) and OpenClaw's `tool-result-error.ts` status-string enumeration:
- **Schema violation** (required field missing, wrong type) — a deterministic, non-retryable-as-is failure; the "fix" is data correction, not backoff. Closest analog: OpenClaw's `format` bucket philosophy ("retrying the same payload fails the same way").
- **Reference/dependency failure** (a card references another card/entity that doesn't exist or was deleted) — analogous to `model_not_found`/`session_expired`'s "the target of this operation is gone" shape; should skip retry and surface directly.
- **Migration/version mismatch** (an old-shape card hitting new validation code) — a CBX-specific category with no direct source-system analog; worth its own bucket given `cb-migration`'s existence as a distinct concern already in this codebase.
- **Transient write-contention** (concurrent card write, lock contention) — analogous to OpenClaw's session-write-lock carve-out (§2.1, "must abort, not consume failover candidate slots") — worth treating as retryable-with-backoff but explicitly not as a "provider is broken" signal.
- **Successful-but-noisy result** — Hermes's `file_mutation_result_landed()` distinction (nested lint/diagnostic output inside an otherwise-successful write) is directly relevant: a card write that succeeds but reports secondary warnings shouldn't be classified as a failure.
