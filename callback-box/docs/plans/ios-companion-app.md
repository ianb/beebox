# iOS Companion App for Callback Box

**Status:** active — umbrella plan; the pairing/auth and APNs tracks need their own subplans before implementation. (Revised 2026-07-06 after a codex cross-model review.)

This plan designs a native iOS app that pairs with one or more self-hosted Callback Box instances and replaces the parts of the web experience that are weak on a phone: text/voice **input**, **audio** (both listening and the box speaking back), and **capture/sharing** into the box. It is deliberately **not** a full iOS port of the web UI. **The conversation view itself is the box's existing web chat, embedded in a `WKWebView`;** the app makes native only the parts that are weak in mobile web — input, voice, capture, and notifications. The native input POSTs to `/chat/send`; to make the embedded webview show that turn *streaming live* (not just refresh once it finishes), a box-side change broadcasts the native-started `turnId` on the event bus so the webview subscribes to that turn's stream (**Track H**) — because today `/chat/send` returns the `turnId` only to the POSTing client and other clients see only the turn-end `chat-complete`. This keeps native and webview in sync through the box (no `WKWebView`↔native JS bridge), but it is a real box-side change, not free reuse. The app targets **public App Store distribution** as a client for users' own self-hosted boxes (no commercial hosting), stands on its own as a **standalone mobile client**, and treats **audio as a core capability** within the ceiling iOS actually permits (see Track D and Failure modes).

## Why an app at all (vs. the messaging-channel alternative)

The lowest-hassle way to reach a box from a phone already exists and is shipped: the **Telegram connector** (`src/webapp/routes/telegram.ts`). This mirrors the peer landscape — **Hermes** ships no native app and reaches phones purely through ~30 messaging platforms + a web dashboard; **OpenClaw** ships iOS/macOS/Android companion apps but they are WebView hosts (freeform HTML or the A2UI declarative protocol rendered in a WebView) and its own docs call that surface *"low-use and experimental… a bundled plugin, not a core feature"* (`research/openclaw-hermes/deep-openclaw-canvas-a2ui.md`). Both peers primarily reach the phone through existing chat apps.

So this plan justifies the app on the **native-only capabilities messaging cannot provide**: a native input composer with **on-device STT** (offline dictation), **on-device TTS + a voice session that survives screen-lock**, a **Share Extension**, and control over **audio/notification** behavior. Reading threads, replying, and being pinged are *not* the justification — Telegram already does those; the native input/voice/capture experience is. The boxholder is confident the native voice experience will land, so the plan proceeds on that expectation rather than gating on a prove-it-first experiment. Telegram remains the standing fallback if reality disagrees, but it is not a checkpoint the plan waits on.

**Design invariant that keeps a configurable backend from becoming a maintenance hassle:** the heterogeneous/configurable surface (chat, cards, views — which vary per box) lives *only* in the embedded WebView, which renders whatever the box is configured to render. **Native code touches only stable contracts** (`/chat/send`, `/capture`, pairing) and must never depend on box-specific config, schemas, or views. This is the same pattern every front-end to a configurable self-hosted service uses — Home Assistant (WebView of your own frontend), WordPress iOS (stable REST API + WebView), Discourse's DiscourseHub (WebView shell + native push), OpenClaw Canvas. It is what makes fronting an "unknown/configurable" box tractable rather than a per-box hassle.

## Stated preferences this plan trades against

This plan spans two codebases: box-side changes (TypeScript, this repo) and a new Swift/iOS codebase. The box-side work is evaluated against the usual references; the iOS work against Apple's platform contracts, which this plan treats as an external boundary (principle 3).

- `callback-box/docs/engineering-principles.md` — the ones this plan leans on:
  - **#1 Types are structure** — a paired device is a new identity crossing the wire; it needs a branded token type and a typed device record, not a bare `string` (the box has branded-path/card-ID precedent).
  - **#3 Validate at boundaries** — the phone is a new untrusted input boundary. Every request it makes (paired-token auth, submitted emissions, share payloads, APNs registration) is validated once at the boundary with `safeParse`, like the `/chat/send` body. Note the *inbound* direction is the validated one; the event-bus stream a client reads is **not** a validated boundary today — `event-bus.ts` types read-side payloads as `unknown` and leaves validation to consumers (schemas are a tracked follow-up), so a native WS consumer must validate for itself rather than inherit a validated contract.
  - **#4 Resilient AND never silent** — the phone operates over a flaky connection by design (offline STT, queued sends). Degradation is expected and must stay visible, never a silent drop.
  - **#8 One way to do each thing** — the phone must not become a second, divergent input pipeline. It hits the same `/chat/send` contract the web composer does. But the `<speech>`/selections/attachments assembly is **frontend-only TypeScript** today (`chat-assemble.ts`), not a shared or server-side contract — so "don't reinvent it" means either moving that assembler to a shared/server surface or reimplementing it in Swift pinned by cross-language tests, not literal reuse (see What already exists).
  - **#5 Failure paths in signatures** — pairing/auth is a place callers branch on *why* (expired token vs unknown device vs revoked), so a discriminated Result is the right shape box-side.
- `callback-box/CLAUDE.md` — the tRPC-vs-raw-Fastify boundary (`CLAUDE.md`: *"Raw Fastify routes … are only for … file upload/download, OAuth redirects, webhooks, and the `/chat/send` POST"*); "keep source generic, never hardcode personal names."
- `callback-box/code-style.md` — standard mechanical rules for the box-side TS.
- **Most relevant precedents:** the **Telegram webhook** (`src/webapp/routes/telegram.ts`) — the existing "external device submits input to a box remotely with secret-token auth" shape (note it uses its own `ChatSessionPool`, distinct from the `/chat/send` path the phone will actually use); and the **web chat client** itself (`/chat/send` + `events.turnStream`), which is the closer model since the phone submits through the same registry-backed endpoint. Mirror these rather than inventing a parallel pipeline (principle #8).

## What already exists

The box is further along toward this than a greenfield companion app would be. Concretely:

- **Input abstraction — reference, not wire contract.** `src/frontend/src/input/emission.ts` defines the `Emission` value object (`readonly id`, `origin`, `text`, `images`, `files`, `selections`, `diarized`) with `createTypedEmission` / `createVoiceEmission`; `input/targets/chat-target.ts` (`acceptEmission`) turns it into a send. **`Emission` is a frontend-only TypeScript object — not the backend's wire contract.** The backend accepts `{ message, session, messageId, images, ... }` (`chat-helpers.ts`), and the `<speech>` wrapper / selections / attachments block is assembled in frontend TS (`src/frontend/src/input/targets/chat-assemble.ts`). So the phone can model an emission however it likes, but the assembler that turns it into the `message` string is what must be replicated (Swift) or relocated (shared/server) — see principle #8 above.
- **Backend input entry — reuse, with a streaming caveat.** `POST /api/chat/send` (`src/webapp/routes/chat-send-routes.ts`, `registerChatSendRoutes`) with body `sendBodySchema` → `SendBody` (`src/webapp/routes/chat-helpers.ts`). It returns a **`turnId` to the POSTing client only** (`chat-send-routes.ts:296`); live streaming is a subscription to `events.turnStream` keyed by that `turnId` (`trpc/routers/events.ts`). Other clients do **not** see the stream — they get only the turn-end `chat-complete` broadcast and refresh. `messageId` dedups *retries*, not concurrent sends (`chat-send-routes.ts:214`). Per-session concurrency is a busy-check/enqueue on `ChatSessionRegistry` (`chat-send-routes.ts:203,246`), **not** the Telegram `ChatSessionPool`. This is the phone's submit target and is not coupled to any STT provider — but "the webview sees the native turn stream live" needs Track H.
- **Remote-input precedent — reuse the pattern.** `src/webapp/routes/telegram.ts` (`registerTelegramRoutes`): secret-token header → append to thread → route into a persistent per-thread session via `ChatSessionPool` (`src/core/chat/session/pool.js`), stream `<chat-response>` back. Event bus: `src/core/event-bus.ts`.
- **Transport — reuse.** tRPC primary (`src/webapp/trpc/router.ts`), subscriptions over WebSocket (`wsLink`), raw Fastify for streaming/webhooks. The phone uses the same surfaces.
- **Auth — partially reuse, partially build.** `src/webapp/auth.ts`: Google OAuth → signed `cb_session` cookie (`signSession`/`verifySession`/`getSessionUser`); bearer diag key (`verifyDiagBearerKey`, `CB_DIAG_API_KEY`); hub headers (`verifyHubSecret`, `CB_HUB_SECRET`, `resolveRequestIdentity`). **No device-pairing / long-lived personal-token concept exists** — this is the one genuine gap (Track A). The bearer-key check and the Telegram secret-token pattern are the nearest reusable primitives.
- **TTS — reuse.** `POST /api/chat/tts` (`src/webapp/routes/chat-audio-routes.ts`, `registerChatAudioRoutes`) proxies OpenAI `gpt-4o-mini-tts` (voice "marin"). Playback is browser-side today; the phone plays natively instead.
- **STT — reuse selectively; the live leg is more than transcription.** `src/core/transcription/index.ts`: `TranscriptionService = "whisper" | "voxtral" | "deepgram" | "openai-realtime"` (`:108`), default `{ service: "voxtral", hqService: "whisper" }` (`:147`). Live stream proxies Mistral Voxtral at `/api/chat/transcribe-ws` (`:152`, `:161`); batch HQ pass `transcribeAudioHq` (`:229`). The phone replaces the *live* leg with on-device STT and keeps the *HQ* leg by uploading recorded audio (Track D). But the web voice path (`InteractiveChat-voice.ts:95,124,136,145`) also freezes selections, folds prior text, shows pending-HQ UI, re-runs keyword detection on the HQ text, re-injects a send keyword if HQ normalized it away, and retains audio by emission id. **Replicating this voice loop is the real cost** (the keyword-spotter critical gap below), not the transcription swap itself.
- **Diarization — a non-issue for on-device STT.** Diarization is produced **server-side** by Voxtral's `diarize=true` on the *uploaded HQ audio* (`voxtral-request.ts:96/189`, `voxtral-text.ts` `buildDiarizedText`), consumed as `<speech diarized="1">` (`chat-assemble.ts`), explained to the agent at `src/core/chat/session/prompts.ts:52`, gated behind off-by-default **narration mode** (`InteractiveChat-hooks.ts:145`). Because it lives entirely in the server HQ pass on uploaded audio — which the phone keeps — the fact that on-device STT has no *local* diarization changes nothing: there is no local diarization anywhere in the system, and none was expected. It is not a loss or a fallback tradeoff.
- **Push — reuse the store, build a new channel.** Web Push (VAPID) is production-ready: `src/services/push.ts`, `src/core/send-push.ts`, `src/core/push-subscriptions.ts` (box-slug-keyed subscription store), tRPC `src/webapp/trpc/routers/push.ts`, `src/schemas/web-push.ts`, `src/connectors/push.ts`. **No APNs** anywhere. Track F bolts an APNs channel onto the existing box-slug subscription store rather than building a parallel one.
- **Capture — reuse for media only; text/URL needs a new endpoint.** `src/webapp/routes/capture.ts` (`registerCaptureRoutes`), `POST /api/capture/sessions`; finalize lands a card at `box/inbox/<name>.capture-session.card` (`src/webapp/routes/capture-finalize.ts`). **This is a media-upload pipeline** — a session with no uploaded file bytes finalizes to `cards: []` with `success: true` (`capture-finalize.ts:239`), so a plain URL/text share posted through it would **silently produce no card**. `box/inbox/` is the right target directory, but text/URL capture needs a dedicated endpoint (see Track E / Open questions).
- **iOS codebase — build (net-new).** There is no Swift code in the monorepo. `callback-clerk/` (the Chrome extension) is the precedent for "a client to a hosted box lives in the monorepo as its own top-level project"; the iOS app should follow that as `callback-ios/` (see Open questions for the monorepo-vs-separate-repo decision).

## Prior art (external)

Searched during planning (the audio/background question is the load-bearing external unknown). Findings with URLs:

- **Proactive/background audio is capped by iOS, and the cap is documented.** A suspended app cannot start new audio; background-audio mode only *continues* already-playing audio. Sources: Apple `AVAudioSession` (https://developer.apple.com/documentation/AVFAudio/AVAudioSession), Mux (https://www.mux.com/blog/background-audio-handling-with-ios-avplayer), sagorin.org (https://www.sagorin.org/ios-playing-audio-in-background-audio/).
- **Silent-audio keepalive is an App Store rejection (Guideline 2.5.4).** https://developer.apple.com/app-store/review/guidelines/ ; rejection reports: Apple Forums 105443 (https://developer.apple.com/forums/thread/105443).
- **Reliable backgrounded "speak now" = alert push with a custom sound, ≤30s, `.caf/.aiff/.wav`, in the app bundle or App Group container; a Notification Service Extension can fetch/render the clip.** Sources: Insider One (https://academy.insiderone.com/docs/ios-customizing-notification-sound), OneSignal (https://documentation.onesignal.com/docs/en/notification-sounds), STRV (https://www.strv.com/blog/app-extensions-introduction-to-notification-service-engineering).
- **Silent (`content-available`) push is throttled and not guaranteed** — treat as best-effort data sync, not an audio trigger. Bugfender (https://bugfender.com/blog/advanced-ios-push-notifications/), Pushy (https://support.pushy.me/hc/en-us/articles/360043925371), Apple Forums 114124 (https://developer.apple.com/forums/thread/114124).
- **PushKit/VoIP push now requires reporting a real CallKit call (iOS 13+) or the app is terminated** — not a general background-wake mechanism. Apple Forums 118607 (https://developer.apple.com/forums/thread/118607), Twilio voice-quickstart #251 (https://github.com/twilio/voice-quickstart-ios/issues/251).
- **Continuously-active session survives screen-lock** (the ChatGPT-voice-mode / turn-by-turn-nav pattern) via `UIBackgroundModes: audio` + an active session — the sanctioned way to keep a *user-initiated* session alive through display sleep. getstream.io (https://getstream.io/blog/ios-background-modes/).

**Self-hosted iOS client review — researched (Home Assistant, Nextcloud, Immich, Swiftfin, Prologue, Mastodon clients):**
- **Sign in with Apple (Guideline 4.8) is NOT required** for an app that authenticates only to the user's own server. The "must also offer" rule triggers *only* when the app itself presents a third-party/social login (Google/Facebook Sign-In). Two independent exemptions cover a QR-pairing-to-your-own-server flow: "your company's own account setup and sign-in systems" and "client for a specific third-party service." Since cb's Google OAuth happens on the *desktop web* side (outside the app) and the app only scans a QR to pair, the app is exempt — **as long as no in-app social login is added** (that would break the exemption). Source: https://developer.apple.com/app-store/review/guidelines/#login-services. This resolves the pivotal Track A question in the app's favor.
- **The demo-server requirement (Guideline 2.1(a)) is the hard practical gate.** Apple can't reach a user's private box, so at submission the developer must supply one of: (a) a live, publicly-reachable demo box + non-expiring credentials in App Store Connect's private review notes; (b) a built-in demo mode showing full functionality — **requires prior Apple approval**; or (c) a demo video for hard-to-replicate setups. Apps with free public self-signup (Mastodon) sidestep this; a private self-hosted-only app (Prologue) is the closest analog and its solution is undocumented (in Apple's private notes). Sources: https://developer.apple.com/app-store/review/guidelines/#app-completeness, https://developer.apple.com/help/app-store-connect/reference/app-review-information/, https://developer.apple.com/forums/thread/810791.
- **The 4.2 "web-wrapper" line is reviewer discretion, not a checklist — and it cuts both ways.** Home Assistant is *heavily* WKWebView-based (its dashboard is a webview of the user's own HA frontend) yet ships, carried by a broad native surface: push/Live Activities, location/sensors, CarPlay, Apple Watch, WidgetKit, App Intents/Siri, native onboarding. Conversely Ice Cubes — *fully native* SwiftUI — was rejected under 4.2.2 **seven times in six days** and only cleared after press pressure (a Daring Fireball article), not a code change. Lesson: native-vs-webview is not the axis; **breadth of things-a-browser-can't-do is.** Keep the webview as a component inside a native shell (which this plan does), and add cheap high-signal OS integrations. Sources: https://developers.home-assistant.io/docs/apple/architecture/, https://companion.home-assistant.io/docs/getting_started/, https://daringfireball.net/2023/01/ice_cubes_app_store_limbo.

**Not yet searched (research debt, owed before the relevant track starts):**
- **On-device STT: `SpeechAnalyzer`/`SpeechTranscriber` minimum-iOS and whether it is the dictation-grade engine** vs the older `SFSpeechRecognizer` floor. Owed before Track D.
- **On-device TTS premium/enhanced-voice licensing and whether `AVSpeechSynthesizer` can render to a file inside a Notification Service Extension.** Owed before Track D/F.

## Tracks / scope

Ordered by implementation dependency, then surface size. Box-side TypeScript: Tracks A, B, G, H (and the Track E capture endpoint). iOS app: Tracks C, D, E (client), F.

### Track A — Box-side device pairing & authenticated channel *(subplan)*
- **What.** A pairing flow that issues a long-lived per-device token to a phone, and box-side verification of that token on every phone request, sitting alongside the existing session-cookie / bearer-key / hub-secret checks in `auth.ts`.
- **Why this needs to change.** No device-pairing primitive exists (`auth.ts` has only OAuth cookie, diag bearer, hub headers). Every other track depends on an authenticated phone↔box channel, so this is the spine.
- **Direction.** Desktop web (already authenticated) displays a QR encoding `{ boxUrl, oneTimeCode }`; the app exchanges the code for a branded `DeviceToken` bound to a typed device record `{ deviceId, label, boxSlug, issuedAt, revokedAt? }`; the token is sent as a bearer header and verified via a new `verifyDeviceToken` returning a discriminated Result (`ok | { reason: "expired" | "unknown" | "revoked" }`, principle #5). Tokens are revocable from an admin surface. **Sign in with Apple (4.8) is not required** (Prior art: QR-pairing to the user's own server is exempt) — the one hard constraint this imposes is a negative one: **the app must not add any in-app social login**, or the exemption breaks.
- **The credential must also authenticate the embedded webview and carry user identity**, not only pass a native API request. Two real complications the subplan must settle: (1) the `WKWebView` loads the box's chat page, so pairing must yield a credential the webview carries — a `cb_session`-compatible cookie installed into the `WKWebView` cookie store, or a device token exchangeable for a web session — so `verifyDeviceToken` and `verifySession` converge on one identity (principle #8). (2) **User attribution.** `/chat/send` attributes the sender via `getSessionUser(request)`, which reads the `cb_session` cookie *only* (`chat-send-routes.ts:205`, `auth.ts:191`); and **hub-mode boxes never trust session cookies — they trust only hub-injected secret-gated headers** (`auth.ts:272,282`, `resolveRequestIdentity`). So a device-token prehandler bolted on beside these would authenticate the request but leave chat attribution null unless device-token identity is unified across `resolveRequestIdentity`, the tRPC context, and `getSessionUser`. This is the subplan's hardest problem, not a detail.
- **Vocabulary lock-ins** — `DeviceToken` (branded), the device-record field names, the pairing endpoint path.
- **First implementation chunk** — *blocked on the subplan*; the token format and the device-token/web-session convergence (so one credential authenticates both native requests and the embedded webview) are the remaining open decisions. It needs `docs/plans/ios-pairing-auth.subplan.md` first. (The Sign-in-with-Apple question is now resolved — see Prior art.)

### Track B — Box-side APNs push channel *(subplan)*
- **What.** An APNs sender alongside the existing Web Push sender, feeding the same box-slug subscription store.
- **Why this needs to change.** Notifications and the ≤30s spoken-alert mechanism (Track F) require APNs; none exists.
- **Direction.** Extend `push-subscriptions.ts` to hold APNs device tokens (discriminated on channel: `webpush | apns`), add an APNs sender service (`src/services/` real+fake, per the services convention), and route `web-push` output cards (`src/schemas/web-push.ts` / `src/connectors/push.ts`) to whichever channel a subscription uses. For spoken alerts, the payload carries the alert **text**; the phone synthesizes audio on-device (Track F). **Adding the channel discriminant is a store-schema change**, not a purely additive field: existing records are endpoint-keyed Web Push shapes (`keys: { p256dh, auth }`) validated by a zod load (`push-subscriptions.ts:24,97`), so the load must default old records to `channel: "webpush"` or it will reject them. That defaulting *is* a migration (see Rollout).
- **Vocabulary lock-ins** — the channel discriminant on the subscription record; the APNs payload shape.
- **First implementation chunk** — *blocked on the subplan* (`docs/plans/ios-apns-channel.subplan.md`): payload shape and the spoken-alert-vs-plain-alert split are open decisions.

### Track C — iOS app skeleton, pairing client, authenticated transport
- **What.** The Swift app: project skeleton, QR-scan pairing against Track A, a paired-box store (one or more boxes), and an authenticated HTTP/WS client to the box.
- **Why this needs to change.** Net-new; nothing exists.
- **Direction.** SwiftUI app; a `PairedBox` model persisted in the keychain (token) + app storage (metadata); a transport layer wrapping the box's `/chat/send` POST and the WS event-bus subscription. Multi-box = a list the user switches between.
- **First implementation chunk** — the app skeleton + a keychain-backed `PairedBox` store + a single authenticated "echo" request against a Track-A dev endpoint. This chunk depends on Track A landing a minimal verify path first.

### Track D — iOS input & voice session (on-device STT/TTS, keyword spotter, emission assembly)
- **What.** The native input surface: text composer, and a live voice session with on-device STT, the four-command keyword spotter, on-device or cloud TTS, and correct `Emission`/`<speech>` assembly on submit.
- **Why this needs to change.** This is the core "the input system sucks on the web" motivation, and it is native-only (on-device STT/TTS, screen-sleep-surviving session).
- **Direction.**
  - On-device STT (`SpeechTranscriber` on new iOS, `SFSpeechRecognizer` floor) streams interim results; raw mic audio is captured to a file in parallel from the same `AVAudioEngine` tap.
  - The **four voice commands** (`submit | cancel | mic-off | erase`, plus trigger phrases) — currently detected client-side in `input/voice-intent.ts` — are reimplemented in Swift against the on-device partial results.
  - On submit, the phone must assemble the `message` string the way the web client does — the `<speech>` wrapper (the "spoken" signal), selections, and attachments — since that assembly is frontend-only TS (`chat-assemble.ts`), not a backend contract. Either the assembler moves to a shared/server surface the phone calls, or it's reimplemented in Swift and pinned by cross-language tests against the TS output (principle #8). Then POST to `/chat/send`.
  - **HQ path preserved:** the retained raw-audio file is uploaded to the box for the Voxtral HQ pass (`/api/chat/transcribe-audio`), which returns higher-quality text and, when narration mode is on, server-side diarization (`Speaker 1A/1B`). On-device STT gives instant/offline text; the server HQ pass gives quality and diarization on the same audio. Diarization is entirely server-side, so nothing about it depends on the on-device leg.
  - TTS: on-device `AVSpeechSynthesizer` (offline/free, default mode when the box is unreachable or the user prefers it) or streamed OpenAI `/chat/tts` (quality, when online). A user toggle plus automatic degradation.
  - The live session uses `UIBackgroundModes: audio` + a continuously-active `.playAndRecord` session so it survives display sleep.
- **First implementation chunk** — text-only composer → `/chat/send` (no voice yet), proving the `Emission`/transport round-trip end to end. Voice is a later chunk within the track.

### Track E — iOS native capture surfaces (Share Extension + Siri/App Intents + Widget)
- **What.** Native ways to send content into the paired box without opening the chat: a Share Extension (URLs/text/images), an App Intents / Siri Shortcut ("add to my box", voice-first), and a home-screen Widget quick-capture.
- **Why this needs to change.** Native share-sheet and voice capture are stated goals and are native-only. **These also do double duty as the 4.2 "minimum functionality" defense** (Prior art: the corpus shows breadth of OS integrations — Share Extension, App Intents/Siri, Widgets — is what reliably clears the web-wrapper bar; these are cheap and align with a voice-first capture app).
- **Direction.** Media shares post to `POST /api/capture/sessions`; **text/URL shares need a new dedicated endpoint** (`POST /api/capture/url` or similar) — the existing session pipeline is media-only and silently produces no card for a fileless session (see What already exists), so this endpoint is a firm prerequisite of the track, not optional. Both land in `box/inbox/`. The extension needs the device token shared from the app via an **App Group keychain** item, and must respect the extension's memory/time limits (quick hand-off). The App Intent exposes "capture to box" to Siri/Shortcuts using the same endpoints; the Widget offers a one-tap capture entry.
- **First implementation chunk** — the box-side text/URL capture endpoint (testable without the app), then share a plain URL → box inbox card end to end. The App Intent and Widget are later chunks within the track.

### Track F — iOS notifications & spoken alerts
- **What.** APNs registration, notification handling, and the ≤30s spoken-alert mechanism via a Notification Service Extension.
- **Why this needs to change.** "Box speaks to me when I'm away," within the documented iOS ceiling.
- **Direction.** App registers for APNs → posts the token to Track B. Alert pushes carry text; a Notification Service Extension renders the text to a ≤30s `.caf` on-device (`AVSpeechSynthesizer` write-to-file) into the App Group container and sets it as the notification sound. Tapping the notification foregrounds the app into a full (unlimited) voice/chat session.
- **First implementation chunk** — plain APNs alert delivery (no spoken sound yet), proving the Track-B → device round-trip. The NSE spoken-alert render is a later chunk.

### Track G — Box-side embedded / conversation-only chat mode
- **What.** A mode of the box's web chat page that renders the conversation but suppresses the web composer (and the web voice UI), so the embedded webview shows the thread while the native input owns input.
- **Why this needs to change.** The app embeds the box's chat page in a `WKWebView`; without a composer-suppressed mode, the user sees a doubled/competing input (the web composer under the native one). No embed/hide-composer flag exists today — but the chat UI already separates the conversation view (`src/frontend/src/components/chat/InteractiveChat-messages.tsx`, `InteractiveChat-view.tsx`) from the composer (`InteractiveChat-composer.tsx`), so the mode is reachable without restructuring.
- **Direction.** An embed mode (query param or route) on `ChatPage` that mounts the message/view components without `InteractiveChat-composer` and without the web mic UI, leaving layout room for the native input. The webview stays a full box client (WS event-bus subscription intact) so it reflects sends from the native composer and any other client. Must respect the paired-device auth (Track A) for the webview's own requests.
- **Vocabulary lock-ins** — the embed-mode flag name and how it's passed (query param vs a dedicated route).
- **First implementation chunk** — an embed flag that renders `ChatPage` conversation-only (composer hidden), verified by loading the chat page with the flag in a desktop browser and confirming the thread renders and live-updates with no composer. Box-side and self-contained; can land before the iOS webview chunk.

### Track H — Box-side cross-client turn broadcast
- **What.** A box-side change so a turn started by one client (the phone POSTing `/chat/send`) can be streamed live by another client (the embedded webview), rather than only surfaced at turn-end.
- **Why this needs to change.** Today `/chat/send` returns the `turnId` only to the POSTing client (`chat-send-routes.ts:296`) and live streaming is a `turnId`-keyed `events.turnStream` subscription (`trpc/routers/events.ts`); other clients see only `chat-complete` and refresh (`InteractiveChat-ws.ts:129`). So without this, a native send would leave the webview showing a frozen conversation until the whole turn finishes — the original "independent clients, no bridge" assumption was wrong (found in codex review 2026-07-06).
- **Direction (chosen: box-side broadcast, not a JS bridge).** When a turn starts, broadcast its `turnId` (with `sessionId`) on the event bus so any subscribed client for that session can pick it up and subscribe to `turnStream`. The embedded webview's WS handler learns the native-started `turnId` and streams it exactly as it streams its own. This keeps sync in the box (the boxholder's chosen architecture) rather than wiring a `WKWebView`↔native JS bridge. The native app is itself a valid event sink for the same broadcast if it wants to show turn state natively.
- **Vocabulary lock-ins** — the broadcast event name and payload (`{ sessionId, turnId }`).
- **First implementation chunk** — emit the turn-start broadcast and have the *web* client subscribe to a turn it didn't start (verifiable entirely in the browser with two tabs: tab A sends, tab B streams it live). Box-side and self-contained; unblocks the webview-streams-native-send behavior before any Swift exists.

## Subplans

Both ship together with the parent when the parent completes; the parent links them as dependencies.

## Failure modes

New codepaths and their realistic failure modes.

> **Critical gap:** on-device STT keyword spotter (Track D) — if the Swift reimplementation of `voice-intent.ts` mis-detects "submit"/"cancel", a voice session could send a half-finished utterance or drop a completed one with no visible signal. No test and no handling exist yet (the codepath is net-new). Must land with a visible pre-send confirmation state and a test harness before the voice chunk ships.

> **Critical gap:** offline send queue (Track C/D) — a dictated emission composed offline must not be silently lost if the app is killed before the box reconnects. No persistence layer exists yet. The queue must be durable (survives app termination) and its pending/failed state must be visible (principle #4).

| What can fail | Test exists? | Handling exists? | Clear-or-silent? |
|---|---|---|---|
| Paired token expired/revoked mid-use (Track A) | No — net-new | Planned: discriminated Result → app re-pairs | Must be **clear** (app prompts re-pair), not a silent 401 loop |
| Emission composed offline, app killed before reconnect (Track C/D) | No | **Gap** — durable queue not yet designed | Currently would be **silent**; critical gap above |
| Keyword spotter mis-fires (Track D) | No | **Gap** — pre-send confirm not yet designed | Currently **silent**; critical gap above |

## Agent-flow / user-flow edge cases

- **Wrong tag / wrong field** — the phone must assemble the `<speech>` wrapper correctly; a malformed wrapper is the phone-side analog of picking the wrong tag. **PARTIALLY ADDRESSED** — the assembler is frontend-only TS (`chat-assemble.ts`), so correctness depends on either relocating it to a shared/server surface or pinning the Swift reimplementation with cross-language tests against the TS output (Track D). Not "free reuse."
- **Stale ref** — a shared item references a card that moved. **DEFERRED** — the Share Extension creates new inbox cards, not refs into existing ones, so this is out of the initial capture path; note in Track E.
- **Two agents / clients touching the same thread** — phone and web submit concurrently. **ADDRESSED** by the existing per-session busy-check/enqueue on `ChatSessionRegistry` (`chat-send-routes.ts:203,246`); `messageId` covers retry dedup only. (Not `ChatSessionPool` — that's the separate Telegram path.) Flagged in Failure modes to verify enqueue ordering for the new client.
- **Hand-edit drift** — n/a; the phone doesn't hand-edit card text. **ADDRESSED** (out of scope by construction).
- **Fabricated free-form value** — the phone submits user speech/text, not agent-fabricated content; on-device STT errors are transcription noise, not fabrication. The server HQ pass raises transcription fidelity. **ADDRESSED**.
- **Validation-error UX** — a phone request that fails box-side validation (bad token, malformed emission) must surface a readable error in the app, not a silent failure. **ADDRESSED** in Failure modes (principle #4/#5); concrete copy is Track C/D work.
- **Partial migration / transition state** — during rollout the box gains a new auth path and a new push channel while the web app is unchanged. **ADDRESSED with one caveat** — the auth path is additive, but the push-subscription store gains a `channel` field old records lack, so the zod load must default absent `channel` to `"webpush"` (a small default-on-read migration; see Rollout). During the window, old records read as `webpush` and new APNs records carry `channel: "apns"`.

## NOT in scope

- **A native reimplementation of the chat conversation view or the card/renderer system.** The conversation view is the box's web chat in a `WKWebView`; the rich card/view/renderer system (`src/frontend/src/renderers/`, browse pages) is likewise web. The app makes native only input, voice, capture, and notifications. Rationale: reimplementing the chat UI and renderer registry natively is a multi-month effort with no input/voice/capture payoff. **The 4.2 caveat is explicit:** because the primary interactive surface (the conversation) is web, the native surface (input, voice, on-device STT/TTS, share, push) is the *load-bearing* minimum-functionality defense — it must stay substantial, and the Home Assistant precedent (a webview-first self-hosted client that ships) is the bet. This is tracked as research debt (Prior art) and a live risk, not a settled fact.
- **Android / cross-platform.** iOS only; no React Native / Flutter shared layer. Rationale: the whole value proposition is native-iOS-only capabilities (on-device STT/TTS, share extension, background audio session); a cross-platform layer would forfeit exactly those.
- **An always-on voice companion** that speaks to a locked, untouched phone at length. iOS does not permit it (Prior art); the app caps at ≤30s spoken alerts + full in-app sessions. Rationale: platform ceiling, not a choice.
- **Commercial/hosted-box support or an account system.** The app pairs with users' own self-hosted boxes only. Rationale: stated by the boxholder; also simplifies the App Store "who is this for" story to the self-hosted-client model.
- **Replacing the box's server STT/TTS entirely.** The server HQ transcription (Voxtral, incl. server-side narration diarization) and OpenAI TTS remain; on-device is the offline/interactive default with the server as the quality path. Rationale: the server HQ pass gives quality and diarization on uploaded audio, and lower on-device TTS quality means keeping OpenAI as the online path (principle #4 — degrade gracefully, don't remove the capable path).

## Open design questions

- **Where does the iOS code live?** New `callback-ios/` top-level project in this monorepo (mirroring `callback-clerk/`), or a separate repo? Lean: **in the monorepo** as a top-level project — keeps the box-side contract and the client versioned together, matching the clerk precedent. Xcode/Swift tooling doesn't touch the pnpm workspace.
- **Shape of the text/URL capture endpoint.** That a dedicated endpoint is needed is settled (the media session path silently no-ops for text). Open: its exact shape — a small `POST /api/capture/url` that writes an inbox card directly, vs. routing text through a thread append. Lean: a dedicated capture endpoint validated at the boundary (principle #3), not overloading `/chat/send`.
- **On-device STT minimum iOS.** If `SpeechTranscriber` (the good engine) requires a very recent iOS, what's the minimum-iOS floor, and do we ship the `SFSpeechRecognizer` fallback or just set a high floor? Unresearched (research debt above).
- **How reviewers get a working box (Guideline 2.1(a) demo requirement).** Stand up a public demo box + non-expiring credentials in App Store Connect review notes, or build an Apple-approved in-app demo mode? Lean: **a public demo box + review-notes credentials** — simpler than a demo mode (which needs prior Apple approval), and it mirrors what Immich/HA appear to do. This is a submission-time deliverable, not app code, but it's a real gate — flagged in Rollout.
- **Multi-box UX.** Switching the active box vs. viewing an aggregated inbox across boxes — how central is multi-box on day one? Lean: pair multiple, but operate one active box at a time initially.
- **Native input ↔ webview coupling — decided: box-side broadcast (Track H), no JS bridge.** Codex review (2026-07-06) showed the naive "both are independent WS clients" assumption fails: `/chat/send` gives the `turnId` only to the POSTer, so the webview can't stream a native-started turn without help. Chosen fix is the box-side turn broadcast (Track H), not a `WKScriptMessageHandler` bridge — it keeps one sync path through the box (principle #8). A bridge stays a later option only if a concrete UX gap (e.g. reflecting an interim transcript mid-dictation) demands it.

- **APNs channel (Track B)** — same: infrastructural, not agent-recalled. **Skip-with-rationale.**
- **`<speech diarized="1">` on the phone path (Track D)** — unchanged concept: diarization is still produced server-side on uploaded audio (the phone just uploads audio like the web client does). **No new audit needed**; the existing narration audit still covers it since the signal's producer (the server HQ pass) is unchanged.

## Implementation order

1. **Track A subplan** → minimal `verifyDeviceToken` + pairing exchange + identity unification (box-side). Everything depends on it.
2. **Track G first chunk** — box-side embedded / conversation-only chat mode (composer-suppressed `ChatPage`). Box-side and independent.
3. **Track H first chunk** — box-side turn-start broadcast; a client streams a turn it didn't start (verifiable two-tab in a browser). Unblocks "webview streams the native send."
4. **Track E box-side** — the text/URL capture endpoint (box-side, testable without the app).
5. **Track C first chunk** — app skeleton + keychain `PairedBox` + authenticated echo against Track A; embed the Track-G chat webview under the paired credential.
6. **Track D first chunk** — text composer → `/chat/send` round-trip; webview streams the native turn via Track H.
7. **Track E client** — share a URL → inbox card (against the Track-E endpoint).
8. **Track B subplan** → APNs sender + channel discriminant + defaulting migration (box-side).
9. **Track F first chunk** — plain APNs alert delivery.
10. **Track D voice chunk** — on-device STT + keyword spotter + HQ upload + TTS (the biggest chunk; depends on the critical-gap resolutions).
11. **Track F spoken-alert chunk** — NSE renders ≤30s clip.

Steps 1–9 establish the spine and each feature's thinnest end-to-end slice, front-loading the box-side pieces (A/G/H/E-endpoint) that are testable with no Apple tooling; 10–11 are the heavy audio work, last because they depend on the critical-gap designs (durable queue, pre-send confirmation).

## Rollout shape

- **Test posture.** Box-side (TS) gets doctests per `docs/testing.md`: a route doctest for `verifyDeviceToken` (`makeTestServer()`) covering the expired/unknown/revoked Result branches (the Track A Failure-modes rows); a route doctest for the APNs channel routing (Track B), reusing the Web Push test patterns; a route/filesystem doctest for the capture-url endpoint if added (Track E). The iOS side is tested with Swift/XCTest in its own project — the box-side contract is what this repo's doctests pin. The done-when for the box-side tracks is those doctests passing; the iOS done-when is each track's first-chunk round-trip demonstrated on device.
- **Knowledge-audit entries.** None new (see Knowledge audits); diarization is unchanged (server-side), so the existing narration audit still applies.
- **Migration.** One **defaulting migration**, in the push-subscription store. The device-token auth path is genuinely additive (a new credential type alongside existing auth). But the APNs channel discriminant changes the persisted push-subscription schema: existing endpoint-keyed Web Push records have no `channel` field, and the zod load (`push-subscriptions.ts:97`) will reject them unless the load defaults absent `channel` to `"webpush"`. That default-on-read *is* a (small, in-place) migration — the Track B subplan specifies it, and the earlier "no on-disk migration" framing was wrong (codex review 2026-07-06).
- **App Store submission gate (not app code, but a hard gate).** Guideline 2.1(a) requires reviewers to reach a working box. The submission deliverable is a **public demo box + non-expiring credentials placed in App Store Connect review notes** (see Open questions), plus review-notes text explaining the QR-pairing step so the reviewer can pair against it. Because 4.2 rejections are reviewer-discretionary and sometimes arbitrary (Prior art: Ice Cubes), budget for an appeal/resubmit cycle and lead with the native-surface breadth (voice, on-device STT/TTS, Share Extension, App Intents/Siri, Widget, push) in the review notes.
